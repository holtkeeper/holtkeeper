# @holtkeeper/guide

The Guide: the rules every agent task of a repository follows, in one place. Humans write team rules per scope and section; a generator ([@holtkeeper/guide-generator](../../guide-generator/docs/README.md)) proposes text from repository signals; accepted learnings from review replies sit next to them. One resolver turns all of it into the stable context block of review, thread replies, agent tasks, release notes and MCP.

Human-written rules always outrank generated text: research on context files found that rules people write help agents, while generated ones alone make them worse. Generated text is therefore marked lower priority in every prompt and reaches tasks unaccepted only when nothing human exists.

## Model

- **Sections** (`guideSections`): `general`, `review`, `testing`, `testids`, `assets`, `commits`, `releases`.
- **Scopes** (`GuideScope`, keyed by `guideScopeKey` / `parseGuideScope`): `all` → `team:<team key>` → `path:<forge>:<folder>` (a folder of the forge's path tree and every repository under it, e.g. `path:work:acme/round`) → `family:<id>` → `repo:<forge>:<path>`. `scopesFor(repo, family?)` lists the keys that apply to a repository, most specific first: the repository, its family, every folder holding it deepest first (`pathAncestors` of [@holtkeeper/access](../../access/docs/README.md)), its owner teams (`repo.teams`, in their given order), then `all`. Team scopes hold process rules (how the team reviews, commits, releases); code rules belong on folders and families. See [Teams and paths](../../../docs/teams-and-paths.md).
- **Section row** (`GuideSection` in `Store.guides`, see [@holtkeeper/store](../../store/docs/README.md#guides-and-families)): human `rules` and `steering` with revisions, a `generated` layer (`body`, `inputHash`, `model`, `costUsd`, `status: proposed | accepted`, `generatedAt`, `sha?`, the run's extra `prompt?`, `acceptedBy?`/`acceptedAt?`), a `proposal` (newer generated text waiting while `generated` holds accepted text; the resolver ignores it) and `learnings`. Steering only steers the generator; it never goes into task prompts.
- **Families** (`Store.families`): a named set of similar repositories, e.g. near-identical app frontends of one team. A repository is in at most one family.

## Resolver

`resolveGuide(input)` is pure; `createGuideResolver({ store, teamTitle? })` reads what it needs (the repository's family, the sections of its scopes, policies from settings, accepted knowledge) and calls it. For a repository with no tests by design (`repo.tests`) it leaves out every stored `testing` section, so stale team or generated testing rules never reach agents. The result is `{ text, sections, blocks, warnings, budget }`.

Blocks, strongest first:

1. the repository's own rules files (`REVIEW.md`, `CLAUDE.md`, `AGENTS.md`, ...; capped, see Budget), passed in as `repoDocs` by callers with a checkout (the review reads them with `readGuidelines`) or read from the forge (`readRepoRuleFiles`); one `repo-file` block;
2. panel team rules of the repository, then its family, its folders deepest first (`path` layer, titled `Rules for folder acme/round`), its owner teams in `repo.teams` order (`team` layer, `Team rules for team …`), then `all`;
3. accepted learnings of those scopes;
4. policies as plain facts (`policiesFor`: the `commits.conventions` setting through `commitPolicyFacts`, the team's test id overrides in the `analyzers.testids` setting through `testIdOverridesFor` and `testIdPolicyFacts`, `testIdsSettingKey`, an `assets.policy` entry covering the repository through `assetsPolicyFacts` of `@holtkeeper/assets`, in the Assets section, and, for a repository with no tests by design (`repo.tests`), a General line telling agents not to add test files, frameworks or scripts, not to run tests and not to ask for tests in reviews);
5. generated sections of the repository under "Generated from repository signals, lower priority; ignore any line that conflicts with the rules above." (`GENERATED_HEADER`);
6. knowledge notes picked by `selectForTask` of [@holtkeeper/knowledge](../../knowledge/docs/README.md) from what budget is left. The task carries the repository's family id and, when known, the files it touches (`GuideNotes.files`, `GuideRequest.files`, e.g. a merge request's changed files), so entries narrowed by `match.families` or `match.files` apply only where they hold; without a file list a `match.files` entry still applies. When knowledge vectors are on, the server passes `GuideNotes.semantic` / `GuideRequest.semantic` (entry id → cosine between the entry's vector and the query's): it reaches `selectForTask` as `semantic` and only ranks the notes (text and vector rankings fused); it never makes a note apply.
7. knowledge of similar repositories (`neighbours` layer, titled `Knowledge from similar repositories`, source `Similar repositories: acme/square/web · …`), last and lowest: given `GuideNotes.neighbours = { repos, entries?, maxChars? }` (`repos`: `KnowledgeNeighbour`s from `repoNeighbours`, with their family id; `entries`: the candidates, default the notes' entries), `selectNeighbourKnowledge` picks accepted entries written for a neighbour but not for this repository, ranked by similarity × relevance (the notes' query and `semantic` map). It gets what the notes leave, at most `maxChars` (default `GUIDE_NEIGHBOURS_SHARE` = 15% of the total), so it is the first thing cut; `budget.neighboursUsed` is its size (`notesUsed` includes it). `GuideRequest.neighbours = { repos, readable?, maxChars? }` does the same through `createGuideResolver`: it fills each neighbour's family from the stored families when missing and keeps only entries `readable` accepts (the server's access rule, see its docs); `notesChars: 0` drops it with the notes.

Every block (`GuideBlock`) carries its `layer`, `scope`, prompt `title`, a short `source` (`REVIEW.md · AGENTS.md`, `This repository`, `Family Widget apps`, `Folder acme/round`, `Team widgets`, `Team Widget crew (widgets)`, `All repositories`, `Learned rules`, `Policies`, `Generated Testing`, `Team knowledge`, `Similar repositories: acme/square/web`), its `text` exactly as the prompt has it (the block texts in order, after the header, are the prompt), `chars`, `fullChars`, `cut`, and for generated text `proposed` and the stored `version`. Team blocks are titled through the `teamTitle` labeler (the server passes a `teamLabel` of the config); without one they name the key. Folder blocks name the folder without its forge (it is always the repository's own).

Sections per task (`sectionsForTask`): `review` reads `general`, `review`, `testing`, `testids`, `assets`; `release-notes` reads `commits` and `releases`; `chat` and `agent` read `general` plus the section the work is about. `focus` (on `resolveGuide` and `GuideRequest`) replaces the task's sections with the given ones; the Guide chain reads one section at a time this way. `guideTaskOf(taskKind)` maps agent task kinds (`review`, `release-notes`, `chat`, `tests` → `agent` + `testing`, anything else → `agent`).

**Budget** (`GUIDE_CAPS`): 12 000 characters in all, about 8 000 for human text and 4 000 for generated text. Long rules files never crowd out the rules people accepted: they get at most `repoFiles` (4 800, `GUIDE_REPO_FILES_SHARE` = 40% of the total) and must leave of the human budget what the repository's own team rules take plus `rules` (4 000, `GUIDE_RULES_SHARE` = a third of the total) for the other team rules, learned rules and policies, as much of it as those need. A rules file over its room is cut at a line break and ended with `[… truncated, see <file>]` (`truncatedMarker`); room for a heading and that pointer is kept for every later file, so no file disappears without one. Repository rules are placed next and never cut to make room for other layers; when they push human text over `human` the result carries a warning, and only past `total` is their end cut (also with a warning). The other human blocks share what is left of `human`: `all` is cut first, then owner teams (last one first), then folders (shallowest first), then the family, learnings and policies. Every cut, rules files included, adds a warning the Guide chain and the effective prompt show. Generated text gets at most 4 000 characters and what human text leaves; notes get the rest. Other cuts end at a line break with `[...]`. With a custom `total` (`caps`), `repoFiles` and `rules` follow its shares unless given.

**Unaccepted generated text** is included only when no human rules apply to the selected sections and the repository has no rules files.

**Determinism.** The same inputs give the same text whatever order rows come in, so the block can sit in a cached prompt prefix.

## Guide chain

`buildGuideChain(resolve, { repo, sections?, repoDocs? })` is the layered Guide of a repository per section, built with the same resolver prompts use, so order and cuts match: each section's layers are that section resolved alone (`focus: [section]`) for the task it stands for (`chainTaskOf`: `review` for Review, `release-notes` for Commits and Releases, `agent` otherwise, which picks the notes). `chainLayers(resolved)` turns the blocks into numbered layers (`GuideChainLayer { n, kind, scope?, source, text, chars, fullChars, cut, version?, proposed? }`) in agent reading order: repository files, repository rules, family, folders (deepest first), owner teams (in `repo.teams` order), all repositories, learned rules, policies, generated text, notes, knowledge of similar repositories, numbered from 1 without gaps. `buildGuideChain` passes `neighbours` (same shape as `GuideRequest.neighbours`) to every section it resolves. With one section the result's budget and warnings are those of the whole prompt of its task (a review also reads general, testing, testids and assets under the same 12k cap), so the bar shows what that prompt really uses; with several, those of all requested sections resolved together. The server's `GET /api/guide/chain` and the MCP tool `repo_rules` (which lists the layers under the text, and with `only` reads one section exactly as the chain does) both use it.

## Repository rules files

`readRepoRuleFiles({ forge, forgeId, repo, files, kv? })` reads the given rules files (the server passes the review's `GUIDELINE_FILES`) at the default branch head (`headCommit`), keeps the non-blank ones in order with their git blob sha (`blobSha`), and caches the result in `Store.kv` under the head sha (`guide:repo-files:<forge>:<repo>:<sha>`, 7 days), so an unchanged head never reads the forge again. Without a head sha every call reads. `repoDocsOf(files)` gives them to the resolver.

## Family suggestions

`suggestFamilies(signals, { threshold = 0.6, minSize = 2, exclude })` proposes families from `RepoSignals { repo, dependencies, toolchain }`: repositories with the same framework (`frameworkOf`: the first known framework dependency, meta-frameworks first) and the same toolchain (runtimes and package managers) are clustered by complete linkage on the Jaccard similarity of their direct dependency names (`jaccard`), so every two members reach `threshold`. Repositories without dependencies and `exclude`d ones (already in a family) are never proposed. Clustering ignores where repositories sit: `acme/round/web` and `acme/square/web` are suggested together when their dependencies agree. Each suggestion has a proposed `name` plus the framework: the members' shared shape when their paths differ in one folder segment only (`sharedShape`, e.g. `acme/*/web (react)`), else the last segment of the deepest folder they share (`commonFolder`) and the words their repository names share (e.g. `round/front (react)`); when two suggestions would get the same name, each adds a dependency only it shares, or a number), sorted `members`, the lowest pairwise `similarity`, `framework`, `toolchain` and up to ten `shared` dependencies. Suggestions only: a person confirms them through the families API. `familyOf(families, repo)` finds the family of a repository (a repository belongs to at most one). `suggestionKey(members)` is a suggestion's identity across runs (member set, sorted), which the server's dismissals use.

## Repository neighbours

`repoSimilarity(a, b)` is the similarity families cluster on: 0 unless both repositories have the same framework and toolchain, else the Jaccard similarity of their direct dependency names. `repoNeighbours(signals, repo, { limit = 5, min = 0.5, families? })` lists the repositories most like `repo` by it (`{ repo, similarity }`, similarity rounded to three decimals, most alike first, then by path), at least `min` and above 0, at most `limit`. The repository itself, repositories without dependencies and, given `families`, the members of `repo`'s own family are left out: they already share family knowledge. Folders do not matter, so `acme/round/web` and `acme/square/web` are neighbours when their stacks agree. The same signals always give the same list. The server feeds the result to the resolver's `neighbours` layer.

## Review learnings

Rules people teach Holtkeeper by replying to its review comments ("we don't do X here", "this is intentional because…"), stored apart from team rules and reaching prompts only after a person accepts them (`learnings.ts`).

- **Candidates** (`LearningCandidate` in `Store.learnings`): `rule` (one imperative sentence, at most `LEARNING_RULE_MAX` = 200 characters, no personal names), `key` (`normalizeRule`: lowercase letters and digits, single-spaced), `section`, `suggestedScope` (`learningScopeKinds`: `repo`, `family`, `path` or `team`; `path` means the folder directly holding the repository, `team` its first owner team; the default is `repo`), `targetScope` (an exact `repo:`, `family:`, `path:` or `team:` key of the repository the proposer named, e.g. an owner team or a parent folder; accepting without a scope goes there, `defaultLearningScope(candidate, scopes)`; `learningScopeKindOf(key)` gives its kind, which `suggestedScope` holds). `learningScopes(scopes)` lists where a learning of the repository may go, narrowest first: the repository, its family, its folders deepest first and its owner teams (everything but `all`); the panel offers them as the choices, `status` (`proposed`, `accepted`, `rejected`), `sources` (repository, merge request, discussion, note, the author's username, time, link; empty for a direct proposal), `proposal` (`{ by, reason }` for a direct proposal), extraction `model` and `costUsd`, and once decided `acceptedScope`, `decidedBy`, `decidedAt`.
- **Capture** (`captureLearning(deps, reply)`): `looksLikeFeedback(body)` is a deterministic filter first (substance plus convention, deliberate-decision or "do not flag" wording, English and Russian; thanks, "fixed" and questions never pass), so most replies cost nothing. A passing reply is claimed by its note (`learningSourceKey`): one note never makes two calls, and a failed call (a budget denial included) releases the claim and rethrows. The call is one turn on tier `fast` with no tools, task kind `LEARNING_TASK_KIND` (`learning`), a $0.02 cap (`LEARNING_CALL_CAP_USD`), the system prompt `LEARNING_SYSTEM` and the repository's known rules as `context`. `cleanRule` drops person `@mentions` and the thread's usernames from the answer's prose and caps its length (a cut that would end inside code ends before it); inline code spans and fenced code stay byte for byte, as do scoped package names (`@scope/pkg`, `@my.scope/pkg`), dotted decorators (`@app.route(...)`), CSS at-rules, TSDoc/JSDoc tags, JSX and eslint pragmas and test directives (`@font-face`, `@override`, `@jsx`, `@vitest-environment`), names glued to an identifier by `_` and dot tokens such as `.d.ts` or `.env`. The stored rule is that cleaned text; dedupe uses its separate key, `normalizeRule` (lowercase letters and digits only). A rule whose key matches a candidate of the repository adds the reply to that candidate's sources (`merged`, status kept); otherwise a `proposed` candidate is stored.
- **Direct proposals** (`proposeRule(store, { repo, rule, section, suggestedScope?, targetScope?, scopes?, reason, by, at })`): a rule proposed without a review reply, e.g. by the MCP tool `propose_rule_change`. No LLM and no cost (`model: 'none'`): `cleanRule` and the key check run, a rule the repository already has a candidate for returns `exists` with that candidate, otherwise a `proposed` candidate is stored with no sources. A `targetScope` must be one of `scopes` (the repository's `scopesFor`) and not `all`, else `LearningScopeError` and nothing is stored; so a rule can be proposed straight to an owner team (`team:widgets`) or a folder (`path:work:acme/round`). Review-reply extraction never sets one. Nothing reaches prompts until a person accepts it.
- **Decisions**: `acceptLearning(store, candidate, { scope, rule?, section?, by, at })` writes a `GuideLearning` with the candidate's id and source links into the scope's section (creating an empty section, no revision) and marks the candidate accepted; accepting again moves it. `editLearning` changes rule, section, suggested or target scope (a target sets the suggested kind; a new suggested kind alone drops the target; `all` throws `LearningScopeError`), and an accepted candidate's Guide entry follows. `rejectLearning` marks it rejected and takes an accepted rule out of the Guide. An edit that would duplicate another candidate's key throws `LearningConflictError`.
- **Reactions**: 👍/👎 on review comments are counted per finding category (`ReactionSignal`, `LearningStore.reactionTotals`) without an LLM; the server reads them when a merge request closes.

Accepted learnings sit in the resolver after team rules and before policies and generated text.

Generated layers carry a `version` the store assigns per section (1 for the first run that stored text, then up by one) and the `jobId` of the run; every stored version stays in the generated history (`Store.guides.generatedHistory`).

## Digests of rules files

`digest.ts` holds the read side of the condensed rules files that [@holtkeeper/guide-generator](../../guide-generator/docs/README.md#rules-file-digests) writes into `Store.kv`. A `RepoDigest` has lines in three groups (`digestGroups`): `general`, `review` and `code`, each with the heading it came from. `digestedDocs({ kv, forgeId, repo, task, docs })` swaps the text of every rules file of at least `DIGEST_MIN_CHARS` (3 000) characters for its digest when one is stored (`applyDigests`): a `review` reads `general` and `review` lines, `agent` and `chat` work `general` and `code`, release notes `general`. Each line ends with `(CONTRIBUTING.md § Heading)`, and the block says the file has the rest. Shorter files, files without a digest, digests of another version or (when `RepoDoc.sha` is known) of another version of the file, and digests with nothing for the task leave the original in place. `createGuideResolver` applies it to `GuideRequest.repoDocs` when the store has `kv`; the server's review path does the same.
