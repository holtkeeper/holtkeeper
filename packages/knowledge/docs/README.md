# @holtkeeper/knowledge

A knowledge base of team decisions that agents read and propose and people curate. Entries live in `Store.knowledge` (see [@holtkeeper/store](../../store/docs/README.md)); this package holds the rules around them: validation, classification of agent proposals, deduplication, and picking the entries an agent should read for a task.

## Entries

| Field                    | Meaning                                                                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`, `body`          | Short statement and markdown explanation                                                                                                                                                          |
| `kind`                   | `decision`, `convention`, `migration`, `quirk` or `howto`                                                                                                                                         |
| `scope`                  | The widest set of repositories it applies to and its authority (`Scope` from `@holtkeeper/access`: everything, owner teams, path patterns); `knowledge:write` over it accepts and edits the entry |
| `match`                  | Optional narrowing within the scope: `families` (family ids) and `files` (repository-relative path globs the task must touch)                                                                     |
| `topics`                 | Free tags, lowercase: `testing`, `i18n`, ...                                                                                                                                                      |
| `appliesTo`              | Task kinds: `review`, `port`, `propagate`, or `*`                                                                                                                                                 |
| `packages`               | `{ ecosystem, name, from?, to? }`; `from`/`to` are semver ranges. Required for migrations                                                                                                         |
| `visibility`             | `team` (default) or `shared`: other teams read it through the cross-team catalog                                                                                                                  |
| `subject`                | What it is about, a join key: `npm:react`, `Go:example.com/kit`, `tool:node`                                                                                                                      |
| `status`                 | `proposed` → `accepted` / `rejected`; `archived` when no longer true                                                                                                                              |
| `source`, `author`       | `human` or `agent`, and who created it                                                                                                                                                            |
| `evidence`               | Links `{ label, url }` backing it up                                                                                                                                                              |
| `supersedes`             | Id of the entry it replaces                                                                                                                                                                       |
| `version`, `history(id)` | `version` grows with every save; the store keeps every previous version with editor and time                                                                                                      |

A migration's `from` and `to` are the ranges it starts from and lands on: a react 18 → 19 note has `from: '>=18 <19'`, `to: '>=19 <20'` and applies to any task touching a react version in either range (`>=18 <20`).

## API

- `sharingDefaults({ kind, packages, subject?, visibility? })` — what an entry gets when its author leaves them out: an entry about exactly one package has that package as `subject` (`packageSubject`: `npm:<name>`, `Go:<module>`), and a decision or convention with a subject is `shared`. Everything else stays `team`. The server applies it to people's new entries too.
- `validateEntry(value)` → `{ success, data | issues }` and `knowledgeDraftSchema` (zod). Rules: the scope covers something, `appliesTo` is not empty, a `migration` names its packages. Topics are lowercased and deduplicated. `match` goes through `knowledgeMatchSchema`: `families` are non-blank ids, `files` non-blank repository-relative globs (no leading `/`, no `..`); lists come out unique, empty lists are dropped, and a match left empty is removed, so a stored match always narrows something.
- `classifyProposal(entry, { taskKind, repo, packages })` — pure heuristics filling what a proposal leaves out:
  - packages: task packages the text mentions (whole word, or the last segment of a scoped name), with `compatibleRange` of the task's versions;
  - kind: `migration` for such a package during `propagate`/`port` or upgrade wording; then `quirk`, `howto`, `convention` by wording; `decision` otherwise;
  - topics: keyword families (`testing`, `i18n`, `security`, `performance`, `build`, `dependencies`, `ci`, `release`, `api`, `style`);
  - appliesTo: the proposing task's kind plus kinds implied by kind and topics; `*` for quirks, how-tos and anything not narrowed.
- `selectForTask({ entries, task: { kind, repo, family?, files?, packages?, query? }, budgetTokens, semantic? })` → `{ selected, omitted, markdown, tokens }`. `repo` carries its owner teams (`RepoTarget`), `family` is the repository's family id and `files` the repository-relative paths the task touches (a merge request's changed files). Keeps accepted entries whose scope covers the repository, whose `match` holds (`matchHolds`) and whose `appliesTo` holds the task kind or `*`; migrations only when a task package overlaps their ranges; drops entries another match supersedes. Ranks by scope specificity (`scopeSpecificity` of `@holtkeeper/access`: exact repo > folder glob, deeper first (`acme/round/**` over `acme/**`) > team > everything), then an entry narrowed by `match` before an equally specific one that is not, then relevance to the query and task packages, then recency. With `semantic` (entry id → cosine between the entry's vector and the task's query vector, see [Vectors](#vectors)) relevance is the reciprocal rank fusion of the text ranking and the ranking by cosine among the matching entries (`SelectedKnowledge.score` then holds the fused value, Σ 1/(60 + rank), at most 2/61); entries without a vector rank last in the latter, and vectors never make an entry apply. Adds entries while the rendered block stays within the budget (4 characters per token); oversized entries are skipped, not cut. Each entry is headed `### [kb:<id>] Title` so the agent can cite it.
- `selectNeighbourKnowledge({ entries, task, neighbours, budgetTokens, semantic? })` → `{ selected, omitted, markdown, tokens }`: knowledge written for similar repositories (`neighbours`: `KnowledgeNeighbour { repo: RepoTarget, similarity, family? }`, e.g. from `repoNeighbours` of `@holtkeeper/guide`). Keeps accepted, non-migration entries applying to the task kind that no accepted entry supersedes and whose scope covers a neighbour but **not** the task's repository (scope is authority: entries covering the task repository belong to `selectForTask`). Each entry is credited to the most alike neighbour its scope covers whose family and the task's files satisfy its `match`; without one it is left out. Ranks by `weight` = similarity × relevance (relevance as in `selectForTask`: the text score of the query, fused with `semantic` when given; 1 without a query), then similarity, scope specificity, recency and id. Each `SelectedNeighbourKnowledge` names its `neighbour`. The markdown starts with `NEIGHBOUR_KNOWLEDGE_HEADER` (`## Knowledge from similar repositories` and an instruction to apply an entry only when it clearly holds here and cite it as `[kb:<id>]`), and every entry (`### [kb:<id>] Title`) says which repository it was written for and how similar it is (`written for acme/square/web (similarity 0.82) · convention`). Budget as `selectForTask`. Who may read which entries is the caller's decision: pass only entries the task may use.
- `matchHolds(match, { family?, files? })` — applicability of a `match`, deterministic (no similarity): `families` needs the task's family among them (no family: fails); `files` needs one task file to match one glob (`Bun.Glob`, leading `./` ignored), but only when the task says which files it touches — unknown files leave the entry applying. Empty lists narrow nothing. `isNarrowed(entry)` tells whether a match narrows anything; `matchWithin(inner, outer)` whether `inner` applies nowhere `outer` does not (families a subset, file globs within).
- `proposeEntry({ store, input, actor, task, now, autoAccept?, duplicateOverlap?, notDuplicates?, duplicateScope?, similarity? })` — creates a `proposed` agent entry (or `accepted` when its kind is in `autoAccept`), scoped to the task's repository unless the input says otherwise; `input.match` is validated and stored. If the proposal repeats a proposed, accepted or rejected entry — same title or body words, word overlap (Jaccard) ≥ 0.8, or, with `similarity(candidate)` (the cosine between the proposal's vector and the candidate's, `undefined` without one), a cosine ≥ `SEMANTIC_DUPLICATE` (0.9), which catches the same lesson worded differently or in another language — nothing is created: new evidence links are merged into the existing entry and its id comes back as `duplicateOf`. These rules hold against entries whose `match` applies at least wherever the proposal's does (`matchWithin`; an entry without a match qualifies for every proposal). An entry narrowed differently — a family or file entry when the proposal is broader, or narrowed to another family — applies elsewhere, so it counts only when both title and body words are the same: similar wording or meaning there is a generalisation or a sibling, not a repeat. Scopes play no part in the check. Invalid proposals throw `KnowledgeValidationError`. Unless the input sets them, `sharingDefaults` picks subject and visibility. Audits `knowledge.propose`, `knowledge.accept` or `knowledge.evidence` (actor the agent, `via: 'job'`, target the entry and the task's repository) when the store has an audit log.
- `proposeEntry` also takes `input.supersedes`: the id of the narrower entry the proposal replaces (a repository entry a folder-wide one generalises). That entry is left out of the duplicate check, so the generalisation is not swallowed as its duplicate, and the new entry stores it as `supersedes`; every other entry still dedupes. Accepting the new entry archives the superseded one (server). `notDuplicates` leaves more ids out of the check (every narrower entry a promotion generalises), and `duplicateScope(entry)` limits the check to the entries it holds for (starter knowledge: the repository's neighbourhood and the same library subject), so a lesson is not merged into an unrelated team's entry.
- `mergeEvidence({ store, entry, evidence, actor, repo?, now })` → `{ entry, added }` — adds the links whose URL the entry does not have yet, text and status untouched; audited as `knowledge.evidence`. `proposeEntry` uses it for duplicates.
- `placeLessons(input)` — the scope agreement of starter knowledge, see [below](#scope-agreement).
- `bootstrapMarker(repo)` — `knowledge:bootstrap:<forge>:<path>`, the `Store.kv` key that marks a repository whose starter knowledge was built (written by [@holtkeeper/knowledge-bootstrap](../../knowledge-bootstrap/docs/README.md)).
- Scope helpers: `describeScope(scope, match?)` (`team widgets`, `folder work:acme/round/**`, `repos work:acme/*/web`, `repo work:other/kit`, followed by `· family f-web` / `· files src/**` when a match narrows it), `exactRepos`, `scopeNamesRepo(scope, repo)` (the scope names the repository by exact path, `forge:path` or bare), `entryTeams(entry, teamsOf, forge)` (every owner team an entry reaches, through its teams or the repositories it names exactly; globs reach none), `reachesRepoTeams(entry, repo, teamsOf)` ("same team": covers the repository or reaches one of its owner teams), `nearRepo(entry, repo, { teamsOf, familyOf? })` and `entriesNearRepo(entries, repo, { teamsOf, familyOf? })` (the repository's neighbourhood, see below).
- `knowledgeAccess({ store, now, autoAccept?, semantic?, proposalSimilarity? })` — what agent tools call. Repositories are `KnowledgeRepo { forge, path, teams, family? }` (owner teams and family id). `autoAccept` is a list of kinds or a function of the proposing repository returning them (the server resolves the scoped `knowledge.autoAccept` setting this way):
  - `search(query, { repo, taskKind, limit? })` → `{ id, title, kind, body, score }[]`: accepted entries applicable to the repository (scope covers it, `match.families` holds `repo.family`; file matches do not narrow, the files are unknown) and task kind, best match first (blank query: all applicable, most specific first). Migrations are not filtered by package here, since the query decides. With `semantic(query)` (entry id → cosine with the query's vector; `undefined` or a rejection leaves search full text only) a non-blank search also finds entries with a cosine ≥ `SEMANTIC_MATCH` (0.3) that share no word with the query, and orders by the reciprocal rank fusion of the full-text and the vector ranking (`score` is then the fused value).
  - `propose(input, { actor, repo, taskKind, packages? })` → `{ id, status, duplicateOf? }`. `proposalSimilarity(input)` gives the `similarity` function `proposeEntry` dedupes this proposal with (the server embeds the proposal); `undefined` or a rejection dedupes by words only.
- Helpers: `matchesTask`, `renderEntry`, `citation`, `packageOverlaps`, `compatibleRange`, `coerceVersion`, `describePackage`, `relevance`, `textOverlap`, `estimateTokens`.

## Vectors

Vectors rank and dedupe; they never decide where an entry applies. The server embeds `embeddingText(entry)` (title, blank line, body, a `Topics: …` line when there are topics) with an [`Embedder`](../../embed/docs/README.md) and stores the vector in `Store.embeddings` under `embeddingSubject(id)` (`knowledge:<id>`) with the `contentHash` of that text, so an edit re-embeds. It then passes cosines to `selectForTask` (`semantic`), `knowledgeAccess` (`semantic`, `proposalSimilarity`) and `proposeEntry` (`similarity`). `fusedRelevance(items, semantic)` is the fusion they share: items with a lexical score above 0 ranked by it (ties in the order given), items with a cosine ranked by it, then `reciprocalRankFusion`; an item missing from a ranking gets nothing from it. Without vectors everything works on words alone, as before.

## Scope agreement

`placeLessons({ repo, lessons, entries, teamsOf, familyOf?, libraryHome?, promote })` decides, for each lesson an agent learned about one repository, at which level the entry goes (`PlacementLevel`: `repo`, `family`, `shape`, `folder`, `team`, `library`). `repo` is a `RepoTarget` with its owner teams, `teamsOf` gives the owner teams of any other fleet repository and `familyOf` its family id (without it nothing has a family). It is pure and deterministic; the caller writes each decision through `proposeEntry` (`create`) or `mergeEvidence` (`covered`). Lessons (`LessonDraft`) carry `level` (`repo` code, `process` team process, `library` how to use the library in `library`), `repoSpecific`, `related` (ids of existing entries the lesson repeats) and an optional `general` wording true for every repository involved.

1. **Library.** A `library` lesson gets the library as `subject` (`Go:<module>`, `npm:<name>`), visibility `shared` and the package. When `libraryHome(subject)` is another fleet repository, the entry is scoped to that repository (level `library`) and placement stops.
2. **Neighbourhood and matches.** Candidates are proposed and accepted entries near the repository (`entriesNearRepo`), never `all` scopes: entries reaching one of its owner teams (their teams or the owner teams of the repositories they name; "same team" = a shared owner team, consumers never count), entries about its family (`match.families` holds it, or they name repositories of the family), and entries whose path pattern shares a folder at least `FOLDER_DEPTH` (2) deep with it (`acme/round/api` for `acme/round/web`). An entry another candidate `supersedes` is no candidate itself: its text and id count for the entry that replaces it, so later siblings find a pending promotion instead of proposing a second one. A lesson matches an entry it names in `related`, or one whose title overlaps by `TITLE_MATCH` (0.5), or whose title and text overlap by `TEXT_MATCH` (0.35) — Jaccard over significant words, `general` wording counted too. Matches rank linked first, then overlap, then narrower scope, then newest, then id.
3. **Covered.** When any match already applies to the repository (scope covers it and its `match.families`, if any, holds the repository's family; file matches do not count against it) the lesson is `covered`: its evidence goes into the best such entry and nothing new is written. This also holds for `repoSpecific` lessons and with `promote: false`, so a forced rerun does not repeat the repository's own entries.
4. **Repository by default.** Otherwise the scope is the repository (`forge:path`). With `promote: false` or a `repoSpecific` lesson it stays there.
5. **Team process** goes to the owner team the best match reaches, else the repository's first owner team (`team`, `{ teams: [key] }`) — with or without matches, since how a team reviews, merges and releases is the team's either way. A repository without owner teams keeps it.
6. **Other lessons** need matches and take the narrowest description that holds the repository and all of them, in this order:
   1. **family** — the repository has a family and every match is about it (narrowed to that family alone, or naming only its repositories): the entry gets `match: { families: [id] }`. Its scope is the bound and the authority, chosen as the narrowest that holds the repository and every match: their deepest shared folder at least two deep (`work:acme/round/**`), else their shape (`work:acme/*/web`), else the owner teams of the repository and of the matched repositories (`{ teams: ['widgets', 'gizmo'] }`, so each team's maintainers can accept it), else the repositories themselves. The family narrowing is what keeps a shape or team bound from reaching backends.
   2. **shape** — the repository and the repositories the matches name differ in exactly one segment that is not the last (`sharedShape`): `{ repos: ['work:acme/*/web'] }`. Paths that differ only in their last segment are siblings in one folder, left to the next step.
   3. **folder** — the deepest folder of the repository, at least two segments deep, holding every match (`folderPattern`): `{ repos: ['work:acme/round/**'] }`. A shared `acme` alone is too broad.
   4. **team** — the owner team the best-ranked match reaches (ties: more matches, then the repository's team order): `{ teams: ['widgets'] }`. Only the matches reaching that team count from here on.
      Otherwise (say, a repository without owner teams whose matches span folders) it stays at the repository.
7. **Promotion.** A promoted entry uses the lesson's `general` wording when given, carries the lesson's evidence and that of every match narrower than the target (its teams are the target's, its patterns lie within the target's patterns or name repositories of the target's teams, its match within the target's — for a family target, naming only family members also counts; globs never lie within a team), lists those in `generalises` and supersedes the best of them. `why` names the reason and the matches (`a sibling in acme/round has it: matches kb:1a2b3c4d (repo work:acme/round/api, overlap 0.62); supersedes kb:1a2b3c4d`).
8. **Rejected promotions.** `entries` may hold rejected entries: one for the same target (the same family in `match.families`; or, without a family match, naming the same team or pattern) that supersedes a generalised match, or that matches the lesson, means people refused this promotion, and the lesson stays at the repository (`a promotion to folder work:acme/round/** was rejected (kb:…); kept at the repository`).

Promotions are proposals: nothing placed this way should be auto-accepted, and the starter knowledge analyzer passes no `autoAccept`.

Helpers: `entriesNearRepo`, `nearRepo`, `reachesRepoTeams`, `entryTeams`, `exactRepos`, `scopeNamesRepo`, `describeScope`, `bootstrapMarker`, `FOLDER_DEPTH`; `Neighbourhood { teamsOf, familyOf? }` is the fleet view they take.

## Freshness, links and chapters

- **Freshness** (`freshness.ts`). `freshnessSignals({ entry, repoPath, state })` lists deterministic reasons to doubt an entry: an evidence file (links into the repository, `evidencePaths`) is gone (`missing-file`) or changed since the last check (`changed-file`, also for `match.files` globs), a package it is about is no longer a direct dependency (`package-gone`, only `npm` and `Go` and only when that ecosystem was read), or the content was last judged (`judgedAt`, else the entry's update) over `FRESHNESS_MAX_AGE_DAYS` (90) days ago (`aged`). `evidencePaths` and `evidenceCommits` read links whose URL path starts with the repository path (`/acme/web/` is not inside `/x/acme/web/`). The result of a check is a `KnowledgeFreshness` (`fresh`, `suspect`, `stale`; method `signals` or `model`; reason, signals, `proposal` id) kept in `Store.kv` under `freshnessKey(id)` (`readFreshness`, `writeFreshness`). It is written by the `knowledge-verify` analyzer of [@holtkeeper/knowledge-bootstrap](../../knowledge-bootstrap/docs/README.md#keeping-knowledge-current).
- **Links** (`graph.ts`). `knowledgeLinks(entries, vectors?)` derives, never stores, the links between entries: `supersedes`, `cites` (`[kb:<id>]` or `[[<id>]]` in a body, the whole UUID or a unique prefix of at least six characters), `subject`, `topics` (at least two shared) and, with vectors, `similar` (cosine ≥ 0.8, at most three per entry). One link per pair, strongest kind wins; deterministic. `linkIndex` gives id → linked ids.
- **Chapters**. `knowledgeChapters(entries)` groups entries without anyone naming groups: by `subject`, else the most common shared topic, else kind; chapters under two entries fold into their kind's chapter. Stable for the same entries.
- **Related first**. `selectForTask({ related: true })` (the Guide sets it) pulls entries linked to the three best ones forward (`pullRelated`) so related knowledge wins under a tight budget. It only reorders entries that already match; applicability is unchanged.

## Server

`/api/knowledge` routes (in `apps/server`) let people list, search, edit, accept, reject, archive and delete entries with `knowledge:read` / `knowledge:write` checked against each entry's scope. Accepting an entry archives the one it supersedes. Reviews and agents also read knowledge of similar repositories through the Guide's `neighbours` layer; the server limits it to entries the task's teams read anyway or `shared` ones, and `GET /api/knowledge/:id/citations` reports how review comments citing an entry ended. `GET /api/knowledge/handbook` (`?repo=forge:path` or `?team=key`) returns what the caller may read as chapters with links and freshness, for the Handbook tab. The MCP endpoint offers `search_knowledge`, `get_knowledge` and `propose_knowledge` to external agents under the same permissions; their proposals always wait for review.

## Limitations

- Classification is keyword based and English only; people are expected to correct kind and topics when accepting.
- Version ranges are matched with `Bun.semver`; versions are coerced from loose strings (`^18.2` → `18.2.0`), ranges are taken as written.
- Deduplication compares against every non-archived entry in memory, which is fine for knowledge bases of a few thousand entries.
- Placement cannot list the repositories a glob covers, so a glob entry joins the neighbourhood only by covering the repository or sharing a folder at least two deep with it, and is never generalised by a team promotion.
