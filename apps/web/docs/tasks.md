# Tasks

Part of the web app's [Ops](README.md#tasks) docs.

## Tasks

**Tasks** (`/ops/tasks`, `features/tasks/`, `repos:read`) is the Ops tab for agent write tasks: one task group per request, one task per repository, each opening a draft merge request. Everything comes from `GET /api/task-groups` (polled every 5 seconds while a group works), `GET /api/task-groups/:id` for the open group and `GET /api/write-tasks`, already limited by the server to what the viewer may see.

- **Header.** The Ops tabs (the Tasks tab carries a badge, see below), a ghost **Configure** that opens Settings › AI, a ⋯ menu with **Copy link**, and **New task in Chat** as the one primary action. The toolbar holds the scope switch (_My teams_ keeps groups that touch a repository of the viewer's home groups, matched through `GET /api/repos` and `taskGroupTeams`), a text filter (title, repository, `!12` merge request or the id's start; `/` focuses it), the **Open** / **Ended** / **All** view with counts (`taskViewCounts`), and **Kind**, **Source**, **Repository** and **Proposed by** filters whose choices come from the groups in scope (`taskFilterOptions`, `matchesTaskList`).
- **Write control** (`WriteControl`). The `tasks.write` switch **Agents may change code** with an _On_ / _Off_ tag, who changed the global entry last and when, and a link to Settings › Audit log (global `audit:read`). Turning it on opens a confirmation that names the risks (decision 17): repository scripts run on write workers without a sandbox, can read the worker's environment and other checkouts and change the mirror's git config; merge requests go out under the bot with the forge token; a wrong change can reach many repositories at once; tasks spend from the weekly AI budget. Turning it off saves at once and holds queued tasks. The switch writes only `enabled` on the global entry (`writeTasksSwitch`, `writeTasksEntry`) and needs global `settings:write`; the deployed instance keeps it off until checks run in a sidecar. Beside it: the write pool (running tasks, its state from `writePoolState`: _Turned off_, _Idle_, _Working_ or _No write worker_ when a task waited over five minutes with nothing running, the busy workers' ids, _Workers_ as busy against live workers (`writeWorkersText`: `1 / 3` from `pool.busyWorkers` and `pool.totalWorkers`; the total counts workers of every pool, since the registry does not record pools), queued and running counts, the oldest wait and the last start), this week's write spend against the weekly cap with a link to AI spend, and the caps (per repository, per task, repositories per task, weekly) with **Edit caps**, which opens the `tasks.write` entry editor for the global entry.
- **Sections** (`taskSections`, `taskSectionOf`). Groups land in **Needs approval** (a task still proposed; nothing runs until someone approves; its header links _Also in Inbox_ to `/inbox?kind=task`), **Running** (approved, queued or running; the caption counts repositories on workers and queued ones), **Opened MR** (merge requests open and nothing failed; the caption counts drafts), **Failed** (a task failed and none still works, even with other merge requests open) and **Ended** (done or cancelled). The Open view shows the first four and folds Ended into one row, _Ended · 41 done, 6 cancelled_ (`endedSummary`), that expands in place; Ended and All show their sections in the same order.
- **Columns.** Status in words (a group in Failed reads _Failed_), the task with kind, source and proposer (the first error instead for failed groups), the first repository with `+N`, progress as a segment bar per task status with a caption (`taskProgressCaption`: _0 of 5_ before anything starts, _2 of 2_ once every repository has a merge request, else _1 MR · 1 running · 1 queued_), the first two merge requests, the CI column, spend (the spend cap as _≤ $10.00_ while waiting for approval, `groupSpendCap`), the last update and the row's action.
- **CI column** (`groupCiSummary`). The most pressing CI among the group's tasks with a merge request, in the order failed, running, pending, canceled, passed, no pipeline, read from each task's `ci`; when the merge requests differ it adds how many share it, e.g. _Failed · 1 of 3_. A dash while no task has a merge request.
- **Actions.** Needs approval: **Approve** (asks first, names the cap, and cannot confirm while `tasks.write` is off) and **Reject** (asks first; `POST /api/task-groups/:id/reject` cancels the proposal and audits it as `task.reject`), each shown only when the group's `can` allows it. Running: **Cancel** (asks first). Opened MR: opens the first merge request on the forge. Failed: **Retry** (`POST /api/task-groups/:id/retry` queues every failed or cancelled task again, no confirmation since the group was approved before). The shared dialogs live in `useGroupDecisions` (`decisions.tsx`).

### Badge

The Tasks tab shows how many task groups the viewer sees that wait for approval, from `GET /api/task-groups/needs-approval` (`useTaskApprovalCount`, every 30 seconds, only while the Tasks tab is visible). `NavItem.badge` in `features/shell/nav.ts` marks which tabs carry a count (`inbox`, `tasks`); `AppShell` renders it with `taskApprovalBadge` (empty for none, `99+` past 99) and reads it out as _N need approval_.

### Sheet

A row opens the group in the `SideSheet` (`?group=`, J/K step through the rows in the order shown; with no sheet open J opens the first row and K the last). The header shows `task <short id>` (copies the full id), the position, a segment bar with _2 of 5 repositories finished · $1.20 of $10.00_ (`taskGroupProgressLabel`), at most two quiet actions in the order Approve and run, Reject, Retry failed, Cancel task, and the rest in the ⋯ menu with **Open the chat thread** for chat requests and **Copy link**. Tabs (`?tab=`, `parseTaskSheetTab`):

1. **Plan**: kind, source and a _patch first_ tag; the plan (or the request when there is no plan); the expected diff from the group's patch per file (`patchFiles`, the first six) or the merge requests' diffstat; repositories that asked to join with **Add** and **Reject**; the repositories with status and spend cap; then who proposed it, who approved it or who may (_anyone with `tasks:run` on every repository_), who stopped it, the budget class, the branch and the write switch.
2. **Repositories**: every repository's task; one opens (`?task=`) with its branch, job, spend, CI, error, its own patch, **Retry this repository** and **Cancel this repository**, and its agent runs.
3. **Diff**: each task's diffstat (`AgentTaskView.diffstat`, from the merge request or the patch) with a bar scaled to the largest row (`diffstatShares`) and the total (`groupDiffstat`, `formatDiffstat`), then the group's patch per file and in full.
4. **Agent runs**: each started repository's write job with its agent runs and transcripts.
5. **Request**: where the request came from (a link to the chat thread for chat requests), who asked and when, and the prompt.
6. **Flow**: the group as a read-only React Flow diagram (`FlowCanvas`, `taskGroupFlow`): the source, one node per repository colored by status, its merge request and CI; repositories a task asked for hang off it, dashed.

Search parameters are parsed by `parseTasksSearch` in `lib/tasks.ts`: `group`, `task` and `tab` (only with a group) and `view` (`ended` or `all`). Filters and the scope live in the page and the scope switch's own storage.
