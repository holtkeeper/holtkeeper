# Reviews

Part of the web app's [Quality](README.md#quality) docs.

**Reviews** (`/quality/reviews`, `features/reviews/`, `analyses:read`) lists Holtkeeper's merge request reviews of every readable repository from `GET /api/reviews`, newest first, a page at a time (**Show older reviews** continues from `nextBefore`). It is a `FleetTable`: the scope switch (_My teams_ folds other teams' rows into one row, groups come from `GET /api/repos`), a `Strip` (reviews, one figure per verdict, posted findings with their severities, resolved threads and the AI cost) from the server's window totals (`ReviewList.window` of the first page, _at least_ when the scan was capped) while only server filters apply, otherwise from the shown rows (`reviewTotals`, captioned _of the loaded ones_ while older pages remain), then one row per run: `!iid` and title with the author and, when not a full review, the mode; the repository (links to the hub's Quality › Reviews); the verdict in words with a dot; findings with a severity `SegmentBar` (critical, major, minor, info); resolved threads; cost; age; and a link to the merge request on the forge. Findings, Cost and When sort (`sortReviews`).

Filters live in the URL (`parseReviewsSearch`, `lib/reviews.ts`): `repo` narrows to one repository (a removable chip), `q` matches the merge request number, title, author and repository path, `verdict` goes to the server, `mode` and `author` (choices from the loaded rows) filter the loaded rows (`filterReviews`), and `days` (7, 30 or 90; 30 is the server default) sets `since` (`reviewSince`).

A row opens `ReviewSheet` (`?review=<analysisId>`, `?tab=summary|learnings`; J/K step through the rows in table order, folded other teams' rows last), which reads `GET /api/reviews/:id`: `!iid` with a copy button for the merge request link, the title, the severity bar as progress with the finding count, **Open merge request** (only for an http(s) link) and **Review again**, the verdict, repository, source → target branch and author, then the **Findings** tab (one card per finding: `path:line` linking to the comment, category, severity in words, title, body, the suggested replacement as a diff, whether the forge accepted it and why not, its source) or the **Summary** tab, and under both the run's facts: mode, reviewed commit, model, tokens (`tokenText`), cost and duration, the Guide scopes it read, and the analysis record. The **Learnings** tab (badge: how many) lists the learning candidates whose sources are replies on this merge request (`GET /api/learnings?repo=`, matched by `sources[].mergeRequest`) with their status, and links to Knowledge › Learnings of the repository to decide them. **Open as page** opens the record (`/analyses/$id`).

Under the table, **Reactions by finding category** (`ReviewReactions`) reads `GET /api/learnings/reactions` (with `?repo=` when the page is narrowed or in the hub; without it only for a global `knowledge:read` grant, otherwise the block is left out): the share of 👍 among all reactions as a tag, then per finding category a two-part bar (helpful in info, not helpful in warning, with a legend), the helpful share and the counts of 👍, 👎 and commented findings (`helpfulShare`, `reactionSum` in `lib/learnings.ts`). A link leads to Knowledge › Learnings, where replies to review comments become rule candidates. The block renders nothing while there are no reactions.

**Review a merge request** (the page's primary action) and **Review again** (in the sheet and on a review's record page) queue the `review` analyzer through `POST /api/jobs` (`reviewJobInput`): the first takes a repository (fixed when the page is narrowed) and a merge request number, `!N` or a merge request or pull request URL (`mergeRequestNumber`) and sends `{ mergeRequest }`; the second sends `{ mergeRequest, force: true }` so a head that was reviewed already is reviewed again. Both need `analyses:run` and a `review` analyzer in `GET /api/jobs/analyzers` (`useCanReview`); a toast links to the queued job. **Configure** opens the `analyzers.review` setting in the settings sheet (`pageSettingKeys.reviews`; settings search names Quality › Reviews as its home, and Settings › Analyzers shows it too).

The hub's Quality › Reviews area (`ReviewsRepoSection`) is the same table, sheet and reactions block narrowed to the repository, without the repository column and scope switch, its filters kept in component state, with **Review a merge request** for that repository.
