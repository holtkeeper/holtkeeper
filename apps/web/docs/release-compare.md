# Release compare

Part of the web app's [Releases](README.md#releases) docs.

`/releases/compare?repo=&from=&to=` (`ComparePage` in `features/releases/ComparePage.tsx`, the **Compare** tab of the Releases workspace, `releases:read`) compares two ends of one repository: two version tags, or a version and the target branch (what waits for the next version). It reads `GET /api/releases/refs` (`useReleaseRefs`) for the choices and `GET /api/releases/compare` (`useReleaseCompare`, kept 5 minutes) for the result. The breaking-change check, the public API section and the dependency details live in `features/releases/CompareImpact.tsx`. Pure helpers live in `features/releases/compare-range.ts` (range and dependency table) and `features/releases/compare-impact.ts` (API, package and check).

## Header and range

The title row holds the repository switch (`ReleaseRepoSwitch`, the repositories on the overview); picking another repository drops `from` and `to`. Without `?repo=` the page opens the first repository of the overview, action first, as the timeline does.

Under it, **From (older)** lists every version tag newest first (prereleases marked) and **To (newer)** lists the target branch, captioned _target branch — unreleased_, then the same tags. A ref named in the URL that is in neither list is added as its own option. The swap button exchanges the ends. Picking **To** derives **From** again from the new end; picking **From** keeps **To**. Every change replaces `?from=&to=` in the URL, and the defaults are written into it as soon as the refs load, so a copied link keeps naming the same range after new tags.

Without ends in the URL the page compares the latest stable version with the stable version before it (prereleases stay selectable but count only when there is no stable one); with only `to`, `from` is the stable version before it, or the latest stable version when `to` is a branch; the oldest version compares the whole history (`defaultRange`). There is no explicit "first commit" start: the server, like the page, starts at the version before `to`. A backwards range (`from` newer than `to`, `from` on the target branch, or both ends the same) shows a warning (`rangeProblem`); the server still answers it. If the refs cannot be read, a warning says so, the server's default range is shown and the pickers offer only the ends already in the URL.

## Sections

- **Summary line**: the resolved ends, _Unreleased_ when `to` is the target branch, the bump, the commit count (`300+` when capped), the task count, the dependency change count (`dependencyChangeCount`) and **Compare on the forge** when the forge gives a compare URL.
- **What changed**, only when the answer says `summaryAvailable` (the viewer has `releases:run` and the repository has an AI agent): **Describe changes** posts `POST /api/releases/compare/summary` (`useReleaseCompareSummary`) and renders the Markdown it answers. **Include code changes** adds the code diff to the input (a heavier, costlier call); when the forge cannot compare commits or no code survives filtering, the server describes the commits only. The caption says what the description was written from and whether the server kept it from an earlier request. Changing the range or repository clears it.
- **Breaking-change check** (`BreakingCheckCard`): the AI check of the range from `GET /api/releases/compare/check` (`useReleaseCompareCheck`, polled every 3 seconds while `queued` or `running`). **Check what could break** posts `POST /api/releases/compare/check` (`useStartReleaseCompareCheck`); the caption says it runs several AI agents and spends budget. The button shows only when the answer says `summaryAvailable` (the viewer has `releases:run` and the repository has an AI agent); without it the card shows only when a check exists. While the check is queued or running the card says so, with a link to the job in Ops › Runs. Once done it shows the verdict tag (`verdictTags`: _Safe to upgrade_, _Review before upgrading_, _Breaks_), both ends, a link to the stored analysis, the summary Markdown, findings grouped by severity (`findingGroups`, `severityTags`: breaking, risky, worth knowing) with category, detail, what they affect, files (`fileLocation`) and _How to check_, the areas the agents read in a disclosure, and the changed files no agent read (`skippedLines`) or a size-limit note. A failed run shows its error above the earlier result when one exists. After a result the button turns into **Run again**, which posts `force: true` (`checkAction`); a failure without an earlier result offers **Check what could break** again, without `force`. The check is kept per pair of commits, so a moved target branch is a new range. The card is reset when the range or repository changes.
- **Public API** (`PublicApiSection`): `GET /api/releases/compare/api` (`useReleaseCompareApi`) lists the repository's own packages whose exports differ between the ends, in the server's order (breaking ones first). Each package is a disclosure whose header shows the versions (_new_ or _removed_ when one end has none), a _breaking_ tag when the changes call for a major bump (`apiBreaks`, the server's `breaksCallers` rule), _needs_ the bump the changes call for, _bumped_ what the version numbers did (red when lower, `underBumped`), the counts (`apiCounts`) and, when at least one repository is affected, how many repositories, breaking uses and uses to check the change touches. Open, it shows a semver warning, the API diff Markdown and the affected uses. _No public API changed._ shows only when both ends had a snapshot. Packages without a snapshot at one end are named in a note (`missingText`), as _Cannot compare: no snapshot for …_ when no package could be listed; without any snapshot a muted line says so. When the answer's `backfill.allowed` is true both carry **Snapshot &lt;tags&gt;**, which queues `api-surface` at each of `backfill.refs` through `POST /api/jobs` (`useJobMutations`), or **Analyze past releases** (the `api-surface` backfill dialog) when there are no refs (a target branch end). A caller without catalog reach to the repository gets 403, shown as an error.
- **Tasks**: the tracker keys of the commits with tracker title and status (`TaskList`).
- **Changelog**: the grouped changelog Markdown of the range.
- **Dependencies**: one block per lockfile root or Go module (`rootLabel`, `.` for the repository root, with ecosystem, manager and lockfile from `rootFacts`). Read errors of a root show as warnings above it. A table lists direct changes: package, workspace (only when it says something, `hasWorkspaces`), field (`prod`, `dev`, `optional`, `peer`, `require`, `indirect`), the version from → to (the resolved version, else the declared range; a range that differs from the version is in the tooltip and after the new version, `sideText` and `sideRange`) and the change tag (`changeTones`). Each updated or added row has a **What changed** toggle that opens a row below it and loads `GET /api/releases/compare/package` (`useReleaseComparePackage`, only once opened, kept 30 minutes) for that package with the resolved versions at each end and `npm` or `Go` (`packageQuery`; declared ranges are not sent): the API diff, the changelog and migration notes of third-party packages and the uses in this repository the upgrade affects. When the package is not indexed the server's note shows as a muted line. Removed rows have no toggle. Transitive changes fold into a disclosure with their counts (`transitiveCounts`) and every version at each side, noting when the server cut the list. A note says when the forge listed only part of the changed files (`partial`) or roots past the cap were skipped. When the server could not read dependencies (`dependencies: null`), a muted line gives `dependenciesUnavailable`.

## Entry points

The **Compare** tab and the command palette (both from `nav.ts`), **Compare versions** on the [timeline](release-timeline.md) (`?repo=` only) and **Compare versions** in the version sheet (`from` the previous version, `to` that version).
