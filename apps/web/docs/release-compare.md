# Release compare

Part of the web app's [Releases](README.md#releases) docs.

`/releases/compare?repo=&from=&to=` (`ComparePage` in `features/releases/ComparePage.tsx`, the **Compare** tab of the Releases workspace, `releases:read`) compares two ends of one repository: two version tags, or a version and the target branch (what waits for the next version). It reads `GET /api/releases/refs` (`useReleaseRefs`) for the choices and `GET /api/releases/compare` (`useReleaseCompare`, kept 5 minutes) for the result. The breaking-change check, the public API section and the dependency details live in `features/releases/CompareImpact.tsx`. Pure helpers live in `features/releases/compare-range.ts` (range and dependency table) and `features/releases/compare-impact.ts` (API, package and check).

## Header and range

The title row holds the repository switch (`ReleaseRepoSwitch`, the repositories on the overview); picking another repository drops `from` and `to`. Without `?repo=` the page opens the first repository of the overview, action first, as the timeline does.

Under it, **From (older)** lists every version tag newest first (prereleases marked, and each tagged with the deploy environments that run it, `versionText` naming them in the option's text) and **To (newer)** lists the target branch, captioned _target branch — unreleased_, then the same tags. A ref named in the URL that is in neither list is added as its own option. The swap button exchanges the ends. Picking **To** derives **From** again from the new end; picking **From** keeps **To**. Every change replaces `?from=&to=` in the URL, and the defaults are written into it as soon as the refs load, so a copied link keeps naming the same range after new tags.

Without ends in the URL the page compares the latest stable version with the stable version before it (prereleases stay selectable but count only when there is no stable one); with only `to`, `from` is the stable version before it, or the latest stable version when `to` is a branch; the oldest version compares the whole history (`defaultRange`). There is no explicit "first commit" start: the server, like the page, starts at the version before `to`. A backwards range (`from` newer than `to`, `from` on the target branch, or both ends the same) shows a warning (`rangeProblem`); the server still answers it. If the refs cannot be read, a warning says so, the server's default range is shown and the pickers offer only the ends already in the URL.

## Sections

- **Summary line**: the resolved ends, _Unreleased_ when `to` is the target branch, the bump, the commit count (`300+` when capped), the task count, the dependency change count (`dependencyChangeCount`) and **Compare on the forge** when the forge gives a compare URL.
- **What changed** (`SummaryCard`): `GET /api/releases/compare/summary` (`useReleaseCompareSummary`, polled every 3 seconds while `running`) loads on page open, so a description started before a reload shows as running (_Describing…_, the button disabled) or finished. The card shows for viewers only when a description is running or done, and a running state wins over a failed poll (the placeholder stays instead of an error); the controls need `summaryAvailable` (the viewer has `releases:run` and the repository has an AI agent). **Describe changes** posts `POST /api/releases/compare/summary` (`useStartReleaseCompareSummary`), which starts the description in the background or joins the one already running, so a second click never starts a second paid call; its answer seeds the query of the selected flag, so the card does not flash a placeholder; the button is hidden once a description of the selected flag exists and reads **Try again** after a failure, whose error shows in the card. **Include code changes** adds the code diff to the input (a heavier, costlier call); when the forge cannot compare commits or no code survives filtering, the server describes the commits only. Until the checkbox is touched the page asks without a flag and the server answers the running description, else the one with code, else the one without; the checkbox then follows the answer's `code`. The caption (`summaryNote`) says what the description was written from and whether the server kept it from an earlier request. Changing the range or repository loads that range's state.
- **Breaking-change check** (`BreakingCheckCard`): the AI check of the range from `GET /api/releases/compare/check` (`useReleaseCompareCheck`, polled every 3 seconds while `queued` or `running`). **Check what could break** posts `POST /api/releases/compare/check` (`useStartReleaseCompareCheck`); the caption says it runs several AI agents and spends budget. The button shows only when the answer says `summaryAvailable` (the viewer has `releases:run` and the repository has an AI agent); without it the card shows only when a check exists. While the check is queued or running the card says so, with a link to the job in Ops › Runs. Once done it shows the verdict tag (`verdictTags`: _Safe to upgrade_, _Review before upgrading_, _Breaks_), both ends, a link to the stored analysis, the summary Markdown, findings grouped by severity (`findingGroups`, `severityTags`: breaking, risky, worth knowing) with category, detail, what they affect, files (`fileLocation`) and _How to check_, the areas the agents read in a disclosure, and the changed files no agent read (`skippedLines`) or a size-limit note. A failed run shows its error above the earlier result when one exists. After a result the button turns into **Run again**, which posts `force: true` (`checkAction`); a failure without an earlier result offers **Check what could break** again, without `force`. The check is kept per pair of commits and AI language, so a moved target branch or a changed review language is a new range. The card is reset when the range or repository changes.
- **Public API** (`PublicApiSection`): `GET /api/releases/compare/api` (`useReleaseCompareApi`) lists the repository's own packages whose exports differ between the ends, in the server's order (breaking ones first). Each package is a disclosure whose header shows the versions (_new_ or _removed_ when one end has none), a _breaking_ tag when the changes call for a major bump (`apiBreaks`, the server's `breaksCallers` rule), _needs_ the bump the changes call for, _bumped_ what the version numbers did (red when lower, `underBumped`), the counts (`apiCounts`) and, when at least one repository is affected, how many repositories, breaking uses and uses to check the change touches. Open, it shows a semver warning, the API diff Markdown and the affected uses. _No public API changed._ shows only when both ends had a snapshot. Packages without a snapshot at one end are named in a note (`missingText`), as _Cannot compare: no snapshot for …_ when no package could be listed; without any snapshot a muted line says so. When the answer's `backfill.allowed` is true both carry **Snapshot &lt;tags&gt;**, which queues `api-surface` at each of `backfill.refs` that has no queued or running job (`refsToSnapshot`) through `POST /api/jobs` (`useSnapshotCompareRefs`, which refetches the section), or **Analyze past releases** (the `api-surface` backfill dialog, with `onQueued` so it stays on the page instead of opening Ops › Runs) when there are no refs (a target branch end). The answer's `snapshots` show one line per ref (`snapshotLine`: _Waiting to snapshot v1.2.0…_, _Snapshotting v1.2.0…_, or the failure with its error) with a link to the run, also for a target branch end's default-branch job and, when nothing is recorded, for the jobs a backfill queued; the server lists them only to callers with `analyses:read`. While any is queued or running the section polls every 5 seconds (`snapshotsActive`), so the diff appears once they finish without a reload; after a backfill it also polls for a minute (`pollUntil` of `useReleaseCompareApi`), since the server queues those jobs in the background after answering. The button queues only the refs without a queued or running job, so a failed one can be retried while another still runs; it reads **Retry snapshot** then. A ref whose newest job succeeded but is still missing gets no line. A caller without catalog reach to the repository gets 403, shown as an error.
- **Tasks**: the tracker keys of the commits with tracker title and status (`TaskList`).
- **Changelog**: the grouped changelog Markdown of the range.
- **Dependencies**: one block per lockfile root or Go module (`rootLabel`, `.` for the repository root, with ecosystem, manager and lockfile from `rootFacts`). Read errors of a root show as warnings above it. A table lists direct changes: package, workspace (only when it says something, `hasWorkspaces`), field (`prod`, `dev`, `optional`, `peer`, `require`, `indirect`), the version from → to (the resolved version, else the declared range; a range that differs from the version is in the tooltip and after the new version, `sideText` and `sideRange`) and the change tag (`changeTones`). Each updated or added row has a **What changed** toggle that opens a row below it and loads `GET /api/releases/compare/package` (`useReleaseComparePackage`, only once opened, kept 30 minutes) for that package with the resolved versions at each end and `npm` or `Go` (`packageQuery`; declared ranges are not sent): the API diff, the changelog and migration notes of third-party packages and the uses in this repository the upgrade affects. When the package is not indexed the server's note shows as a muted line. Removed rows have no toggle. Transitive changes fold into a disclosure with their counts (`transitiveCounts`) and every version at each side, noting when the server cut the list. A note says when the forge listed only part of the changed files (`partial`) or roots past the cap were skipped. When the server could not read dependencies (`dependencies: null`), a muted line gives `dependenciesUnavailable`.

## Entry points

The **Compare** tab and the command palette (both from `nav.ts`), **Compare versions** on the [timeline](release-timeline.md) (`?repo=` only) and **Compare versions** in the version sheet (`from` the previous version, `to` that version).
