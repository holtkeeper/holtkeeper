# @holtkeeper/web

The Holtkeeper admin panel: Home (what needs you, what changed, AI spend, your team's repositories), audit reports, background jobs, automation (a canvas of events, rules and actions per team, freshness and the AI forecast), credentials, settings, AI usage, storage, database, caches, users, your own account (passkeys and linked external accounts, at `/account`) and History, the one log of who did what. A single-page React app that talks only to the server's JSON API (`/api/*`) and auth endpoints (`/auth/*`). The server serves the built files from `apps/web/dist`.

Stack: React 19, HeroUI 3 (React Aria + Tailwind CSS 4), TanStack Router (code-based routes), TanStack Query, TanStack Table, Motion, Recharts, React Flow (`@xyflow/react`) with dagre layouts, lucide icons, `@simplewebauthn/browser` for passkeys.

## Running

```sh
# API server on :7420 (see apps/server/docs), then in another terminal:
cd apps/web
bun run dev          # Vite dev server, proxies /api and /auth to http://localhost:7420
bun run build        # writes apps/web/dist, which the server picks up
```

Set `HOLTKEEPER_SERVER=http://host:port` to proxy to another server. Session cookies work through the proxy because requests stay same-origin.

Checks: `tsc -p apps/web` (part of `bun run typecheck`), `bun test apps/web`, `bun run lint`.

## API client

Pages never call `fetch`. `api/endpoints.ts` maps every endpoint to a typed function using the shared types from `@holtkeeper/api` (types and browser-safe helpers only; no runtime code from other packages). `api/queries.ts` wraps them in hooks; mutations invalidate the affected query keys. Errors arrive as `ApiError` with the HTTP status; a 401 anywhere refetches `/api/me`, which shows the sign-in page.

## Access in the UI

Scope editors (grants, settings, knowledge) and the schedule and trigger dialogs take group intersections as `frontend + storefront`: one tag that means both groups at once (`formatGroupMatch` / `parseGroupMatch` in `lib/scope.ts`).

`lib/access.ts` `can(principal, action)` only asks whether any grant names the action (or `*`). It decides which navigation entries and buttons to show; the server still checks the exact scope on every request, and pages show "No access" on a 403. `canGlobal(principal, action)` needs the action on a grant over everything (`scope.all`), as the server does for global objects: the Automation entry and the Settings → System tab (`global: true` in `nav.ts`), the forges, Slack, storage, database and caches sections of Settings, **Show on Automation** on a job and the schedule and trigger links on a repository's config use it, so a group-scoped `settings:read` holder sees no link the server would refuse. `useSession()` offers both bound to the signed-in principal.

## UI wrappers

Everything from `@heroui/react` is imported in `src/ui/` only. Pages use `Button`, `Panel`, `Dialog` (`size="xl"` for wide editors), `Markdown`, `TextField`, `Select`, `Switch`, `Checkbox`, `Segmented`, `MultiToggle`, `Tabs`, `Tooltip`, `SearchInput`, `notify` and friends from `ui/index.ts`, so replacing the component kit means rewriting `src/ui/` and nothing else. Wrappers expose small, explicit props rather than passing HeroUI props through. Tables (`Table`, report tables, heatmaps, diffs) cap their height with `tableScrollClass` and scroll inside under a sticky header; paged lists end in `LoadMore`, a show-more button that also presses itself when scrolled into view, placed inside the table's scroll area when there is one.

## Proxy secrets

A forge's dialog has **Packages for jobs** (on by default) and **Cache packages** (off by default, needs the first): with it the egress proxy keeps the package files jobs download from the forge, and the forge card shows a "packages cached" chip.

With global `settings:read`, each credential of kind `github` under Settings → Integrations gets a usage section in its card (`GitHubCredentialUsage` in `features/credentials/GitHubUsage.tsx`, `GET /api/system/library-index/github?days=`, 30 days, refreshed every minute, hidden on 403/404): the GitHub account, requests with the share answered `304` from the cache and rate-limited answers, the live `core` limit as a bar with what is left and when it resets, a warning when it is a duplicate of another token's account or GitHub rejected it, and **Usage details** with the other limits (`search`, `graphql`) and the counts per resource; a credential the `libraries.github` setting leaves out says so. The pool-wide **GitHub API usage** lives in Settings → System (see **Library index**).

AI provider credentials (kind `ai-sdk`, `AiProviderFields.tsx`) pick a catalog provider or one of your own, its package, base URL and advanced options as JSON (headers, settings, `modelMap`, `pricing`, limits). There is no model field: agents run on fixed tiers resolved to the newest Haiku, Sonnet and Opus the provider lists; **Models** (`ModelsDialog.tsx`) shows that listing with prices. Opening an old credential drops its `model` and `models` options on save. Which credential agents use is the global `llm.provider` setting.

The credential dialog offers **Rotation** only for kinds the server can rotate (`canRotate` in `features/credentials/form.ts`: the stored credential's `rotatable`, else `gitlab`); GitHub has no API to issue a personal token, so `github` credentials are renewed by hand and saved with rotation off.

Credentials of kind `egress-secret` ("Proxy secret") hold a secret the egress proxy puts into job requests in place of a placeholder (`EgressSecretFields.tsx`): a generated UUID with copy and regenerate buttons, more hosts, paths, methods and where to replace (headers, URL, body). The URL is where the secret goes, e.g. a Turborepo remote cache. The form keeps them as `options`, see the server docs on egress rules.

## Forges

Settings → Integrations also lists forges (global `settings:read`, `ForgesSection`). With global `settings:write` you add a GitLab forge (id, URL, a GitLab token credential and the optional bot username Holtkeeper posts as, `PUT /api/config/forges/:id`), edit or delete forges, and issue, rotate or remove a forge's SSH key (`POST`/`DELETE /api/forges/:id/ssh-key`): what it is used for (clone and push, signing, or both), its lifetime and an optional commit identity. `forge-form.ts` holds the form's validation.

Below the forges, **Slack** (`SlackTokensSection.tsx`, global `settings:read`) shows whether a Slack app's bot token and signing secret are stored (`GET /api/slack`) and, with global `settings:write`, saves or replaces them (`PUT /api/slack/connection`) or forgets them. Nothing uses them until a Slack integration comes back.

## Repositories and groups

`/repos` shows headline cards (repositories, audited this week, with critical or high findings, active findings) and a table: the path with its namespace dimmed, forge and groups; active findings with a severity bar and fixed/allowlisted counts; the last audit with a freshness dot (week, month, older, never; `auditFreshness` in `lib/repo.ts`); and, with `analyses:read`, one icon per analysis kind linking to its newest record (dimmed when there is none, metrics in the tooltip). A strip of groups sits above it. **Add repository** (global `settings:write`) adds an exact path to an existing group of the chosen forge or to a new group through `PUT /api/config/groups/:id` (`withRepo` in `lib/repo.ts`). The path is typed or picked from `RepoExplorer`: the projects the forge's token is a member of (`GET /api/forges/:id/repositories`), searched by the path text; ones Holtkeeper already knows are marked added. Before **Add** is enabled the path is checked against the forge (`GET /api/forges/:id/repositories/access`, 400 ms after typing stops): `repoAccessAdvice` in `lib/repo.ts` turns the answer into a notice, naming the token's account to invite when the forge answers 404, pointing at Credentials for a rejected token, and blocking archived repositories; a check the forge could not answer does not block. `/repos/view?repo=forge:path` shows one repository: its groups, a tag saying how it gets updates (webhook, polling or none; `settings:read`) and **Run job** in the header, and `SegmentedTabs` kept in `?tab=` (`repoTabs`, `visibleTabs` and `pickTab` in `lib/repo-page.ts`; a tab the viewer may not see falls back to the first). **Overview** (`analyses:read`, `RepoOverview`) reads `GET /api/repos/overview` and shows analysis cards instead of link buttons: `RepoCoverageCard`, an assets summary that opens the Assets tab, dependencies (direct count, the newest audit's vulnerabilities as a severity bar, links to Dependencies and the audit), the stack (tools with their support, convention drifts, `stackHealth`; linking to the group's Stack tab), **Releases** linking to `/releases/<forge:path>` (`releases:read`), and an **Analyses** list: the newest record of every kind with two metrics, its short sha and age and a freshness tag (`recordFreshness`: over a month or a week old, else behind HEAD when it ran on another sha than the default-branch head freshness last saw, else current), most worrying first (`freshnessRows`). **Guide** (`knowledge:read`, `ScopeGuide`) shows the resolved guide a task gets on the repository (`EffectivePrompt` from the Knowledge page's preview, with a task switch) and then the repository's own Guide sections to edit (`GuideTab`); notes and learnings stay on Knowledge. **Assets** is described below. **Reviews** (`analyses:read`, `RepoReviews`) reads `GET /api/repos/reviews`: Holtkeeper's last 20 reviews with merge request, verdict, posted and resolved comments, 👍/👎 on its comments and cost, and their sums with the 👍 share (`approvalShare`). **Settings** (`settings:read`, `ScopedSettings`) lists only overrides: settings with entries naming the repository, each with the value it replaces and where that comes from (`inheritedEntry`/`inheritedFrom`: the most specific entry for one of its groups or everything that does not name it; repository globs are not matched), and **Add an override** picks any other setting; new entries start scoped to it. The updates tag opens `RepoUpdates` in a side sheet: polling cadence, last and next poll, a warning when the token's budget slows it down, **Poll now** and the recent polls with their result; the repository's webhook URL with copy, **Regenerate**, **Turn off**, **Register on GitLab**, the last delivery and setup steps for adding it by hand. `/repos/groups/:id` shows a group with tabs (`groupTabs`): **Repositories** (its include and exclude patterns, **Listing on the forge** (`GroupListing`: what the patterns resolve to, **List now** and the recent listings with their errors) and known repositories), **Guide** (the group's Guide sections), **Stack** (`analyses:read`: the Stack page's `StackView` limited to the group, its view in `?view=`) and **Settings** (the group's overrides). Nothing on these pages calls an LLM. `lib/scope.ts` `namesFocus` decides which entries belong to the page: the exact group, or the exact repository path with or without its forge.

## Scope switch

List pages that show repositories share one three-position `ScopeSwitch` (`ui/ScopeSwitch.tsx`): **My team** (the viewer's home groups), **All I can see** and **Other teams** (counts only). `useScope()` (`features/shell/scope.ts`) holds the position, remembered per browser under `holtkeeper.scope` and defaulting to _My team_ when the viewer has home groups, otherwise _All I can see_; its `scope(items)` calls `scopeList` (`lib/home-scope.ts`), which splits items with `groups` by the home groups (a `frontend + storefront` entry needs both groups) into what to list and the counts, plus the folded "N repositories of M other teams" line. Home groups come from `GET /api/me/preferences` (the groups in the viewer's grants until changed) and are edited in the **Home groups** panel of the account page. They are a UI default, not a permission: the lists already hold only what the viewer may see. `/repos` uses it; other list pages adopt it as they are rebuilt. Under _My team_, pages whose data reaches other teams through the cross-team catalog (Dependencies, Public API **Used by**, Stack, Knowledge notes, a library's team decisions) show them in a collapsed **Other teams (N)** section (`OtherTeams` in `ui/OtherTeams.tsx`, with the team names) split off by `foldOtherTeams` (`lib/home-scope.ts`: items in a home group or owned by nobody stay, the rest fold; nothing folds without home groups).

## Home

`/` (`features/home/HomePage.tsx`) reads `GET /api/home` once (refetched every minute) and is open to every role; each part shows only what the server let through. The `ScopeSwitch` narrows it on the client (`scopeHome` in `lib/home.ts`): rows about no repository stay in every position, a row about several repositories stays where any of them belongs. **Needs attention** lists the server's items with a severity `Tag`, a sentence, the repositories and the age; a row opens its link. **AI spend this week** (with `ai:read`) is a `SegmentBar` of the top three features plus the rest against the weekly limit, with a marker where the reserve starts and the projection as a `Tag`. **What changed** lists the summed History rows of the last 7 days with the actors' avatars. **Repositories** is a grid of tiles, worst first, each with a `TickStrip` of jobs, vulnerabilities, release and analyses that opens the repository page; it and its **All repositories** link show only with `repos:read`.

## Jobs

`/jobs` (Ops workspace, `analyses:read`) lists background analyzer runs as dense rows: a status tag, the analyzer, the repository or group in mono, the trigger or schedule with the requester's avatar, duration, attempts and the start time, newest first with **Load older** (paged by `before`), refreshing every few seconds while some are queued or running. Jobs an AI budget refused or stopped show as **Blocked by budget** (a warning, not a failure) with the budget's reason under the analyzer. The filters bar picks a status, analyzer, repository and trigger; `?schedule=` and `?signature=` show as removable tags (all filters live in the URL, `parseJobsSearch` in `lib/jobs.ts`). The `ScopeSwitch` narrows the list to the repositories of the viewer's home groups or the rest, from `GET /api/jobs/targets` (`jobScopeRepos`); a picked repository wins. The **Failures** tab groups jobs that failed for good in the last 24 hours, 7 or 30 days by analyzer and normalized failure (`GET /api/jobs/failures`): count, repositories, last seen (first seen on hover); a row lists those jobs, **latest** opens the newest one. A row opens the job in the `SideSheet` (J/K step through the loaded rows, with **Run again**, **Cancel**, **Result** and a link to the full page); `/jobs/$jobId` shows the same `JobDetail`: status, target and ref, trigger or schedule, requester, worker, attempts and timings; **Why** (`GET /api/jobs/:id/why`): what queued it and, while queued, what holds it back (an exclusive job, results it waits for, a retry time) and the due jobs ahead; the error, or the budget's reason for blocked jobs, with a link to jobs with the same failure; the picked attempt (a switcher once it ran more than once) with its status, worker, duration and failed step and a steps timeline built from the log's step marks (`stepBars`); the log (`JobLogView`): step marks (start, end with duration, failure) with the step's lines indented, error lines highlighted, the last 1000 lines polled every 2 seconds while the attempt runs and until the worker closed the log and **Show earlier** for older pages (`GET /api/jobs/:id/log`); **Agent runs** (`JobAgentRuns`, `GET /api/jobs/:id/runs`) with their summed cost, each run's model, tokens, turns and cost opening its transcript (prompt, model text, tool calls and results, outcome); and the options. `RunJobDialog` (`analyses:run`, only when the config has `jobs`) queues an analyzer: the target is fixed by the page (repository, group) or picked, the options form comes from the analyzer's JSON Schema (`GET /api/jobs/analyzers`) with its presets. Repository and group pages, the Audits page (**Run audit**, the `audit` analyzer) and every analysis page (**Run now** with that page's analyzer, also in its empty state) open it. **Analyze past releases** (`BackfillReleasesButton`) on the Public API page (API snapshots) and the Bundles page (bundle sizes), for the picked repository or all of them, queues that page's analyzer for the newest 10–100 releases it has not analyzed (`POST /api/analyses/backfill`) and opens the Jobs page.

## Tasks

`/tasks` (Ops workspace next to Jobs, `repos:read`) lists agent write tasks from `GET /api/task-groups`, one row per task group: a status tag, the title with kind and source (`taskSourceLabel`), the target repositories in mono (the first one and `+N`), a `SegmentBar` of the tasks by status (`taskSegments`), links to the merge requests opened so far, the agent spend and when it last changed. It polls every 5 s while a group waits or works. `SegmentedTabs` filter **In progress** (proposed, approved, queued, running), **MR open** and **Ended** (`matchesTaskFilter`; `?filter=`). Tasks are their own page rather than a Jobs segment because a group is a different record from a job: it spans several repositories, waits for approval and lives on after its jobs end (merge request state and CI), while Jobs stays the queue of single analyzer runs.

A row opens the group in the `SideSheet` (`?group=`, J/K step through the filtered list; `GET /api/task-groups/:id` refreshes merge request state and CI and polls every 3 s while it works), drawn by `TaskGroupView`: status, kind, source and a `patch first` tag for the `git apply -3` fast path, **Approve** (asks first, with the spend cap; while `tasks.write` is off a warning shows and the confirm button stays disabled) and **Cancel** when the group's `can` allows; who proposed and approved it and when; the budget class; spend against the cap (the tasks' budgets once queued, else `taskGroupCap` from `GET /api/write-tasks`); the plan as Markdown with the original request folded and the group's patch (`patch` of the detail) folded under it, so approvers see what runs; a read-only `FlowCanvas` (`TaskGroupFlow`, projection `taskGroupFlow`): source → one node per target repository → its merge request → CI, each node with a stripe in its status color, dashed edges to proposed or cancelled repositories and to repositories a task asked for, failed ones in red; repositories a task asked to add with **Add** and **Reject** (`POST /api/task-groups/:id/requests`); and one row per repository. A row (`?task=`) opens the task: branch, job link, spend against its budget, the merge request with its CI tag and when it was last checked, the error, its own patch (`taskPatches`, e.g. a rollout fix's bump), **Retry** (`POST /api/tasks/:id/retry`) and **Cancel this repository** (`POST /api/tasks/:id/cancel`) when the task's `can` allows, and the job's agent runs with their transcripts (`JobAgentRuns` from Jobs). Mutations (`useTaskGroupMutations`) refresh task lists and open chat threads.

## Automation

`/automation` (Ops, `settings:read`; editing with global `settings:write`) is one page without tabs. Each team gets a lane: one for **All repositories** (rules without groups, label and command triggers, policies scoped to everything or to repository globs only, and the release assistant), then one per config group. A lane is a `FlowCanvas` of event nodes (push, tag, merge request, label, command, new repository, schedule, freshness) → rule nodes → action nodes (analyzers, review, a policy action such as approve or label, a release step, or a set such as "every read-only analyzer"), projected by `automationLanes` in `lib/automation-flow.ts` from the stored trigger and schedule documents (`/api/config/triggers`, `/api/config/schedules`), the `mergeRequests.policies` setting entries and the analyzers' `refresh` (`/api/jobs/analyzers`). Nothing about the drawing is stored. A rule limited to groups appears in each member group's lane; an intersection (`a + b`) adds an "only a + b" chip. Rule nodes carry condition chips (branches, events, `describeCondition` clauses, cadence, skipped analyzers), an **AI** tag when an action may call an LLM and **off** when disabled (its edges dashed). Clicking a rule opens the `SideSheet` with its linear form, **When / Where / If / Then / Limits** (`RuleForm`): `TriggerForm` (event, groups, merge request events and drafts, branches or command arguments, analyzers; a new repository trigger can run on every known repository), `ScheduleForm` (cadence, time zone, next and last runs with a `TickStrip`, groups and repositories, weekends and nights, analyzers, enabled, jitter and spread, **▶** run now; allow and deny windows and holidays of older schedules are kept as stored) and `PolicyForm` (name and id, merge request events, the entry's scope, the common conditions, actions with options from the setting's schema via `SchemaForm`, enabled, stop and skipped analyzers; other conditions such as size, pipeline or nested groups are kept as stored). They save through the same APIs as before: `PUT /api/config/<collection>/:id` and `PUT /api/settings` (`withPolicy`/`withoutPolicy` in `lib/policies.ts` replace one policy of an entry; a team's new policy goes to the entry scoped to exactly that group, `policiesEntryFor`, with an id no other policies entry uses). **New rule** adds a trigger, schedule or every-repository policy, **New policy** on a lane one for that team. The freshness rule opens the lane's Freshness card, the release assistant points to Releases. Next to each lane a **Freshness** card, which edits only the team's override, (`FreshnessCard`) lists the analyzers that declare `refresh` with their policy (`describeRefresh`), what the last sweep found stale or waiting (`GET /api/automation/freshness`), the next sweep, the night window and hourly caps (`sweepLimits` over `freshness.sweep`), and the team's override as **On / Slower / Off** (with a factor), saved as the `freshness` setting scoped to the group (`laneFreshness` reads it; an entry shared with other groups or the every-repository entry is shown as inherited and never rewritten or deleted from a lane). `mergeRequests.policies` and `freshness` are therefore left out of Settings (`automationSettingKeys`). With `ai:read` an **AI forecast** card (`forecastAutomaticSpend` in `lib/automation-forecast.ts`) averages the last four full weeks of AI usage by `week,analyzer` (runs an analyzer started count as automatic; only weeks since usage began; this week projected when there is none) and draws it against the weekly budget with a `SegmentBar`: automatic so far, the rest of the forecast, other work, with the limit automatic work stops at (budget minus reserve). **Why did this run**: the job detail's Why section links to `/automation?job=<id>`, which shows the job's origin and highlights in the lanes of its groups the event → rule → action path that queued it (`whyPath`: the schedule, also run by hand; freshness; or the triggers and policies of its event that queue its analyzer; disabled rules count only for a schedule run by hand), edges in the accent color; a job nothing on the page explains (by hand, polling, a rule changed since) says so. The forges under Settings → Integrations get a webhook block: a panel forge generates or rotates its secret and registers the hook on GitLab (`POST /api/forges/:id/webhook`), the secret shown once.

## Repository config and media

**Coverage** (`/coverage`, `features/test-coverage/`, `analyses:read`) reads `GET /api/coverage` and shows one card per repository with a coverage record, lowest line coverage first (`sortCoverageCards`): line share toned like the report (good from 80%, bad below 50%, `coverageTone`), its change in points since the record before, branch share, a `SegmentBar` of covered lines, uncovered lines and lines in files without tests (`lineSegments`), a `TickStrip` of line coverage over the last 12 records (`trendTicks`), the line coverage of files that changed since the record before, file counts, the record's short sha and age, and a freshness tag (`coverageFreshness`: over a month or a week old, else behind HEAD when freshness saw a newer default-branch head, else current). A `ScopeSwitch` picks the viewer's team, everything or other teams; under _My team_ other teams' cards fold into `OtherTeams`. A card opens `CoverageSheet` (`?repo=`, J/K step through the cards), which reads `GET /api/coverage/repo`: shares and tools, a table per workspace package or top-level folder, the files with the most uncovered lines, the files that moved by 5 points or more, a link to the full record and **Run now**. `RepoCoverageCard` is the same card loading itself for one repository, shown on the repository page's Overview, with **Run coverage** until a record exists. Nothing on these pages calls an LLM.

The repository page's **Assets** tab (`AssetsTab` in `features/assets/`, `analyses:read`) reads `GET /api/assets/repo`: a summary of the newest assets record (total bytes, files, error and warning tags, savings, duplicate bytes, a bar of bytes per kind in stable series colors (`kindColor`), a sparkline of total bytes over recent records and exceeded budgets), a files table with size, problems as tags and the best conversion, filtered to files breaking the policy or everything to improve (`filterRows`), with **Optimize** opening the media dialog on an image (`analyses:run`), and the **Asset policy**: the effective policy as labelled lines (`policyLines`), where it comes from (`policySource`: default, every repository, a group, this repository; the server names the group only to viewers with `settings:read` on that entry's scope) and the `assets.policy` entries of the repository with the setting's own form (`PolicyBlock`). `?file=&ref=` on the repository page opens the media dialog on that file, which is where review comments link. There is no separate Assets page.

The media dialog, opened by **Optimize** on the Assets tab (`analyses:run`), generates image variants of a file (`POST /api/media/variants`), compares sizes, previews variants, shows markup snippets and puts the chosen files into a merge request or a ZIP (`POST /api/media/apply`).

## History

`/history` (Ops workspace, `repos:read`) replaces the old Activity and Audit log pages. It reads `GET /api/history`, so it lists only what the viewer may see: every audit event with global `audit:read`, otherwise only events about repositories the viewer can read. The `ScopeSwitch` narrows it to the repositories of the viewer's home groups (_My team_), the rest (_Other teams_) or everything (_All I can see_), using the repositories and groups from `GET /api/history/scope`. The filters bar picks an area (an action prefix: releases, settings, knowledge, access, credentials, repositories, jobs, MR policies, analyses), one repository, an outcome and a time range (24h, 7d, 30d, all); clicking an actor filters by them. Rows are dense: relative time in mono, actor avatar and name, the action in words with a status tag when it was denied or failed, and the target (repository or `type:id`) in mono. A row opens the `SideSheet` with the actor, request, field-level changes as a before/after diff and the raw details as JSON; J/K step through the loaded rows. With global `audit:read` the header also offers **Verify chain** and CSV/NDJSON export of the filtered events (`lib/history.ts` builds the query).

## AI usage, storage and database

These are sections of Settings (see below), no longer pages of their own. **AI usage** (Settings → AI, `ai:read` or `ai:admin`, `features/ai/AiUsage.tsx`): this month against the previous one, each weekly budget as a bar of this week's spend against `weeklyUsd` with a marker where automatic work stops (the reserve) and the projected spend by week end, daily cost for 30 days, top repositories, models and task kinds, and every run with links to its job and analysis. **Storage** (Settings → System, `features/storage/Storage.tsx`): space per storage area with breakdowns and **Clear** where the area allows it (global `settings:write`); git mirrors and the tool cache are broken down by worker as the workers report them, and clearing them asks every worker. **Database** (Settings → System, `features/database/Database.tsx`): the store's database — size with 7-day growth, cache hit ratio, connections and uptime (or table, row and migration counts on SQLite), findings worth a look, and behind **Diagnostics** the tabs: **Tables** (rows, data, index and TOAST bytes, dead rows, last vacuum and analyze; filter and sort), **Growth** (daily size chart and size per domain with its 7-day change), **Statements** (top `pg_stat_statements` entries by total time, mean time or calls, refreshed every 30 seconds, **Reset** with global `settings:write` when the database allows it, or how to turn them on), **Sessions** (replicas and client connections, busy or all, every 5 seconds, with what they wait for and who blocks them), **Indexes** (size, scans, unused and duplicate flags) and **Migrations**; Statements and Sessions are Postgres only. **Caches** (Settings → System, `features/caches/Caches.tsx`): the egress proxy's download cache (`GET /api/egress/cache`) — stored size, bytes saved by hits, hit rate and bytes served since the answering replica started, packages and tools with their TTL and largest hosts, every entry with size, hits, last use and expiry (filter by kind and URL), the store and cached URL patterns, a warning that cached copies outlive upstream and access changes, and removing one entry, a kind or everything (global `settings:write`). `/account` also lists linked external accounts, links new ones and issues verification codes.

## Knowledge

`/knowledge` (Team workspace, `knowledge:read`) is the single place for the rules agents follow. The URL holds the space and tab (`?space=all|group:<id>|family:<id>|repo:<forge>:<path>&tab=guide|notes|learnings`, parsed by `knowledgeSearch` in `lib/guide.ts`).

- **Spaces** (`SpacesSidebar`): _All repositories_, then teams (config groups) with their families and repositories (`buildSpaceTree`). A repository in several groups shows under each; a family shows under every team holding a member. The `ScopeSwitch` folds other teams (_My team_ keeps teams named by the viewer's home groups) and the "N other teams folded" line widens it. With `settings:write`: **Suggested families** from `GET /api/families/suggestions` with **Confirm** (`POST /api/families`), **Edit** and **Dismiss** (`POST /api/families/suggestions/dismiss`, kept on the server for everyone), plus a small family editor (`FamilyDialog`: name and at least two known repositories; deleting a family deletes its rules).
- **Guide** (`GuideTab`): one card per section (General, Review, Testing, Test ids, Assets, Commits, Releases) from `GET /api/guide?scope=`. _Team rules_ render as Markdown with "edited by <avatar> name · time"; editing opens a Markdown editor with preview in place and saves with the section version (`PUT /api/guide/section`, 409 when someone else saved first). **History** opens a `SideSheet` with every revision (`GET /api/guide/section`) and **Restore**. _Learned rules_ list accepted learnings with their sources. Sections with generated text (General, Testing, Test ids, Commits) take a short _Steering_ prompt; in a repository space they show _Generated_: read-only Markdown with its status (proposed, accepted, new proposal) and model, cost, time and commit in mono, **Accept** (`POST /api/guide/section/accept` with the shown `inputHash`) and **Regenerate** with an optional extra prompt (`POST /api/guide/regenerate`, needs `analyses:run`). The Commits section renders the `commits.conventions` setting's entries made for the space, the Assets section the `assets.policy` entries, and the Test ids section the `analyzers.testids` entries (the team's overrides of the learned test id convention: attributes, elements, excluded files), with the setting's own form (`PolicyBlock`, `settings:read`, editing with `settings:write`). There is no separate Test ids page: the catalog reaches people through this section and agents through the MCP tools. Editing follows the API's `canEdit`.
- **Effective prompt** (header button, `PreviewSheet`): the resolver's text for a chosen repository of the space and task (`GET /api/guide/preview`), the character budget as a `SegmentBar` (human, generated, notes against the total), warnings and every block with what was cut.
- **Notes** (`NotesTab`): knowledge entries of the space (all of them for _All_, those naming the team or a family member, and for a repository those covering it, marked _inherited_ when they come from a broader scope) as cards grouped by first topic or by kind (`groupNotes`, `notesOfSpace` in `lib/knowledge.ts`), filtered by Live / Rejected / Archived and text. Proposals from agents and MCP come first with **Accept** and **Reject**. Cards show "written/proposed by" and "edited by" with avatars from the list's `people`, a `shared` tag and the subject. In the _All_ space, accepted notes of other teams (by the list's `owner`) fold into **Other teams (N)**. `NoteEditor` creates and edits notes in place: title and Markdown text, with kind, scope, tasks, topics, packages, visibility (_Default_ lets the server share a decision about one package, _My team_ or _Shared_) and subject and evidence under _Details_; saving a proposal can accept it in the same step (`POST /api/knowledge/:id/accept` archives the entry it supersedes).
- **Learnings** (`LearningsTab`): candidates from replies to review comments and rules proposed over MCP (`GET /api/learnings`) with their sources (or who proposed them and why), section and suggested scope; with `canDecide` **Accept** into one of the offered scopes, edit the rule and section in place (`PATCH`), **Reject**. Accepted rules show where they live and who accepted them, rejected ones fold away. _Reactions on review comments_ sums 👍/👎 per finding category (`GET /api/learnings/reactions`) in the All space and repository spaces only, since totals are kept per repository; hidden when the caller may not read them.
- **Settings** (header button, `settings:read`): `knowledge.autoAccept` and the review analyzer's options (`analyzers.review`; `knowledgeSettingKeys` in `lib/knowledge.ts`) in a `SettingsSheet`; Settings has no Knowledge tab.

## Settings

`/settings` is four tabs, and the shell's top bar draws them: the Admin workspace has one entry per tab (`/settings?tab=ai|access|integrations|system`, `parseSettingsTab` in `lib/settings-tabs.ts`), so the page has no tab row of its own. A tab is shown only to principals the server lets read some of it, mirroring the server checks (`visibleSettingsTabs` in `nav.ts`); an unknown or hidden `tab` falls back to the first visible one, and with none the page says "No access".

- **AI** (`ai:read`, `ai:admin`, `settings:read` or `credentials:read`): the `llm.provider` and `llm.budget` settings with `agent.tools` under **Advanced**; the AI provider credentials (`Credentials kinds="ai"`: kinds `anthropic`, `anthropic-compatible`, `ai-sdk`, with **Models**, **Test** and the `modelMap` in their options); AI usage.
- **Access** (everyone): users with passkeys and the access map (`users` provider and `users:read`), `access.crossTeam` and `repo.readOnly`, and the MCP server section (connect, tokens, tools and usage as a `SegmentedTabs` switch inside the section).
- **Integrations** (`credentials:read` or `settings:read`): forges with webhook and SSH key (global `settings:read`), the other credentials, the `trackers` setting with the tracker analyzer's options, `releases.notify` (release webhooks) and `limits.credentials`, and the stored Slack tokens (global `settings:read`).
- **System** (global `settings:read`): storage, database, caches, the library index, **Write tasks** (`WriteTasksSection` in `features/tasks`: the kill switch, which flips only `enabled` on the global `tasks.write` entry (`writeTasksSwitch`), the write pool's state from `GET /api/write-tasks` (`writePoolState`: turned off, idle, working, or **No write worker** when a task has waited over five minutes with nothing running), queued and running counts, the oldest wait, the last start and the workers running now, this week's spend against `weeklyUsd` as a `SegmentBar`, the caps, and the `tasks.write` entries; `sectionSettingKeys` keeps that setting out of the generic list), then `libraries`, `polling`, `toolchain` and `freshness.sweep`, and every setting no page or tab claims (`tabDefinitions`), such as plugin settings and analyzers without a page (`i18n`, `propagate`), so nothing is left uneditable.

Settings that belong to a page are edited there (`pageSettingKeys` in `lib/settings-tabs.ts`). Analysis pages carry a gear button (`SettingsButton` in `features/settings/SettingsSheet.tsx`, `settings:read`) that opens a `SideSheet` with their analyzers' options: Bundles, Dependencies (`depgraph`, `renovate`), Public API (`api-surface`, `usages`), Stack (`stack`, `browserslist`; also **Edit conventions**), Audits (`analyzers.audit`, `audit.fix`, `audit.upgrade`, `audit.allowlist`), Licenses, Coverage, Branches, CI and the repository Assets tab (**Analyzer options**). Releases keeps `releases` on its flow tab, Knowledge keeps its section policies and settings sheet, Automation keeps `mergeRequests.policies` and `freshness`. The effective value per repository and where it comes from lives on the repository's **Settings** tab (`ScopedSettings`).

Each setting shows its entries per scope next to its `help` (`SettingEntries`: `SettingCard` plus the add, edit and delete dialogs). Adding or editing an entry opens a wide editor: scope and value on the left, the setting's guidance on the right. A `global` setting (such as `llm.provider`) has no scope picker: its entry always applies to all repositories. Settings with `presets` get a **Preset** picker above the value (`PresetPicker`, helpers in `lib/presets.ts`): applying one merges its fields into an object value (replaces other values) and remounts the value editor; the picker shows the preset the value already matches. Values get a form built from their JSON Schema; a setting or a string property with `x-credential: <family>` gets `CredentialPicker` (credentials of that family, e.g. `github` → kind `github`; it stores the id, shows the name, explains how to add one when there is none and falls back to a text field without `credentials:read`), and an array of such strings gets `CredentialsPicker` (several credentials, ids stored in order, an old name or unknown id stays listed as itself until removed, tag input without `credentials:read`). Every value gets a form; merge request policies and freshness are edited on Automation instead. `x-editor: trackers` gets `TrackerEditor`: entity and key normalization, a map (`@xyflow/react`) of sources by role → rules that read those roles → outputs, where dragging from a source to a rule sets the source's `x-role: provides` field to a role the rule reads, preferring one no source provides yet (`linkSource`), with rules that read a role no source provides and sources no rule reads called out, then Sources, Rules and Outputs blocks whose options come from the kind variants of the schema. Shared rails and remove buttons live in `features/settings/blocks.tsx`.

## Chat

**Chat** (`features/chat`, route `/chat?thread=<id>`, needs `repos:read` somewhere) is the team chat over `/api/chat/threads`, laid out as three columns that fill the viewport.

- **Threads** (`ThreadList.tsx`): the scope switch (`scopeThreads`: team-wide threads count as _My team_, and _Other teams_ lists the other teams' threads rather than only counting them), an archived toggle, **New** (a dialog for the title, the scope: whole team, one repository or one of the groups the caller may use, and whether Holtkeeper replies to every message), and the threads with their scope, last activity, a writing indicator and an unread badge. The rail's Chat icon shows the total unread count (`GET /api/chat/unread`, every 30 s).
- **Messages** (`ThreadPane.tsx`, `Messages.tsx`): consecutive messages of one author within five minutes share one header (`groupMessages`), with a line per day and a **New** line above the first message that was unread when the thread opened (`firstUnreadId`). People show with their avatar and name (their participant label, all the model gets, on hover); Holtkeeper with its avatar and an `AI` tag. Bodies are markdown; commands show as code. Agent replies show a collapsible tool trace (`toolSummary`; opening it loads the transcript from `GET /api/chat/messages/:id/transcript` and lists each call with its input and result, `toolCalls`) and their cost in mono (`formatCost`). Messages that mention the viewer are tinted. Holtkeeper's answers are cards (`ChatCard`): a tone stripe, title and subtitle, section headings, dividers, markdown text, fields, steps as a timeline or a row of stages, lists, buttons (danger buttons ask first; they post the command as `/command`), inline forms whose submit runs `formCommand`, and task cards (`TaskBlock`: the plan, the target repositories with the merge requests their tasks opened, a status tag, **Details** to the group on the Tasks page, **Cancel** while it waits or works (`taskCancellable`; asks first, like the sheet's Cancel) and, while proposed, the group's spend cap with **Approve**; Approve asks first (warning and a disabled confirm while `tasks.write` is off) and calls `POST /api/task-groups/:id/approve`, so the change runs for the person who clicked; the server rewrites the card as the group moves on and the next poll shows it). The header renames, archives and restores; the right column (wide screens) shows the scope, the participants with their labels, the autoReply switch, the agent spend of the loaded replies and whether older messages reach the agent as a summary.
- **Composer** (`Composer.tsx`): `@` opens the people who can see the thread (`GET /api/chat/threads/:id/people`) with Holtkeeper first (`mentionAt`, `mentionOptions`, `insertMention`); a leading `/` switches to command mode with matching commands as hints (`matchingCommands`) and the repository or group they run about; in team-wide threads, which refuse commands, it shows that commands run in repository and group threads instead and does not send. Arrows and Tab pick, Escape closes the list, Enter sends, Shift+Enter starts a line. The footer says whether Holtkeeper will reply (`asksAgent`, which reads mentions like the server's `parseMentions`).
- **Live updates**: `useChatThread` loads the newest 50 messages once, then polls every 3 s (1.5 s while a reply is being written or a card from the last day shows unfinished steps) with `after=<cursor>&changedSince=<serverTime>`, folding new and changed messages into the cache (`withNewer`); the cursor moves only with message pages, never with a message the viewer posted, so messages others stored in between are not skipped; **Load older messages** puts the page before the first one in front (`withOlder`) and keeps the scroll position. A posted message goes into the cache at once. The view follows new messages while scrolled to the bottom, and the newest message is marked read while the tab is visible, or as soon as it becomes visible. Thread lists poll every 10 s.

Helpers live in `lib/chat.ts`.

## Releases

**Releases** (`features/releases`, Delivery workspace next to **CI**, shown with `releases:read`) replaces the old release board and the Releases analysis page.

`/releases` (`ReleasesPage`) reads `GET /api/releases/overview`: one card per repository with releases on (`releases.enabled`), joined with `GET /api/repos` for groups so the `ScopeSwitch` applies (_My team_ by default). A card shows the repository, its latest version in mono with its age, the next version with its bump `Tag`, unreleased commits on the target and the source and the task count, where it stands in plain words (`stageText`: "Waiting for acceptance", "Ready to tag", "Deploying to prod", …), a `TickStrip` of the source and target pipelines and the latest version's deploy per environment (`cardTicks`, only when the snapshot has them) and the one next step as a link (`nextStep`). **Needs action** (the default, from the card's `needsAction`) and **All** filter; cards needing action sort first (`sortCards`). **Refresh** starts a background read and the page refetches every 3 s until it finishes. With `settings:write`, **Set up a repository…** opens the Flow tab of a repository that is not listed yet.

`/releases/<forge:path>` (`ReleaseTimelinePage`, a splat route; `?tab=flow` opens the Flow tab) reads `GET /api/releases/repo`:

- **Timeline.** Forge links of the current release, then the **Next** card (`NextCard`): current → suggested version in mono with the bump `Tag` and its reasons, **Change** (a dialog with the suggestion, patch/minor/major and a custom version, saved as an edit), the pending changes grouped by type with breaking changes first (`entryGroups`), **Edit entries** to include, leave out or reword entries (saved at once and previewed before the server recomputes the plan), the tasks from the entries' ticket keys (`planTasks`; with a connected tracker the view's `issues` add the issue's title and a status `Tag`, otherwise the key and the commit titles, linked only when a URL is known), the collapsed **What changed** notes (edit, reset, **Write with AI** on the fast tier when an agent is configured), acceptance (accept or withdraw), the gates as one line that lists only the failing ones when something fails, and one button for the step (**Create vX**, **Open release MR** or **Update !N**). The button opens a confirmation that lists what will happen, previews the text, offers "write the notes with AI first" when proposing (`writeNotes`) and an override checkbox when a soft gate fails. With both a version and a release candidate pending, `SegmentedTabs` switch between them. Under it, `DeployStrip` shows the latest version's environments as chips (status tag, attempts on hover, play/retry/redeploy behind a confirmation when the environment asks for one, waits for an earlier one or already runs it; polls every 5 s while a job runs). **Versions** pages `GET /api/releases/timeline` (10 at a time, more as you scroll): each row has the tag in mono, bump, commit and task counts, a `TickStrip` of recorded deploys per environment (`versionTicks`) and its age; it expands to tasks and the changelog (Markdown, `GET /api/releases/version`), and opens in the `SideSheet` with its deploys and the compare link, J/K stepping through the loaded versions.
- **Flow.** The release flow drawn from the `releases` setting with `FlowCanvas` (`releaseFlowGraph` in `lib/release-flow.ts`): merge request mode `source → release MR → target → tag → environments`, trunk mode `target → tag → environments`, external mode one node followed by the environments; an environment with `after` hangs off that environment. With `settings:write` on the repository, a click opens the node's own fields in a side sheet (source: flow and source branch; target: branch, gates, and acceptance in trunk mode; release MR: labels and acceptance; tag: scheme, tag format, release candidates, CHANGELOG.md, left-out commit types, tracker URL; environment: name, job, after, confirm, remove), **Releases on** switches the repository on or off, **+ Environment** adds one (`addEnvironment`), and a detected flow can be saved and turned on at once. Each save writes the repository's own `releases` entry (`repoReleaseEntry` finds it in `GET /api/settings/resolve`, otherwise a new one is created). The release notes style is a Guide rule (section Releases), not a field here.

Release steps run in the panel are labelled by where they happened (panel, API, forge, panel chat, MCP) and who ran them. Helpers live in `lib/releases.ts`.

## CI

**CI** (`features/ci`, Delivery workspace, shown with `analyses:read`) shows the newest `ci-jobs` record of each repository; it has no list of nightly records and no compare, and offers **Run now** only while a repository has no record yet.

`/ci` (`CiPage`) reads `GET /api/ci`: one card per repository with CI runs in the last 30 days, joined with `GET /api/repos` for groups so the `ScopeSwitch` applies. A card shows the median pipeline time in mono with its week-over-week change as a `Tag` (`changeLabel`: `↑ 12%` slower reads as bad), the success rate, a sparkline of the weekly median, the pipeline count and branch, the age of the newest run and a problem-job count; cards with problem jobs sort first (`sortCiCards`). `/ci?repo=forge:path`, the link analysis cards and repository pages use, redirects to the repository page.

4. **Problem jobs**: at most five rows from the view, each a kind `Tag`, the job, its stage, a one-line reason and a link to the run.

## Analyses and reports

Analyses (`bundle`, `depgraph`, `coverage`, …) all produce the universal `Report` from `@holtkeeper/report`. The Code workspace has **Dependencies**, **Public API**, **Stack**, **Licenses**, **Bundles**, **Coverage** and **Branches**, without a repository each shows one card per repository with its avatar, newest run, headline metrics as tiles with their change since the run before, a sparkline of the page's trend metric and who ran it, sortable by name, recency or that metric; with a repository it lists the runs with their changes and trends of its preferred metrics (gzip/size for bundles, issues/coverage for quality, to clean up/stale for branches; violations/unknown for licenses; see `analysisPages` in `lib/analyses.ts`). **Stack** and **Coverage** are not record lists (below); a `stack` record's page links back to it. `/analyses/$id` renders the record with `ReportView` and a "compare with" picker that sets `?compare=<id>` (default: the previous record). The repositories table links to each repository's analyses.

**Bundles** (`features/bundles`, route `/bundles?repo=&target=&version=&analysis=`) shows the repository cards of the `bundle` kind without a repository. **Public API** (`features/public-api`, route `/public-api`) reads the API catalog (`/api/api-surface/*`) of the organization's own packages; third-party libraries live on Dependencies. The catalog has two tabs: **Packages** shows totals and a table of every package (version, repository, exports, share documented, versions on record, the `removed` badge) filtered by name, description or repository; **Search** finds exports by name or doc text, optionally of one kind. `?package=&version=&repo=&tab=` opens one package (`tab` is `api`, the default, `changes`, `used-by` or `upgrade`): a version picker, a link to its Markdown, facts (ref, repository, exports, documented, other repositories with the same package) and four tabs — **API** groups the exports of an entry point by kind with doc comments, declarations, source locations and import lines, filterable, 150 at a time; **Changes** diffs it with an earlier release (removed, changed with before and after, deprecated, added), with the semver warning when exports were removed without a major bump; **Used by** (`UsagesTabs.tsx`, from `/api/api-surface/usages/*`) shows the repositories using the package with their versions (green for the newest in use) — under _My team_ other teams' repositories (by the `groups` the server sends) fold into a collapsed **Other teams (N)** table — the exports they use with kinds, props and members as bars, the exports no analyzed repository uses, and the code of the picked export, prop or member as snippets with line numbers; clicking a repository narrows everything to it; **Upgrade** picks an older release and lists what upgrading from it breaks (`breaking`, `check`, `deprecated`), with removed members and the affected code per repository, and **Copy as prompt** copies the plan as Markdown for a coding agent (`upgradePrompt` in `lib/upgrade-prompt.ts`). **Dependencies** (`features/dependencies`, route `/dependencies`) reads `GET /api/dependencies` (one row per library from the newest `depgraph` and `usages` records; the former Updates and Libraries pages are folded into it). The `ScopeSwitch` defaults to _My team_: rows narrow to the repositories of the viewer's home groups with their versions and behind figures recomputed, _All I can see_ shows every row whole and _Other teams_ only counts libraries, repositories and teams (`scopeRows`, `narrowRow`); under _My team_, libraries only other teams use follow in a collapsed **Other teams (N)** table with the same filters (`otherTeamRows`) and its own **Show more**. Three tiles — behind a major, known advisories, update MRs waiting / broken (`tileCounts`, third-party only) — act as filters; the filter bar has a name search, `Third-party`, `Behind`, `Advisories`, `Update MRs` and `Internal`, and an ecosystem picker when there are several. The table shows each library with its ecosystem and an `internal` tag, a version spread bar colored by breaking releases behind the registry latest, latest, a behind tag (majors behind, repositories behind), Renovate state and advisories with the worst severity, 60 rows at a time. With `?repo=` it shows only that repository's libraries and versions. A row opens the library in the `SideSheet` (`?library=npm:<name>&tab=`; J/K step through the rows on screen (the folded table's only while it is open); a button opens `/dependencies/<ecosystem>/<name>`, the same `LibraryDetail` as a page). Its tabs: **Overview** (`/api/dependencies/library`) — facts and links (Public API for internal npm packages), team decisions (people's before approved agent entries; other teams' shared ones with their team, folded under **Other teams**), the version spread, users with versions and behind tags, other teams folded under _My team_, advisories, licenses with verdicts, bundle shares, update merge requests and indexed versions with their roles; **Upgrade** (`/api/dependencies/upgrade`) — from (versions in use) and to (indexed versions and latest) pickers (`upgradeVersions`), notes on what is missing, the affected uses narrowed to the scope (`narrowImpact`) or the API changes, the changelog as Markdown, the open merge requests and **Copy as prompt**, which copies the plan with the repositories, affected files and lines and the release notes quoted as data (`upgradePrompt`), and, for people with `tasks:run`, **Roll out**: a dialog lists the repositories using the library below the target version (`rolloutTargets`) with the estimated spend cap (`taskGroupCap` over the `tasks.write` caps from `GET /api/write-tasks`), warns (and keeps its confirm button disabled) when write tasks are off or there are more repositories than `maxRepos`, and starts a task group (`POST /api/task-groups`, kind `upgrade`, the same plan as prompt, `run: true`), one draft merge request per repository on a shared branch; **Docs** (`/api/dependencies/docs`) — a search over the library's indexed docs, and the documents of the newest indexed version by source. Nothing on the page calls an LLM. Helpers live in `lib/dependencies.ts`, `lib/libraries.ts` and `lib/upgrade-prompt.ts`.

**MCP server** (`features/mcp/McpServer.tsx`, a section of Settings → Access, every signed-in user) is where people connect agents to the `/mcp` endpoint. A switch in its header picks the view. **Connect** (the default) has three steps, the caller's tokens (`/api/api-surface/mcp/tokens`: create with a name, lifetime and the **Release steps** switch, which adds the `release` scope for `release_step` and marks the token with a `release` tag, and the **Run tasks** switch, which adds the `tasks` scope for `start_task` and `request_review` (tag `tasks`), the secret shown once with its Claude Code command, revoke) and the setup: endpoint, Claude Code command, `.mcp.json` snippet, a `curl` that lists the tools to check a token, and a note that tokens also read `GET /api/api-surface/*` and `GET /api/dependencies*`. **Tools** is a reference read live from the endpoint: the page posts JSON-RPC `tools/list` to `/mcp` with the session cookie (`mcpRequest` in `api/client.ts`), so it shows exactly the tools the caller gets, split into the organization's packages and third-party libraries (`libraryTools`), each with its description and arguments (name, type, required, description; `toolParams` in `lib/mcp.ts`), filterable. **Usage** (`/api/api-surface/mcp/usage`) shows calls per day with failures, top tools, packages, people and clients, and recent calls over 7, 30 or 90 days. Helpers live in `lib/mcp.ts`. The Vite dev server proxies exactly `/mcp` (`^/mcp$`), so the panel's own routes are never proxied.

**Stack** (`/stack?tab=runtimes|eol|conventions`, `features/stack/StackPage.tsx`; `StackView` is reused by the group page's **Stack** tab with `group` set) reads `GET /api/stack` and shows the current state, not records. The scope switch folds other teams' repositories as on Dependencies (`scopeStack` in `lib/stack.ts`); under _My team_ the current tab repeats for other teams' repositories in a collapsed **Other teams (N)** section (`otherTeamsStack`), whose convention cells carry no fix. A line under the tabs sums each group's changes since its record a week earlier (`weeklyChanges`). **Runtimes**: one row per tool merged across groups (`toolRows`: runtimes, package managers, services, base systems, images, tools; then by repositories), its latest and latest LTS, and a chip per version line in use (release line, else the major as written, else `floating`; `versionLine`) with the repository count and a dot for the worst support; a chip opens a side sheet with the repositories, what they write and where. **End of life**: one row per repository, tool and ended or ending line (`eolEntries`), ended first, then by end date, with the fix to the newest supported line (`node 18 → 24`, from latest LTS else latest). **Conventions**: repositories × convention files with `matches`, `drifts`, `missing` or `error` (`conventionGrid`, failing repositories first); a cell opens a side sheet with the problems, the suggested fix as a diff (`FileDiffView`) and, with `analyses:run`, **Open merge request** (`POST /api/analyses/:id/changes` with the fix's id). **Edit conventions** (and the page's gear button) opens the Stack settings sheet, where the `analyzers.stack` setting edits them as a form (path, match mode, golden content in a text area through the schema's `x-multiline`).

**Library index** (`features/settings/LibraryIndex.tsx`, the **System** tab of Settings, shown with global `settings:read`) shows what the server indexes for agents (design: [docs/library-docs.md](../../../docs/library-docs.md)). It reads `GET /api/system/library-index?q=&ecosystem=` (every 10 s while a run goes on): totals, a note naming the MCP tools agents use (`library_versions`, `search_library_docs`, `read_library_doc`, `library_changes`, `search_library_issues`, `library_source`), **Indexing now** while a run goes on (`features/settings/IndexStatus.tsx`: libraries done of all as a bar, the libraries in work (several with `concurrency`), time so far and an estimate of the rest from `runProgress`, and the time a GitHub rate limit wait ends), **Coverage** per source (a bar of indexed, nothing to index, failed, skipped and not fetched yet, with the settled share from `coverageDone` and the counts), the last indexing run (when it finished, counts, an error, failed sources expandable with their messages), **GitHub API usage** (`GitHubUsageSection`: capacity per resource across distinct accounts, requests, saved by the cache, rate-limited answers, waits for a reset, requests per day stacked by token and anonymous requests over 7, 30 or 90 days), and a table of libraries — name with description, ecosystem, latest, indexed versions as chips, repositories using it, document sections, issues, a warning badge for sources whose last fetch failed, and when it was updated — filtered by name and ecosystem. **Reindex now** (`analyses:run`, global on the server) posts `POST /api/system/library-index/reindex`. When the server does not index libraries (`enabled: false`), it explains the `libraries` setting instead. Helpers live in `lib/libraries.ts` and `lib/github-usage.ts`.

`features/reports/ReportView.tsx` renders any report without knowing its kind: header (subject repo, ref, compared ref), metric cards with animated values and deltas colored by `better`, and sections as anchored cards with a scroll-spy table of contents. **Adding a block type:** add it to the model, write `blocks/<Type>Block.tsx`, register it in `registry.tsx` and add the type to `blockTypes` in `lib/analyses.ts`. The compiler refuses a registry or list that misses a type, and `registry.test.ts` checks they match. Unknown types from a newer server show a neutral placeholder.

## Design notes

- **Themes.** Dark is the default. The preference (dark, light, system) is stored in `localStorage` under `holtkeeper.theme` and applied as `.dark`/`.light` and `data-theme` on `<html>` by an inline script before first paint; the rail's toggle cycles dark → light → system, and `ui/theme.ts` follows `prefers-color-scheme` while the preference is system.
- **Graphite tokens.** `app.css` defines the palette once per theme on `:root` (dark) and `:root.light` / `[data-theme='light']`: `--bg`, `--panel`, `--raise`, `--sunk`, `--chip`, `--line` and `--line-strong` (hairlines), `--fg`, `--fg-muted`, `--dim`, the one accent `--brand`, and status colors `--ok`, `--warn`, `--bad`, `--info`, `--code`. Tailwind gets them as `bg-panel`, `bg-raise`, `bg-sunk`, `border-line`, `border-line-strong`, `text-dim`, `text-ok`, `text-info` and so on. HeroUI's theme variables (`--background`, `--surface*`, `--accent`, `--success`/`--warning`/`--danger` with their `-soft` steps, `--field-*`, `--border`, `--separator`) map onto them, so HeroUI components pick the palette up. Base text is 13px (`text-sm`), controls are 28px high with a 7px radius, cards use a 12px radius (`rounded-2xl`), and surfaces are separated by 1px hairlines: `--surface-shadow` is a hairline ring, there are no drop shadows except on overlays. A `@layer components` block resizes HeroUI buttons, toggle groups, tabs, inputs, cards and chips to this scale. Mono (`Geist Mono`, `.mono`) is for ids, hashes, versions, cron, paths and costs. Status colors are only for status; tags tint 11% of the color as background and 24% as border. The docs site's `landing.css` still has the old palette. The mascot and capability icons come from [@holtkeeper/brand](../../../packages/brand/docs/README.md) through `ui/BrandIcon.tsx`; `Page` takes an `icon` for capability pages.
- **Shell.** `features/shell/AppShell.tsx` is a 44px icon rail of workspaces (logo, workspaces, then documentation, theme, sign-out and account at the bottom) and a slim top bar with the workspace's pages as `SegmentedTabs`. Workspaces and their entries live in `features/shell/nav.ts`: Home, Repositories, Chat, Code, Delivery, Team, Ops and Admin, each entry with its route, an optional `tab` search parameter for entries that open one tab of a shared page, the action it `requires` (or a list, any of which will do), `global` when the server checks it globally, `catalog` for Dependencies, Public API and Stack (shown on `canCatalog`: a `catalog:read` or `analyses:read` grant, or any read grant while `/api/me`'s `crossTeam` level is not `off`, like the server's catalog check). The Admin workspace is the four Settings tabs. `visibleNav` filters by grants and that level, `groupByWorkspace` groups in rail order and drops empty workspaces, and a rail icon opens its workspace's first visible entry. `activeNav` picks the current entry: the one whose path is the page's or a parent of it, then the entry whose `tab` matches (else the one without a tab, else the first), and for `/analyses/$id` the page of the record's kind (`analysisPages`), so a report stays under **Bundles**, **Coverage** and so on. The active entry also sets the browser tab: the title becomes `<label> · Holtkeeper` and the favicon its `brand` icon (the mascot when it has none or no entry is active).
- **Shell components** (`ui/`). `FlowCanvas`: a read-only React Flow diagram in the Graphite style, generic over node kinds: callers pass nodes (`id`, `kind`, `data`, optional size) and edges (`from`, `to`, optional label, dashed, tone) as plain data (`lib/flow.ts`), a `render` function that draws a node box's inside per `kind`, and an optional `drawer` that returns a title and content (usually a form) for nodes that can be edited; clicking such a node opens it in a `SideSheet`, J/K step through the editable nodes. Layout is dagre left to right (`placeFlow`); nodes are never dragged or connected and no position is stored. `SegmentedTabs`: connected tabs, links or buttons, one current. `SideSheet`: a record opened from a list, docked right without a backdrop so the list stays visible, with a header of the mono id, title, "3 of 41" position and previous/next/close buttons; J and K call `onNext`/`onPrevious`, Escape calls `onClose`, except while typing in a field (`lib/sheet.ts`). `SegmentBar`: segmented progress sized by value with an empty remainder against `total`. `TickStrip`: equal status ticks, oldest first, `skipped` drawn neutral. `Tag`: a status tag in a `StatusTone` (default, accent, success, warning, danger, info, code), optionally with a dot or in mono. Progress uses segment bars and tick strips rather than spinners.
- **Access map.** The Users section (Settings → Access) switches between **List** and **Map**. The map (`features/users/AccessMap.tsx`, `lib/access-map.ts`) links each user to the scopes of their grants, captioned with the actions (`all actions`, `read only`, `n actions`; grants on the same scope are merged), and offers everything and every config group as scopes. With `users:write`, dragging a user onto a scope adds a `repos:read` + `audits:read` grant there (`withGrant`), the × on a highlighted link drops the user's grants on that scope (`withoutGrant`; never on your own links, so nobody locks themselves out), and clicking a user opens the user dialog for exact actions.
- **People.** Users appear with their generated avatar (`ui/Avatar.tsx`, initials when the image fails) in the rail, the users list and History, which resolves actor ids through the `people` map of `/api/history`. The account page rerolls the avatar (`PUT /api/me/avatar`).
- **Color.** Severity colors (`--sev-*`) and the categorical series (`--series-*`) are built from the Graphite status colors, with their own light and dark steps in `app.css`; `statusColor` in `ui/colors.ts` maps a `StatusTone` to its CSS color. Severity always comes with a text label, never color alone; languages keep a stable color slot everywhere.
- **Audit reports.** Findings go through TanStack Table for filtering (severity, language, package manager, free-text) and sorting, then are grouped Language → package manager → source file → package with `sourceInfo`, so every ecosystem renders the same way.
- **Motion.** Pages fade in, lists animate layout changes, headline numbers count up; Motion honours `prefers-reduced-motion`.
- **Keyboard.** Every control is a React Aria component or a native element; `/` focuses the findings search, a skip link jumps to content, Escape closes dialogs and side sheets, J/K step through records in a side sheet.
