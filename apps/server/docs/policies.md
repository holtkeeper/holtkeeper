# Policies

Part of the [@holtkeeper/server](README.md) docs.

Server side of Settings › Policies: policy drafts saved as one change, the license policy, the allowlist rules and the commit convention check. Setting resolution and the allowlist rules live in `setting-rules.ts`.

## `POST /api/settings/draft`

`PolicyDraftInput { changes }`, 1 to 50 changes, each `{ op: 'put', id?, key, scope, value }` or `{ op: 'remove', id }`. Every change is checked first, exactly as `PUT /api/settings` and `DELETE /api/settings/:id` check one (known, non-retired key; `global` keys only for everything; `settings:write` on the new and the stored scope; the key's schema; the allowlist rules below), and nothing is stored unless all pass: 400, 403 or 404 for the first that fails. A draft may change each entry once (400 otherwise) and may not hold secret settings (400: save those on their own). Then puts are stored, removals deleted, and one audit event `setting.draft` is written: target the first saved (or removed) entry, `changes` of every entry with fields prefixed `<key>#<id>.`, details `{ keys, saved, removed }`. Home lists it as "Saved N setting changes at once". Answers `PolicyDraftResult { saved: SettingView[], removed: string[] }`.

## Allowlist rules

`audit.allowlistPolicy` (`{ maxDays?, requireReason }`, default `{ requireReason: true }`) limits `audit.allowlist` entries. The policy that governs entries stored with a scope is the strictest combination of every `audit.allowlistPolicy` entry whose scope contains that scope: the smallest `maxDays` and a required reason when any of them asks for one (`allowlistPolicyFor`). A narrower scope can tighten the organization's rules but never loosen them. A draft that also changes policies is checked against the stored policies plus the drafted ones, by the same rule.

- `PUT /api/settings` and `POST /api/settings/draft` check every allowlist entry that is new or whose reason or expiry changed (entries are matched by advisory and package): under `requireReason` a blank reason is refused; with `maxDays` the entry needs an expiry no later than today plus `maxDays`. 400 names the entry and the latest allowed day. Unchanged entries pass, so tightening the policy never blocks unrelated edits.
- `POST /api/audits/allowlist/renew` checks the renewed entry the same way. It takes an optional `reason` that replaces the stored one; the audit event's `changes` carry `expires` and `reason`.

## License policy

`analyzers.licenses` options are the `licenses` analyzer's (see [@holtkeeper/licenses](../../../packages/licenses/docs/README.md)), including `review`, `devDependencies` and `exceptions`. `GET /api/licenses` (and the `license_overview` tool) read the organization's entry, the newest scoped `{ all: true }` (`orgEntry`), and send `review`, `devDependencies` and `exceptions` along with the policy summary (`LicensePolicyRules`); repository rows count `excepted` packages.

## `POST /api/commit-conventions/check`

`CommitConventionsCheckInput { repo, message?, branch? }` (at least one of message and branch, else 400; `repo` as `forge:path` on a configured forge, else 400). Needs `analyses:read` on the repository, the same reach as the MCP tool. Reads the conventions through `commitConventionsReader` and checks them with `checkConventions`, the function `check_commit_message` uses. Answers `CommitConventionsCheckResult { ok, problems }`: each problem with `target`, `rule`, `message`, `severity` and `source`; `ok` when no problem is an `error`.

## Setting resolution for tools

`cascadeFor` and `applyingEntry` resolve a key for a repository as `GET /api/settings/resolve` does (most specific scope, then newest; `global` keys only from entries for everything). The MCP and chat tools that return settings use them: commit conventions and test id overrides in `tools/rules.ts`, the license policy in `tools/repos.ts` through `GET /api/licenses`'s overview.

## Repositories without tests

`repo.tests` (`{ expected, reason? }`, most specific entry wins; see [@holtkeeper/settings](../../../packages/settings/docs/README.md#repositories-without-tests)) marks repositories with no tests by design. `repo-tests.ts` reads it per call: `repoTestsFor(store, config)` gives `{ expected, reason? }`, `testsExpectedFor` its boolean, and `TEST_ANALYZERS` (`coverage`) names the analyzers it holds back. With tests off:

- `automaticJobReady` refuses coverage, so webhook, tag and push events and new repositories never queue it; freshness reads the same check once (`automaticJobBlocker`) and decides it `skip` with the reason `the repository has no tests by design` and `repoHealth` leaves coverage heads out of its `freshness` counts; the scheduler leaves it out through `skip`. Manual runs (Run job dialog, MCP `run_job`) still go ahead, and stored records stay readable.
- `GET /api/repos` sets `RepoSummary.noTests` (`{ reason? }`); `GET /api/coverage/repo` returns `tests` (`RepoCoverageTests`: `expected`, `reason`, the deciding entry's `scope` for callers with `settings:read` on that scope, and `configurable` for callers with `settings:write` on the scope `{ repos: ['forge:path'] }` and on the repository's own entry, plus for them `entryId`, the own entry scoped to exactly `forge:path` whether or not it decides, and `inherited`, what applies without it) whenever tests are off or the caller may change them. A forge-less path entry is never the own entry.
- Repository health gives coverage the neutral cell `No tests` with the reason (or `by design`), so Home, the Repos page and MCP `repo_health` / `fleet_health` never count it as failing; the hub overview card reads **No tests by design**.
- The Guide leaves out its `testing` sections and adds a General policy line; the Guide generator skips `testing`; AI reviews get `tests: false`; write tasks get the policy's `noTests` (no test checks, a prompt line); propagation verifies with `withoutTests`; `createTaskGroup` refuses kind `tests` with 409 `<forge:path> has no tests by design (repo.tests)`, which covers the MCP and chat task tools, and `assertMayRun` refuses the same when a `tests` group proposed earlier is approved or retried.
- Test ids (`analyzers.testids`) stay as they are.

## Analyzers turned off

`repo.analyzers` (`{ off, reason? }`, most specific entry wins as a whole; see [@holtkeeper/settings](../../../packages/settings/docs/README.md#analyzers-turned-off)) turns analyzers off on repositories they make no sense for. The server registers it with `repoAnalyzersDefinition(analyzers)` (in `jobs.ts`, next to `analyzerSettings`): `off` accepts the kinds of the repository-scope analyzers that run automatically (every one but `RUN_ONLY_ANALYZERS`), so `PUT /api/settings` and policy drafts refuse unknown kinds. `repo-analyzers.ts` reads it per call: `analyzerOffFor(store, config, repo, kind)` gives `{ reason? }` for an analyzer that is off. For such an analyzer:

- `automaticJobBlocker` answers `{ blocker: 'off', reason? }` (before `no-tests` and `options`) for repository jobs, so `automaticJobReady` keeps webhook, tag and push events, merge request, pipeline and note policy intents and new repositories from queuing it, and a reply in a review thread queues no `review` while `review` is off; freshness decides it `skip` with the reason `turned off: <reason>` (or `turned off for this repository`) whether or not it is due, reading the setting once per pass; the scheduler and a schedule's **Run now** leave it out through `automaticSkip`. Group jobs, manual runs (Run job dialog, MCP `run_job`) and stored records are unaffected.
- Repository health gives the cell that judges it (`security` for `audit`, `dependencies` for `renovate`, `coverage`, `bundles` for `bundle`, `ci` for `ci-jobs`, `licenses`) the neutral `Off` with the reason (or `OFF_FALLBACK`, `turned off for this repository`, the same text the overview card and freshness use), so it never counts as failing, and leaves its records out of `freshness`. The hub overview turns a card whose analyzers are all off into **Off** with the reason (Libraries needs both `depgraph` and `renovate` off; with only `renovate` off it keeps the graph, drops the update figures and reads **Updates off**). The `jobs` cell still counts failed jobs of an off analyzer until they age out of its window.
- With `audit` off, `GET /api/repos` leaves out `latestAudit` (the Security page's latest runs and the fleet strip's vulnerability figures), `GET /api/audits/findings` (and MCP findings) leave the repository out, `GET /api/dependencies` and `GET /api/dependencies/library` (Supply › Libraries) build advisories without its audit, MCP `evaluate_dependency` leaves its audit runs out (`auditOff` of the catalog context, through `analyzerOffFilter`), and Home's Needs attention drops its vulnerability item. Home also leaves the records of every off analyzer out of stale analyses.

## Merge request reviews off

`mergeRequests.comments` (`{ enabled, reason? }`, default on, most specific entry wins; see [@holtkeeper/settings](../../../packages/settings/docs/README.md#merge-request-reviews)) keeps Holtkeeper out of the merge requests of repositories whose teams do not want it. `mr-comments.ts` reads it per call: `commentsOffFor(store, config, repo)` gives `{ reason? }` while it is off. With it off:

- **No review.** The event dispatcher never queues a review analyzer (`isReviewAnalyzer`: the built-in `review` or the one `jobs.commands.review.analyzer` names), whatever asked for it: `jobs.onMergeRequest`, `jobs.onLabel`, policy `enqueue` intents, `/holtkeeper` commands and replies in review threads. `POST /api/jobs` refuses a manual review with 409 and the task tool `request_review` with a tool error. Reviews queued before the setting was turned off are canceled when a worker picks them up (`reviewCancelReason` as the worker's `cancelReason`), before the AI runs, with `merge request reviews are off` and the reason in their log.
- **Nothing posted.** `startManagedConfig` wraps every panel forge in `commentsOffDefinition` of [@holtkeeper/forge](../../../packages/forge/docs/README.md) after the `repo.freeze` guard: comments, reviews (all but a bare approval), thread replies, note edits and resolved threads on the repository's merge requests fail with `MergeRequestCommentsOffError` before they reach the forge, whichever path sends them (reviews, chat answers, policies). Merge request policies run with `commentsOff`, so their `comment` and `label` actions are `skipped` with `merge request comments are off` and `approve` approves without its summary; approve, merge, close, draft, reviewers, webhook and enqueue actions run as usual. Notes on the merge requests run policies and queue their intents but get no answer: commands and thread replies are ignored, though replies to Holtkeeper's earlier review threads are still learned from.
- **Own merge requests.** Merge requests Holtkeeper opens itself (write tasks, propagation, renovate, release candidates) are created and updated with their own title, description and labels; only notes on them are refused.
- No badge, label or warning shows anywhere: the repository simply gets no reviews. Default-branch analyses, schedules and freshness are not affected.

Unlike `repo.freeze`, which refuses every change through the forge and ignores merge request events, this only keeps reviews and comments off merge requests; a repository entry that is on lifts a group entry that is off.

## Tests

`test/policies.test.ts`: a draft over several keys with one audit event and its Home line, nothing stored when one change is refused or invalid, duplicate and unknown keys, allowlist rules on `PUT`, on a draft that changes the policy too and on renew, and the commit convention check with its permission and input errors. `test/repo-tests.test.ts` reads `repo.tests` with config groups; `freshness`, `new-repos`, `repo-health`, `repo-page`, `coverage`, `repos` and `tasks` tests cover each place it changes. `test/repo-analyzers.test.ts` covers `repo.analyzers` in `automaticJobBlocker`, `automaticSkip` with `planSchedule` and its definition, and writing analyzers left out of frozen repositories; `webhooks` and `webhook-policies` tests cover merge request events, thread replies and policy intents of merge requests and pipelines, `schedules` a run by hand; `freshness`, `repo-health`, `repo-page`, `repos`, `findings`, `home`, `dependencies` and `api-surface` (`evaluate_dependency`) tests cover its effects. `test/mr-comments.test.ts` covers `mergeRequests.comments`: review not queued on events and refused on manual runs, a policy comment skipped, a repository entry turning it back on, a queued review canceled at start, and the forge guard of managed forges.
