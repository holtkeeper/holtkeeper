# @holtkeeper/server

The web server: the JSON API for the UI and clients, the active auth provider's endpoints, the built web UI, and background credential rotation. Built on Hono over `Bun.serve`.

## Running

Add a `server` section to `holtkeeper.config.ts` and run `holtkeeper serve`. The file holds infrastructure only (see [@holtkeeper/core](../../../packages/core/docs/README.md#removed-keys)); forges, groups, triggers and settings are added in the panel:

```ts
import { passwordAuth } from '@holtkeeper/auth-password'
import { defineConfig, env } from '@holtkeeper/core'
import { sqliteStore } from '@holtkeeper/store-sqlite'

export default defineConfig({
  server: {
    auth: passwordAuth({
      password: env('HOLTKEEPER_PASSWORD'),
      sessionSecret: env('HOLTKEEPER_SESSION_SECRET'),
    }),
    store: sqliteStore({ path: 'holtkeeper.db' }),
    vaultKey: env('HOLTKEEPER_VAULT_KEY'),
    port: 7420,
  },
})
```

| Field                     | Default                                                                                                                                                                                                                                                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth`                    | required: `noAuth()`, `headerAuth()`, `passwordAuth()` or `usersAuth()`                                                                                                                                                                                                                                              |
| `store`                   | required: `sqliteStore()`, `postgresStore()` (several processes) or `memoryStore()`                                                                                                                                                                                                                                  |
| `vaultKey`                | required, at least 32 characters; seals credentials and secret settings                                                                                                                                                                                                                                              |
| `hostname`, `port`        | `127.0.0.1`, `7420`                                                                                                                                                                                                                                                                                                  |
| `webRoot`                 | `apps/web/dist`; without a built UI only the API is served                                                                                                                                                                                                                                                           |
| `rotationIntervalMinutes` | 60; `0` disables background rotation                                                                                                                                                                                                                                                                                 |
| `artifactsDir`            | `.holtkeeper/artifacts`; shorthand for `artifacts: { kind: 'fs', dir }`                                                                                                                                                                                                                                              |
| `artifacts`               | `{ kind: 'fs', dir, quotaBytes? }` or `{ kind: 's3', bucket, endpoint?, region?, accessKeyId, secretAccessKey, sessionToken?, prefix?, virtualHostedStyle?, quotaBytes? }` (secrets accept `env('NAME')`; `quotaBytes` is the space the operator declares, shown against usage in Settings › System, never enforced) |
| `retention`               | none; `{ days?, maxBytes? }` sweeps artifacts hourly (age first, then least recently used)                                                                                                                                                                                                                           |
| `databasePath`            | none; the SQLite file, so the storage overview can report its size                                                                                                                                                                                                                                                   |

## Structure

- `context.ts` — `ServerDeps` (config, auth, store, vault, credential service, setting definitions, clock) and helpers: `authorize`, `principalOf`, `repoTarget` (adds config groups to a repository), `groupLabeler` (names group keys in chat, agent and MCP text, see [Group titles](#group-titles)), `repoKey`, `readBody` and `readQuery` (zod validation of a body or the query string → 400 with the first problem), `ForbiddenException` and `ForbiddenToolError` (see [Refusals](#refusals)).
- `app.ts` — `createApp(deps)`: authenticates every request, mounts `/auth/<provider>/*` and the API routes, maps errors to `ApiError` (403: `ForbiddenError`). `GET /api/me` (`MeResponse`) answers the principal with its avatar, the auth info, the `access.crossTeam` level, `version` (`ServerDeps.version`, default the `HOLTKEEPER_VERSION` environment variable, left out when empty) `publicUrl` (`server.publicUrl` without a trailing slash, left out when not configured) and `groupTitles` (display titles of titled config groups the principal may know about, by key: all of them with global `settings:read`, otherwise the groups its grants name and the groups of repositories it holds a listing permission on, `reachableGroups` in `routes/repos.ts`; empty when signed out).
- `routes/` — one module per area: Home (`home.ts`), the Inbox (`inbox.ts`) and personal snoozes (`snoozes.ts`), audits, repositories (`repos.ts`), analyses, credentials, settings, jobs, knowledge, the Guide and families, webhooks, AI usage, the audit log behind Settings › Audit log (`audit.ts`), external accounts and avatars. Each checks permissions with `@holtkeeper/access` and filters lists to what the caller may see.
- `audit.ts` — the audit middleware, `appendAudit`, `diffChanges` and audit retention (see [Audit log](#audit-log)).
- `setting-rules.ts` — the shared setting resolver (routes, MCP tools) and the `audit.allowlistPolicy` rules that settings writes, policy drafts and allowlist renewals enforce (see [Policies](policies.md)).
- `web.ts` — static UI with SPA fallback and immutable caching for hashed assets.
- `agent.ts` — `settingsAgentFor` and `withServerDefaults`: the LLM agent per repository (see [Agents](#agents)).
- `libraries.ts` — the `libraries` setting, the library index leader duty and `serverLibraryDocs` (see [Libraries](#libraries)).
- `freshness.ts` — the `freshness` settings, the freshness sweeper leader duty and `freshnessStatus` (see [Freshness](#freshness)).
- `repo-health.ts` — `repoHealth`, `readHealthSources`: the health cells of a repository and every threshold they use (see [Repository health](#repository-health)).
- `findings.ts`, `licenses.ts`, `fleet-cache.ts` — `readFindings`, `licensesOverview` and `createFleetCache`: the Supply fleet tables, read from stored metrics, and the cache they share (see [Supply fleet tables](#supply-fleet-tables)).
- `coverage.ts`, `assets.ts`, `bundles.ts`, `reviews.ts`, `branches.ts`, `fleet-metrics.ts` — `coverageCards`, `assetsTable`, `bundlesRow`, `listReviews`, `branchesOverview` and `withCurrentMetrics`: the Quality fleet tables, read from stored metrics (see [Quality fleet tables](#quality-fleet-tables)).
- `managed.ts` — `startManagedConfig`: the `ConfigSource` over the file config and `store.config`, panel forges limited and guarded by `repo.freeze` (see [Managed configuration](#managed-configuration)).
- `limits.ts` — the shared `@holtkeeper/limits` limiter: limited forge `fetch`, job admission keys.
- `server.ts` — `startServer(config)`: builds deps from the config, starts rotation, logs provider start lines, listens.

Settings areas have their own pages: [People](people.md), [Integrations](integrations.md), [Analyzers](analyzers.md), [Policies](policies.md), [System](system.md), [Audit log](audit-log.md).

Everything a route needs comes through `ServerDeps`, so tests build the app with `memoryStore()` and any auth provider (see `test/app.test.ts`).

## Refusals

Every 403 under `/api` answers `ForbiddenError { error, missing: { action, target? } }` ([@holtkeeper/api](../../../packages/api/docs/README.md)). `authorize()` and every other permission check throw `ForbiddenException(action, target?, message?)`, which `onError` renders; `TaskError(403, message, missing)` becomes one in the task routes. `missing` holds only what the client sent: the action and, for a repository, its key (`forge:path`, for Guide scopes the repository of a `repo:` scope). It never names groups, and a repository that does not exist gets the same body as one the caller may not see (unknown forges still answer 400). Routes that load the repository from a stored record by id (jobs, analyses, audit runs, knowledge entries, learning candidates and the scope a candidate was accepted into) use `authorizeRecord()`, whose 403 names the action only, so an id never reveals its repository; an unknown id answers 404. Writes to a read-only repository (release steps) answer 403 with `releases:run` on that repository.

Refusals that are not about a permission use other statuses: an MCP token calling the token routes gets 401 (sign in instead), and a repository webhook delivery about another project gets 400.

MCP tools refuse a missing permission with `ForbiddenToolError(message, action, target?)` (or a `ForbiddenException` from shared code); the MCP adapter answers it as an error result whose text is the message and whose `structuredContent` is the same `ForbiddenError` body. Internal agents and chat get the message only.

`/auth/<provider>/*` answers are the provider's own. With `HOLTKEEPER_AUTH=users`, `GET /auth/users/link/:token` returns `LinkInfo` only for a live, unused link: who it is for and `grants: { count, role }` without scopes, group names or the issuer's name; a used or expired link answers 410 with `{ error, state, at }` only (see [@holtkeeper/auth-users](../../../packages/auth-users/docs/README.md)).

## Agents

`agent.ts` builds the LLM agent jobs get (`settingsAgentFor({ config, store, vault, now?, runner?, onRun?, budgets?, log?, models? })`, the default `agentFor` of `startServer`). For a repository it reads the settings:

1. The global `llm.provider` (only its `{ all: true }` entry counts; `PUT /api/settings` refuses narrower scopes for it) set to the id or name of an AI provider credential (kind `anthropic`, `anthropic-compatible` or `ai-sdk`, scope covering the repository): the credential's secret is opened with the vault and `createAgent` from [@holtkeeper/agent](../../../packages/agent/docs/README.md#providers) builds the agent from its `kind`, `url` and `options`. A named credential that is missing, out of scope or has invalid options is logged and yields no agent.
2. `llm.provider` unset: no agent. API keys live only in credentials, never in settings.
3. The loop a task runs on follows `runtimeFor` of `@holtkeeper/agent`: with an `anthropic` or `anthropic-compatible` credential (direct Anthropic, or Waibee's Messages root) tool-loop tasks (reviews, thread replies, chat) run on the Claude Agent SDK unless the credential's stored probe (`capabilities.agentLoop`, see below) failed, then on the AI SDK tool loop; one-shots (`capabilities: []` and no toolsets: release notes, library digests, learning capture, Guide generation) run on the AI SDK, priced with the catalog's `anthropic` prices. `ai-sdk` credentials run everything on the AI SDK.
4. Models are not configurable. Tasks ask for a [model tier](../../../packages/agent/docs/README.md#model-tiers) (`fast`, `main`, `deep`), resolved with `resolveTierModels` against the credential's model listing (cached per credential for an hour in `models`, default `modelCatalog()`); a tier whose family the provider does not list runs on the nearest listed tier (logged once per credential version); a provider that lists no Claude model at all is logged and yields no agent. Runs of one credential share its `maxConcurrency`.

`GET /api/credentials/:id/models` (`credentials:read`) lists an AI provider credential's models with prices (`listProviderModels`, 15 s timeout); a provider API failure comes back as `error` next to the configured models.

`ai-sdk` credentials (see [@holtkeeper/agent](../../../packages/agent/docs/README.md#ai-sdk-adapter)) use the models.dev catalog (`ServerOptions.aiCatalog`, default `modelsDevCatalog()`) with the catalogs of the config's `ai.providers` plugins added ([provider plugins](../../../packages/agent/docs/README.md#provider-plugins); credentials may name their packages): `GET /api/ai/providers` lists the providers Holtkeeper can talk to and the AI SDK packages (shipped and plugins') a provider of your own can use (any signed-in caller; a catalog that cannot load comes back as `error`), `GET /api/ai/providers/:id/models` one provider's models. Their credential models come from the catalog, catalog prices price their runs (a credential's `pricing` wins), and `POST /api/credentials/:id/test { model? }` (`credentials:write`) asks the model (default the `main` tier model of the credential's listing) for a one-word reply: `CredentialTestResult { ok, model, reply?, latencyMs?, error?, capabilities? }`. For `anthropic` and `anthropic-compatible` credentials the test is the agent-loop probe instead (`probeAgentLoop`: one tiny Messages request with a tool, a cache breakpoint and `tool_choice: auto`, 30 s timeout); its outcome is stored on the credential as `capabilities: { agentLoop: 'ok' | 'failed', checkedAt, error? }` (`setCapabilities`) and returned when it is conclusive (a successful answer, or a 400 rejecting the request); transport errors, timeouts, 401/403, 429 and 5xx are only reported, and the stored result stays as it was. A credential never probed counts as `unknown` and runs tool loops on the Claude Agent SDK; changing its URL, secret, kind or options clears the result, so re-test after editing.

The agent is wrapped by `withServerDefaults(agent, options)`, so every task gets:

- the toolsets its task kind mounts (`taskToolsets` in `tools/registry.ts`; tool schemas cost prompt tokens): every task gets `code` (`codeTools`), `docs` (`docsTools`, with the job's runner when the caller passes `{ runner }` as second argument of `agentFor`, else `runner`), `knowledge` (`knowledgeTools(knowledgeAccess({ store, autoAccept }))` for the repository and the task's kind, `autoAccept` from the scoped `knowledge.autoAccept`; the review analyzer's own knowledge access resolves it the same way) and `libraries` (below); `review` tasks (reviews and thread replies) also get `catalog`, the toolset of the [tool registry](#public-api-catalog-and-mcp) with `package_usage`, `find_usages`, `upgrade_impact`, `evaluate_dependency`, `who_uses` and the API tools, so a review can ask how other repositories use an internal API, and `stack` (`stack_usage`, `repo_stack`), within the [cross-team catalog](#cross-team-catalog) policy, and `assets` (`asset_policy`, `repo_assets`, see [Assets](#assets)), so a review can check new images against the policy. A task toolset with the same name wins;
- the repository's [Guide](../../../packages/guide/docs/README.md) for the task kind as `context` (`createGuideResolver`: team rules of the repository, its family, groups and `all`, learnings, policies, generated text, then knowledge notes within `agent.tools.knowledgeTokens`, default 1500 tokens, `0` leaves notes out), unless the task brings its own `context`: the review and thread replies resolve the Guide themselves together with the repository's rules files (`guideFor` of the review analyzer), so they get no second copy;
- toolset `libraries` (`libraryTools` of [@holtkeeper/agent-tools](../../../packages/agent-tools/docs/README.md) over `serverLibraryDocs`, versions defaulting to the task repository's) when the store has `libraries` and `settingsAgentFor` gets `artifacts` (`startServer` passes its artifact store);
- the supply tools `security_findings` and `license_overview` in the `catalog` toolset for a chat answering a person, when `settingsAgentFor` gets `supply` (`startServer` passes `deps.supply`, the one `supplyToolsAccess(deps)` the HTTP routes and MCP use too), narrowed to that person; internal agents never get them;
- every tool result, task toolsets included, capped by `capToolsets` at `RESULT_CAPS` of `@holtkeeper/agent-tools` (about 4k tokens and 20 hits per call; `code` searches report at most 20 hits); no external MCP server is mounted (a task's own `mcpServers` still are);
- a JSONL transcript of every run that reached the provider (`createTranscript` of `@holtkeeper/agent`: start with runtime, model, tools, system prompt and prompt; model messages and tool calls; tool results cut at 4000 characters; the outcome with usage and cost), stored in the artifact store as `application/x-ndjson` tagged `{ kind: 'transcript', repo, taskKind, job? }` (`transcripts.ts`) when `settingsAgentFor` gets `artifacts`. The provider secret, rendered headers and well-known token shapes are redacted before a line is kept, and adapters never write their options or environment. The artifact id is `result.transcriptRef`, reported to `onRun` and stored on the AI usage record; failed runs keep theirs too. A failing artifact store is logged and never fails the run;
- a budget check (`budgetGuard` over `llm.budget`, the default $150 weekly budget when none is set): a run a `block` budget refuses throws `BudgetDeniedError`, an allowed run is capped at what the budget has left (`maxCostUsd`). Runs of jobs a person asked for (trigger `manual` or `command`) and of `ServerDeps.agentFor` (routes a person calls) are interactive and may spend the reserve; every other run is automatic, `ServerDeps.automaticAgentFor` (learning capture, actor `agent:learning`) included. Then an `onRun({ repo, taskKind, provider, providerKind, model, result | error, durationMs, at, actor?, analyzer?, jobId?, interactive?, subject?, transcriptRef? })` call after every run, denied ones included; `subject` (what the runs work on: a job's task title, merge request, version or ref, a chat thread's title) is stored on the usage record. The default `onRun` is `usageRecorder(store.aiUsage)` from [@holtkeeper/ai-usage](../../../packages/ai-usage/docs/README.md); `provider` is the credential's name (or `anthropic`), `model` the provider's model name of the task's tier. `onRun` failures are logged and never change the run's outcome.

Tasks without `taskKind` run as `agent`. `agentFor(repo, { runner, jobId, analyzer, actor })` accepts the job's details; the job engine currently passes only the repository.

## Public API catalog and MCP

`createApiSurface(deps)` (`routes/api-surface.ts`) serves the newest `api-surface` records ([@holtkeeper/api-surface](../../../packages/api-surface/docs/README.md)) to the UI and to agents. The catalog (`api-surface/catalog.ts`) indexes records without their data: the 20 newest are checked at most every 15 s, every record is relisted at most every 10 minutes (records of backfilled releases carry the release date, so they land anywhere in the list); both read `analyses.heads` and fetch data only of records not indexed yet, four at a time; record data is read on demand and the 48 most recent are kept parsed. Versions of a package are one per released version (the newest record of each) plus the newest default branch run as `head`; `latest` is the newest release.

A package is **removed** (`PublicApiPackageRemoval`) when at least two default branch runs of its repository since its newest record lack it; empty snapshots do not count, since they mean the extractor read nothing. `at` is the first such run, `renamedTo` the package that took its folder in the newest run, `movedTo` the readable repositories that still have it. Removed packages stay listed and resolvable with `removed` set; without `repo`, a package resolves in a repository that still has it. MCP answers about a removed package start with a warning not to use it in new code, and `list_packages` lists them last under their own heading.

- `GET /api/api-surface/packages?q=&repo=&kind=` — `PublicApiPackageList`: the newest version of every package in readable repositories, with `removed` on dropped ones, narrowed to one repository or to packages exporting a symbol kind; `facets` counts kinds, packages and repositories over the list before `repo` and `kind` apply.
- `GET /api/api-surface/package?name=&version=&repo=` — `PublicApiPackageDetail`; `version` is a version, a tag, a record id, `latest` (default) or `head`; exact versions prefer releases over `head`. `repo` picks one of several repositories with the same package name (`alsoIn`).
- `GET /api/api-surface/package.md?name=&version=&repo=&subpath=&docs=false` — the same as Markdown for agents (`renderPackage`).
- `GET /api/api-surface/diff?name=&from=&to=&repo=` — `PublicApiDiff`; `to` defaults to `latest`, `from` to the release before `to`.
- `GET /api/api-surface/search?q=&package=&repo=&subpath=&kind=&match=&limit=30` — `PublicApiSearchResult` over the newest record of each repository: exact names, prefixes, substrings, then doc comment text, at most `limit` (1–100) hits with `more` counting the rest. Each hit carries its `match` (`exact`, `prefix`, `part`, `doc`; `match=` keeps one, anything else answers 400), `subpath`, `importPath`, the release `ref` (absent for the default branch), `deprecated` and `removed`. `facets` counts kinds, packages, repositories, subpaths and match types over the hits before the facet filters apply, so the UI can show how many each value would leave.
- `GET /api/api-surface/symbol?package=&name=&subpath=&version=&repo=&limit=20` — `PublicApiSymbol`: one exported symbol in full (declaration, doc comment, `deprecated`, source location, import path, other subpaths exporting the name, `removed`) and its history over the recorded versions, newest first: where it was added, changed, deprecated or removed, at most `limit` entries (1–100, else 400) with `capped` when older versions were left out. 400 without `package` and `name`, 404 when no readable record has it. Answers are kept in the fleet cache while the catalog's records stay the same.
- `GET /api/api-surface/usages/package?name=` — `PackageUsageView`: every readable repository whose newest `usages` record uses the package, with versions, counts and the exports it uses (members and props, no sites), and the exports summed over them.
- `GET /api/api-surface/usages/sites?package=&export=&member=&prop=&kind=&repo=&limit=50` — `UsageSitesView`: kept sites with snippets (`findSites`), at most 200.
- `GET /api/api-surface/usages/repo?repo=forge:path` — `RepoUsageView`: the packages one repository uses; 404 without a readable record.
- `GET /api/api-surface/usages/published?repo=forge:path` — `PublishedPackagesView`: the packages the newest API records of that repository describe, each with the readable repositories using it and their uses and files, most used first; empty when the repository is not readable or has no API record.
- `GET /api/api-surface/usages/impact?package=&from=&to=&repo=` — `UpgradeImpactView`: the catalog's diff between two versions (as `/diff` resolves them) joined with the usage records (`upgradeImpact`), with the old version's declarations to find exports that use a changed type. Repositories whose versions are all at or above `to` are left out; with `to` on `head`, none are. 404 when there are no two versions.
- `POST /api/api-surface/rescan` — rereads every record now, usage records included.
- `GET|POST /api/api-surface/mcp/tokens`, `DELETE /api/api-surface/mcp/tokens/:id` — the caller's personal access tokens (`McpTokenList`, `CreateMcpTokenInput { name, expiresInDays = 90, scopes? }`, `scopes` any of `['release', 'tasks']` or absent → `CreateMcpTokenResult` with the secret once). Logged as `mcp.token.created` / `mcp.token.revoked`. Needs `Store.kv`; without it tokens are unavailable.
- `GET /api/api-surface/mcp/usage?days=30` (1–90) — `McpUsageOverview`: calls and failures per day, by tool, package and client, the 50 newest calls, `people` (calls, errors, last call, the 10 most used tools, packages and clients, calls and failures per day, home groups and unexpired token count per person: everyone for global `users:read`, else only the caller), `me` (the caller's own row) and `tokens` (calls per token of the caller's own tokens only).

The usage index (`api-surface/usages.ts`) keeps the newest `usages` record of every repository ([@holtkeeper/usages](../../../packages/usages/docs/README.md)), rereading it at most every 2 minutes (`newestRecords`: one record per repository) and reusing parsed data of records that did not change.

**Tokens** (`api-surface/tokens.ts`) are `hk_mcp_…` secrets of which only a SHA-256 is stored in `Store.kv` (`mcp:token:<hash>`, with the owner's list under `mcp:tokens:<principal>`). A token acts as its owner, cut down to `analyses:read`, `repos:read`, `audits:read`, `knowledge:read` and `releases:read`, plus `releases:run` when it was issued with the `release` scope and `tasks:run` with the `tasks` scope (`McpTokenScope`, both off by default; Account › Connect agents has a **Release steps** switch): for `users` accounts with the current grants of the user, and disabling the user or bumping its session version (sign out everywhere) revokes the token; for other providers with the grants at issue time. Tokens authenticate only `/mcp`, `GET /api/api-surface/*` and `GET /api/dependencies*`, and cannot issue or revoke tokens. `lastUsedAt` is written at most once an hour.

**MCP** — `POST /mcp` is a stateless Streamable HTTP endpoint (JSON responses, a fresh server per request, `@modelcontextprotocol/sdk`) authenticated by a token (`Authorization: Bearer hk_mcp_…`) or a signed-in session; anonymous requests get 401 with `WWW-Authenticate: Bearer`, `GET`/`DELETE` 405. Its read-only tools are `list_packages`, `get_package_api` (with `subpath` and `docs: false` for big packages), `search_symbols`, `get_symbol` (with the import statement), `list_versions` (with removed/changed/added counts between the newest versions), `diff_versions`, and over the usage index `package_usage` (who uses a package, versions, exports with props and members), `find_usages` (the code of the uses, narrowed by export, member, prop, kind or repository), `upgrade_impact` (what an upgrade breaks, with the affected code) and `repo_packages` (what one repository depends on, or which repositories have a record); `package_usage` and `find_usages` name each repository's team. `who_uses` (`tools/who-uses.ts`, `subject` as `npm:<name>`, `Go:<module>`, `tool:<name>` or a bare name tried as npm, Go, then a stack tool) answers teams → repositories → versions in one call, at most 40 rows: direct dependencies and imports from `fleetLibraryUses`, how many majors each is behind `libraries:latest` (internal packages: their own repository's version), or for a stack tool what `stack_usage` returns. `evaluate_dependency` (`tools/dependency.ts`) answers what the organization knows about a dependency before it is added or upgraded, from stored records only: whether it is an internal catalog package, the newest release (`libraries:latest`, else the library index), repositories in reach using it (`fleetLibraryUses` over `depgraph` and `usages`, with use counts, majors behind and each repository's team) and deprecations, advisories of the newest audit run of each repository the caller may read with `audits:read` (findings and allowlisted ones; the newest 1 000 runs are read; a `version` seen in a finding is marked), licenses from the newest `licenses` record of each readable repository with that repository's verdict, and with `repo` the verdict under `repo`'s policy when its scan does not list the package, the gzip share of every target of the newest `bundle` records that includes it (npm only), and accepted knowledge entries about the package (other teams' `shared` ones included). `commit_conventions` and `check_commit_message` (`tools/rules.ts`) answer for a repository the caller may read with `analyses:read` (`forge:path`). They use [@holtkeeper/commit-conventions](../../../packages/commit-conventions/docs/README.md) with the forge client of the config and the `commits.conventions` setting that applies to the repository. The rules are the setting, the forge's push rules, the commitlint config and the recent history of the default branch. `commit_conventions` takes `commits` (20–500, default 100). `check_commit_message` takes `message`, `branch` or both. A result is reused for 10 minutes per repository, commit count and setting version, and failed reads are not kept. The other `rules` tools: `repo_rules` (`repo`, optional `task` of `agent` (default), `review`, `chat`, `release-notes` and `section`) returns the resolved [Guide](../../../packages/guide/docs/README.md) from `createGuideResolver`, the same resolver internal agents use, without the repository's own rules files (the client has the checkout); it needs `knowledge:read` on the repository. `propose_rule_change` (`repo`, `section`, `rule` of at most 200 characters, `reason`, optional `scope` `repo`/`family`/`group`; not `readOnlyHint`) needs `knowledge:read` on the repository, like `propose_knowledge`, and only stores a `proposed` learning candidate through `proposeRule` with `proposal: { by, reason }` and no sources; people accept it in Knowledge › Learnings, a rule the repository already has a candidate for creates nothing, and a new one is logged as `learning.propose`. It never writes a Guide section. `test_ids` (`repo`, optional `path`: file, folder or component name, `limit`) and `suggest_test_ids` (`repo`, `file`, `content`: the file's text, saved or not) need `analyses:read`; they read the newest `testids` record and the `analyzers.testids` entry that applies (`testIdsReader`), learn the convention from the catalog with the team's overrides on top (`@holtkeeper/testids`), and `suggest_test_ids` runs `findUntaggedInText` with it, deterministic and without an LLM. The server instructions include "Call repo_rules before changing code in a repository". The knowledge tools (`tools/knowledge.ts`) check `knowledge:read` like `/api/knowledge`: `search_knowledge` (`subject` filters on an entry's subject) returns accepted, not superseded entries best first (with `repo`, entries whose scope covers it, which needs `knowledge:read` on the repository, plus shared entries when filtering by `package` or `subject`; otherwise entries of readable scopes and accepted `shared` entries within cross-team reach, which end with the owning team), bodies cut at 600 characters; `get_knowledge` returns one entry of any status in full; `propose_knowledge` (the one tool without `readOnlyHint`) needs `knowledge:read` on its `repo` and calls `proposeEntry` with the caller as author and actor, scoped to that repository, always `proposed` (`knowledge.autoAccept` applies to server agents only); duplicates create nothing and merge new evidence links. With the [library index](#libraries) there are also `library_versions`, `search_library_docs`, `read_library_doc`, `library_changes`, `search_library_issues` and `library_source` (over `serverLibraryDocs`; each takes an optional `repo` as `forge:path`, used for the default version only when the caller may read it; `usedBy` lists show readable repositories only; libraries no repository the caller may read uses answer as not indexed), and `get_package_api`, `list_versions`, `diff_versions` and `upgrade_impact` fall back to the indexed API of visible third-party packages the catalog does not know (`ecosystem: 'Go'` skips the catalog; the version defaults to what `repo` uses, else `latest`; `upgrade_impact` covers npm only). Library and API text from third-party packages is fenced as third-party data. Outputs over 80 000 characters are cut at a line break (`capText`) with a hint to narrow the request; a `ToolError` reaches the client as it is, other failures as `Failed: <message>`, and a missing permission also carries the `ForbiddenError` body as `structuredContent` (see [Refusals](#refusals)). Every call is counted (`api-surface/usage.ts`): daily counters under `mcp:usage:<date>` (kept 90 days) and the newest 200 calls under `mcp:recent`, buffered and merged every 5 s with `compareAndSet`; the client is the first word of the `User-Agent`. Per person and day a counter keeps calls, errors, the last call and full counts per tool, token and client (the token id comes from `tokenPrincipal` for bearer requests; the tool registry and each person's tokens keep these small), plus calls per package for the 200 most asked about, so a day key grows with people, not with calls. Nothing is cut at merge time below those bounds; the overview shows each person's 10 most used tools, packages and clients.

**Inbox decisions are not available through MCP.** No tool approves a proposed task group waiting in the Inbox, accepts or rejects proposed notes, learnings or generated Guide text, dismisses a release or renews an allowlist entry; those stay in the web UI and the REST endpoints (see [Inbox](#inbox)). The token-scoped tools above are separate: `start_task` with `run` approves only the group it just proposed, and `release_step` `accept` is a release step under the `release` token scope.

**Release tools** (`tools/releases.ts`, toolset `releases`, built per caller by `releaseToolsAccess` in `release-steps.ts` over the [release assistant](#release-assistant)): `release_rules` (`repo`) explains the flow in plain language from the resolved `releases` setting (branches, merge request or trunk flow, scheme and tag format, how the bump follows commit conventions, acceptance, gates, environments in order) followed by the Guide's `releases` and `commits` sections (`createGuideResolver` with task `release-notes`, no notes); `release_status` (`repo`) renders `ReleaseRepoView`: where it stands (`stageText`, the same sentence order as the Releases screen: forge error, failed deploy, "Waiting for acceptance" while the flow asks for one nobody gave, the pending step, a ready or running deploy), latest and next version with the bump reasons, unreleased and ahead counts, the candidate merge request, acceptance, the row's `blockers`, failing gates other than those blockers (non-blocking ones marked with their severity), the version on each environment (`row.environments`), deploy state per environment and the steps allowed next (`nextReleaseSteps`, which the chat `release` card uses too; Accept only when the caller's `can.accept` holds, i.e. `releases:run` and an acceptance waits); `release_changes` (`repo`, `from?`, `to?`: versions or tags; default latest version → target branch, with only `to` the version before it) renders tasks and the grouped changelog of the range (`ReleaseService.changes`, `rangeChanges` of @holtkeeper/release, cached for good between two tags), tasks with the tracker's title, type and status when a [tracker](#release-assistant) answers and the range ends at a version or the configured target or source branch (any other ref shows plain keys, so a pushed branch cannot read tickets through the credential), keys linked only when the tracker or `changelog.ticketUrl` gives a URL. They need `releases:read` on the repository. `release_step` (`repo`, `action` `propose`/`accept`/`version`/`deploy`, `environment?`, `tag?`, `override?`, `writeNotes?`, `note?`, `confirm?`; not `readOnlyHint`) is offered only to requests authenticated by an MCP token that has the `release` scope (never to signed-in sessions, even with a bearer header, or internal agents) and each call needs `releases:run` on a repository Holtkeeper may write to; a call refused for either is audited as `release.<action>` `denied`. Without `confirm` it previews (`previewReleaseStep`, shared with the chat confirmations): what the step does, failing gates, or why it is blocked (Accept is blocked unless `can.accept`: already accepted, or a flow without acceptance); `note` is the acceptance note for `accept` and the recorded reason for `deploy`; an unblocked preview stores a one-time token in `Store.kv` (`release:confirm:<token>`, 10 minutes) bound to the caller, the arguments and a SHA-256 of the release state the step depends on. The second call with the same arguments and the token takes it atomically (`compareAndSet`, so two concurrent calls run the step once) and runs the step through the release service with channel `mcp`, so it lands in the release history and the audit log (`release.<kind>`, `via: api`, `details.channel: mcp`); an unknown, expired, reused or mismatched token, or a release state that changed since the preview, is refused and audited as `release.<action>` with outcome `denied`, a failing step with `error`. The instructions add "Before releasing, call release_rules and release_status" and, with steps, "Never pass override to release_step unless the user asked."

**Supply tools** (`tools/repos.ts`, in the `catalog` toolset when the context has `supply`): `security_findings` (`repo?`, `severity?`, `status?` of `open`/`fixing`/`allowlisted`, `limit` ≤ 200, default 50) renders `readFindings` for the asker: severity counts, then one entry per advisory and package with aliases, status (and the fixing task), summary, fixed versions, first seen and a line per repository with versions, lockfiles and status; `license_overview` (`repo?`) renders `licensesOverview` for the asker: totals, the organization's policy, weekly deltas, violations, a row per repository and the license mix, or with `repo` only that repository's row and violations. Both answer exactly the groups and rows `GET /api/audits/findings` and `GET /api/licenses` answer the same principal, through the same `supplyToolsAccess(deps)(principal)` the endpoints answer from (`ServerDeps.supply`, else one built per `createApp` and passed to `auditRoutes`, `licensesRoutes` and `createApiSurface`), so HTTP, MCP and chat share one fleet cache per endpoint across askers. The license policy line appears only for askers with `settings:read` on the organization scope. MCP callers get them from `routes/api-surface.ts`; chat gets them for its asker through `agentCatalogContext`'s `supply` (internal agents without an asker never do).

**Tool registry** (`tools/`): the MCP tools are `defineTool` toolsets ([@holtkeeper/agent-tools](../../../packages/agent-tools/docs/README.md#registry)) shared with the internal agents: `catalog` (`catalogToolset`: the API, usage, `evaluate_dependency` and `who_uses` tools, plus `security_findings` and `license_overview` with `supply`), `stack` (`stackToolset` in `tools/stack.ts`, offered with stack access: `stack_usage` with `tool` and optional `version` or release line lists the repositories using a runtime, package manager, image or chart grouped by team with end-of-life status; `repo_stack` with `repo` lists one repository's runtimes and images, conventions status and its first 25 direct dependencies from the newest `depgraph` record; both read stored records only, built by `storedStackTools`), `knowledge` (`knowledgeToolset`), `rules` (`rulesToolset`: `repo_rules`, `propose_rule_change`, commit conventions, `test_ids`, `suggest_test_ids`, each part offered when its access is given), `assets` (`assetsToolset`), `libraries` (`libraryToolset`), `releases` (`releasesToolset`), `ops` (`opsToolset`) and `tasks` (`tasksToolset`, MCP only), each built per caller from a context that holds what the caller may read. `mcpToolsets` mounts them in that order (`stack` after `catalog`) (`rules` with any of its parts, `libraries` only with the library index) and `api-surface/mcp.ts` is the adapter: `registryServer` registers every tool under its name and input schema, `readOnlyHint` unless the tool sets `readOnly: false`, joins the toolsets' `instructions` into the server instructions and records each call with the tool's `subject`. MCP callers keep their grants: `canRead` is their catalog reach and `canReadSnippets` their snippet reach (see [Cross-team catalog](#cross-team-catalog)), audits need `audits:read`, knowledge `knowledge:read`. Internal agents get the `catalog` and `stack` toolsets through `agentCatalogContext` (reviews and chat mount both): without an asker, every repository's packages, usages, stack and shared notes while `access.crossTeam` is not `off` (usage snippets of other teams only under `snippets`), only repositories sharing a group with the task repository when it is `off`; audits and repository-scoped knowledge of the task repository only. The internal `knowledge` and `libraries` toolsets stay the task-scoped `knowledgeTools` and `libraryTools` of `@holtkeeper/agent-tools`. Chat replies mount `catalog` too, and `rules` through `agentRulesAccess`: `repo_rules` of other configured repositories that share a group or a family with the task's repository, without team notes (asking for the task's own repository is refused, its Guide is already the task's context; reviews do not mount `rules`) and `test_ids`/`suggest_test_ids` of any configured repository; no proposals and no commit conventions. Chat mounts the read-only `releases` toolset too (`agentReleaseAccess`): release state of the task's repository and of repositories sharing a group with it, never `release_step` and never who accepted, and the read-only `ops` toolset (`agentOpsAccess`): jobs of the same repositories and the AI budgets that cover the task's repository, the default one included (`taskToolsets` names what each task kind mounts). For chat every one of these, `agentCatalogContext` and `agentRulesAccess` included, is narrowed to the asking person's grants (see Agent replies).

**Asset tools** (`tools/assets.ts`, toolset `assets`, built by `storedAssetTools` over stored settings and records, never an analysis or an LLM): `asset_policy` (`repo`, optional `path`) renders the effective `assets.policy` as plain facts (`assetsPolicyFacts`) with the scope it comes from and, for a path, whether it is ignored, allowed, its size limits, the dimension limit and the siblings it needs (`pathFacts`); `repo_assets` (`repo`, `severity` `error`/`warning` (default)/`all`) renders the newest assets record's summary: totals per kind, errors and warnings, budgets and up to 30 files with size, problems and the best conversion. Both need `analyses:read` on the repository for MCP callers and chat askers; reviews read their own repository and repositories sharing a group with it. The instructions add "Before adding or changing images, fonts, audio or video in a repository, call asset_policy".

**Ops tools** (`tools/ops.ts`, toolset `ops`, built per caller by `opsToolsAccess` in `ops-tools.ts`): `jobs` (`repo?`, `analyzer?`, `status?`, `trigger?`, `signature?`, `limit` ≤ 30, default 15) lists readable jobs newest first, one line each with status (blocked jobs with the budget's reason), analyzer, target, ref, trigger and schedule, created, duration, attempts and the failure signature; `job_log` (`job`, `attempt?`, `tail` ≤ 300, default 120, `grep?` over the last 300 lines) renders the attempt's steps as an outline with their outcome and duration, then the tail as `n time [step] text` lines in a fence marked as data; `queue_stats` renders `jobStats` for the caller, the same numbers as `GET /api/jobs/stats` narrowed the same way (workers only for MCP callers with global `analyses:read`, never for chat agents; the spend line only for MCP callers with AI read access); `why_job` (`job`) renders `explainJob`: origin (a freshness job's reason included), outcome, and for queued jobs the wait reasons and the due jobs ahead; `analysis_status` (`repo`, `forge:path` or `forge:<group>`) renders, for a repository, its [health](#repository-health) with only the cells the caller may read (the release cell needs the stored release cards, which `routes/api-surface.ts` and the chat setup in `server.ts` pass as `releaseCards`; security also reads the newest audit runs), then `freshnessStatus` per analyzer: state and reason, refresh class, last run, record sha vs the head freshness last saw, next eligible time and whether the sweeper would queue it now; `fleet_health` (`group?`, `health?`, `query?`, `limit` ≤ 200, default 50; offered with fleet access) lists every repository the caller may see in the configured groups, worst first, with the same `health`, readable `cells`, freshness and updates as `GET /api/repos`; the coverage and CI cells of both read the same stored `coverage` and `ci-jobs` metrics as `GET /api/coverage` and `GET /api/ci`; `budget_status` (offered only with budget access) lists this week's budgets with scope, spend, limit, reserve, projection and whether they block. None of them names who requested a job. MCP callers (`principalOpsAccess`) read jobs they may `analyses:read`, health cells they hold the permission of and, with any `ai:read`/`ai:admin` grant, the budgets whose scope those grants cover (the default budget with instance-wide `ai:read`); the instructions add "For a failing or stuck job, call why_job, then job_log".

**Task tools** (`tools/tasks.ts`, toolset `tasks`, MCP only, built per caller by `taskToolsAccess` in `tasks.ts`): `start_task` (`repos`, `title`, `prompt`, `kind` default `fix`, `run` default true; not `readOnlyHint`) proposes a task group with source `mcp` (the client's name) for the caller, who must see every target; with `run` it is approved at once only for a request authenticated by an MCP token with the `tasks` scope whose owner may run tasks on every target, otherwise it stays proposed and the answer says why (a person approves it in the panel). `task_status` (`id`: a group or task id) renders the group the caller may see: status, branch, spend, and per repository the task status, merge request, CI and errors, after refreshing open merge requests. `request_review` (`id`, `repo?`) queues a `review` job (`reviewOwn`, `force`, trigger `command`) for the merge request a task of the group opened; it needs the `tasks` scope and `tasks:run` on the repository.

Connect Claude Code with `claude mcp add --transport http holtkeeper <publicUrl>/mcp --header "Authorization: Bearer <token>"`; Account › Connect agents in the web UI shows the command, issues tokens, lists the tools and shows usage.

## Libraries

The third-party library index of [@holtkeeper/libraries](../../../packages/libraries/docs/README.md) (setup and use: [docs/libraries.md](../../../docs/libraries.md); design: [docs/library-docs.md](../../../docs/library-docs.md)) runs when the store has `libraries` and an artifact store is configured.

**Setting** `libraries` (section `Libraries`, `librariesSetting`): only the entry for **All repositories** counts; without one the index runs with the defaults (`librariesConfigFrom` answers them), so it is on out of the box and `enabled: false` turns it off; a stored value that does not parse turns it off too. Every field is optional: `enabled` (default `true` once the setting exists), `interval` (`1d`; `<n>m|h|d`, at least `1h`), `github` (ids or names of credentials whose secrets are GitHub tokens, a list; a single string counts as a list of one; unset: every credential of kind `github` (`githubReferences`), so adding one is enough; `[]`: anonymous), `digests` (`false`), and the indexer's `exclude`, `include`, `maxVersions`, `firstOfMajor`, `sources { repository, releases, issues, site }` and `graceDays`, defaulting to `defaultLibraryIndexSettings`.

**Uses** (`fleetLibraryUses`, also behind the Dependencies API): exact versions of the direct dependencies in the newest `depgraph` record of every repository (npm and Go, the resolved or selected version; `directDependencies`) and of the packages the code imports in the newest `usages` record (npm; local workspaces and `node:` imports left out). An `accept` filter limits which repositories contribute uses. Packages the fleet defines are internal: workspaces of any `depgraph` layer, versioned or not (`definedPackages`; Go modules also under their name without `/vN`), local `usages` packages and the API catalog's package names; `defined` keeps the highest version an internal package carries in its own repository. The index leaves internal packages to `api-surface`.

**Latest versions** (`latestVersions(kv)` of `@holtkeeper/libraries`, `libraries:latest` in `Store.kv`): each index run records the registry's newest release of every third-party library in use, indexed ones from the metadata it fetches anyway and excluded ones (`exclude` globs) from a registry lookup of their own, and drops libraries nothing uses any more. While indexing is off nothing is recorded. The Dependencies API reads latest only from here; "behind" has one definition, breaking releases behind it (`majorsBehind`: majors, and minors below 1.0).

**Duty** `startLibraryIndex(deps, log)` (scheduler leader): about 2 minutes after start, then on a 30 s poll whenever `interval` passed since the last run or a run was requested (now, or a debounced request whose time came), one run at a time; stop aborts a running run. A run (`runLibraryIndex`) calls `indexLibraries` with `npmRegistry()` and `goRegistry()` over the global `fetch` (Bun honors `HTTP(S)_PROXY`, so the egress proxy applies), the GitHub client over the tokens of the `github` credentials (`githubClientFor`: revealed through the credential service, unreadable ones logged and left out, `ETag`s cached in `Store.kv`, waiting up to 65 minutes for a rate limit reset and aborted with the run; MCP and agent clients wait at most 10 s), the default issue hook and `siteSource()` when `sources.site` is on; it stores the `LibraryIndexRun` (failures capped at 200) under `libraries:last-run` in `Store.kv` and logs a one-line summary. `requestLibraryIndex(kv)` sets `libraries:reindex` to `true`, which the leader picks up on its next poll. A new `usages` or `depgraph` record (a finished job's record through the worker's `onFinished`, or `POST /api/analyses`) calls `noteLibraryUses`, which sets it to `{ after }` 10 minutes ahead, moved again by every further record, so a batch of jobs leads to one run; an explicit request is never postponed. `libraries:running` (15-minute TTL, refreshed while running) answers `started: false` while a run is going.

**GitHub use** (`github-usage.ts`): every client `githubClientFor` builds (index runs, MCP, agents) reports its answers and waits (`GitHubClientOptions.onEvent`) to `githubUsageFor(kv)`, which counts requests, `304`s answered from the `ETag` cache, rate-limit answers and waits per UTC day, credential (`anonymous` without a token) and resource, buffers them and merges them every 5 s into `Store.kv` (`github:usage:<day>`, kept 90 days) with `compareAndSet`, so every process adds up.

**Visibility** (`libraryReader`, shared by the Dependencies routes and MCP; `visibleLibraries` wraps a `LibraryStore` so libraries a caller may not see do not exist for its reads): a library is visible when the caller may read (`analyses:read`) a repository that uses it; libraries no repository uses are visible with global `analyses:read`.

**Progress** (`library-progress.ts`): an index run writes `{ startedAt, total, done, library?, libraries?, waitingUntil?, updatedAt }` to `libraries:progress` from `indexLibraries`' `onProgress` and the GitHub client's waits, at most every 3 s and with a 15 minute expiry renewed on each write, and removes it when the run ends or is aborted, so any process can show it.

**Admin routes** for Settings › System (`routes/library-index.ts`, types in `@holtkeeper/api`):

- `GET /api/system/library-index?q=&ecosystem=` (global `settings:read`) — `LibraryIndexStatus`: every indexed library by ecosystem and name, `repos` counting its users, `versions` the ones in the matrix, `chunks` and `issues` (one `libraryStats` query), `failed` sources, `lastRun`, `enabled`, `progress` (the run going on now, from `libraries:progress`) and `coverage` (`librarySourceCoverage`: per source, how many matrix versions, or libraries for `issues` and `site`, are `ok`, `missing`, `failed`, `skipped` or not fetched yet).
- `GET /api/system/library-index/github?days=30` (global `settings:read`, `days` 1–90) — `GitHubTokenUsage`: every credential `libraries.github` names with its GitHub account and live limits (`githubTokenInfo`: `GET /user` and `GET /rate_limit`, which GitHub does not count, cached a minute per token), `duplicateOf` for a token of an account listed before, `error` for unreadable credentials or rejected tokens; requests per token and resource over the range, per UTC day by token, totals, and `capacity`, the live limits summed over distinct accounts.
- `POST /api/system/library-index/reindex` (global `analyses:run`) — `LibraryReindexResult`; 409 while the setting is off, 503 without `libraries` or `kv`.

**Answers** (`serverLibraryDocs`): `libraryDocs` with `libraryIssues` (live GitHub search cached in `Store.kv` for a day) and `sourceSnapshots` made on demand, the GitHub client resolved once per MCP request or agent. With `digests: true`, issue threads are digested by the agent of the caller repository (`ServerDeps.agentFor`; for MCP only when `repo` is given and readable, for agents the task's agent) in one turn without tools, task kind `library-digest`, so it counts against `llm.budget` and AI usage like other runs.

## Cross-team catalog

`catalog:read` (implied by `analyses:read`) covers derived facts about a repository: package and version inventory, public API, usages, stack and tool versions and `shared` knowledge entries; never findings, audits, jobs, releases or review output. The global setting `access.crossTeam` (`off`, `metadata`, `snippets`; default `snippets`) widens it: under `metadata` and `snippets` any principal with a read grant somewhere (`repos:read`, `analyses:read`, `catalog:read` or `*`) reads the catalog of every repository, MCP tokens included (`catalog:read` is a token action and reach is decided per request); `snippets` adds the code snippets of other teams' uses (`find_usages`, upgrade call sites). `visibility.ts` holds the checks: `canSeeCatalog`, `canSeeSnippets`, `canReadShared` (accepted `shared` knowledge entries), `catalogReach` (reads the policy once per request), and `scopeOwner`, the teams (config groups) an entry's scope names. Results carry the owner (`groups` on repositories, `owner` on knowledge entries and decisions) so the web UI folds other teams into a collapsed section; that is a UI default, not a permission. Chat replies follow the asker: their reach under the policy.

## Dependencies

The Supply › Libraries API (`routes/dependencies.ts`, mounted with the API catalog so it shares its usage index and catalog; helpers in `dependencies.ts`, types in `@holtkeeper/api`). Every answer is limited to the caller's catalog reach; analyzer results (licenses, bundles, Renovate merge requests) only come from repositories the caller may read with `analyses:read`, here and in `evaluate_dependency` (internal agents without an asker: the task's team). Answers read stored records, the library index and `libraries:latest` only: no forge, registry or model call on page load. Libraries are keyed `<ecosystem>:<name>`; Go modules join their library without the `/vN` suffix.

- `GET /api/dependencies` — `DependencyTable`: repositories (groups for team folding, the `depgraph` record, libraries used) and one row per library from `fleetLibraryUses`: users and versions, the version spread with breaking releases behind latest, latest (registry latest from `libraries:latest`; for internal packages the version in their own repository, or for Go modules, which carry none, the highest version any repository requires), `majorsBehind` and `reposBehind`, advisories from the stored `advisories` metrics (allowlisted ones included) of the newest main-line `audit` record of each repository the caller may read with `audits:read`, the same records `GET /api/audits/findings` reads (`auditHeadFindings`; distinct ids, worst severity), license expressions and the worst verdict from the stored `byPackage` metrics of the newest main-line `licenses` records, and Renovate's state from the stored `pending` metrics of the newest main-line `renovate` records (`broken` when an open Renovate merge request carrying an update of it has a failed pipeline or error, `open`, `none`; managers `npm`, `pnpm`, `yarn`, `bun` and `gomod`). The table reads no data of `licenses`, `renovate`, `audit` or `bundle` records (`auditHeadFindings`, `licenseStates`, `renovateStates` in `dependencies.ts`) and no audit runs; records stored before those metrics fields existed add no licenses or Renovate state until their next run. Internal packages are flagged `internal`, sorted last and left out of the third-party totals. The table is kept in the fleet cache under the ids of the newest `depgraph`, `usages`, `licenses`, `audit` and `renovate` records, the API catalog's records and the checked latest versions, together with which repositories the caller reaches through each predicate, so a repeat read with nothing new reads no record.
- `GET /api/dependencies/search?q=&limit=` — `DependencySearchResult`: libraries from the same uses whose name contains `q` (case-insensitive; 400 without it), name prefixes first, then by readable repositories using them, at most `limit` (default 10, at most 50); each hit is `{ ecosystem, name, internal, latest?, usedBy }` with no audits, licenses or Renovate joined. The ⌘K palette's library source.
- `GET /api/dependencies/library?ecosystem=&name=` — `DependencyDetail` (Overview and Docs): users with groups and versions, advisories (from the same `audit` metrics as the table), licenses per version with each policy's verdict, the gzip share of every measured bundle target (npm), accepted knowledge entries about the package (its `subject` or among its packages; readable by scope, applying to a readable repository that uses it, or another team's `shared` entry, flagged `shared` with its `owner`; superseded ones left out; people's entries before agents', newest first; never proposed ones), open Renovate merge requests, the versions the library index keeps and the documents of its newest indexed version. 404 when no readable repository uses it, the caller's library index does not know it and, for npm, no readable API catalog record defines it (an internal package only the catalog knows answers with no users); 400 for an ecosystem other than npm or Go.
- `GET /api/dependencies/api?ecosystem=&name=` — `DependencyApi` (API tab header): for an internal package the newest API catalog record defining it (`definedIn`: repository, release ref, analysis id), otherwise the library index's API at the newest indexed version; `api` counts exports and documented exports of that version and `subpaths` lists its entry points, `.` first. Without a recorded API both are empty; 404 when the library is neither in the catalog nor indexed nor used by a readable repository.
- `GET /api/dependencies/upgrade?ecosystem=&name=&from=&to=` — `DependencyUpgrade`: `from` defaults to the oldest version in use, `to` to latest. For third-party libraries, `library_changes` text in (from, to] and the diff of the two indexed APIs; for internal packages the API catalog's diff. npm uses the diff affects come from the usage index (`impactOfChanges` within snippet reach, repositories already on `to` left out). `notes` says why a part is missing.
- `GET /api/dependencies/docs?q=&ecosystem=&name=&version=&limit=20` — `LibrarySearchResult`: chunks of libraries a readable repository uses, `limit` at most 100.

## Supply fleet tables

Supply › Security, Supply › Licenses and the Libraries table read the newest record of each repository from stored `metrics` only (`latestHeadsWithMetrics`: `analyses.latestHeads`, with metrics computed once from data for a newest record stored without them); record data is read for a sheet or a detail, never for a table row.

- `GET /api/audits/findings?repo=` — `FindingsResponse` (`readFindings` in `findings.ts`): the findings of the newest main-line `audit` of every repository the caller may read audits of, one `FindingGroup` per advisory and package with the repositories it affects (versions, lockfiles), severity, fixed versions and `firstSeenAt`, which the audit metrics carry from record to record at ingest (the record time where none was stored); `severities` counts groups per severity. A repository is `fixing` while an approved, queued, running or `mr-open` `dependency-upgrade` task upgrades that package there (joined from `store.tasks` on every read, past the cache), `allowlisted` while every finding there is hidden by an `audit.allowlist` entry that has not expired, otherwise `open`; a group takes the status of its first repository (open, then fixing, then allowlisted). Worst severity first, then most repositories.
- `GET /api/licenses` — `LicensesOverview` (`licensesOverview` in `licenses.ts`, `routes/licenses.ts`): over the newest `licenses` record of every repository the caller may read analyses of, totals, the license mix, violations (denied, unlisted and unknown packages with versions, licenses, culprits and their repositories, from the stored `flaggedDetails` metrics; records stored before it have their metrics computed from data), a row per repository with counts per verdict and the license file state, the organization's `analyzers.licenses` policy with its matching preset and the number of narrower overrides (only for callers with `settings:read` on the organization scope, the check `GET /api/settings` applies to that entry), and `deltas` against each repository's main-line scan at least about a week older.

**Narrowing**: every fleet endpoint first lists the newest heads of all repositories, then keeps the ones the caller's grants allow with the endpoint's action (`canSee`: `audits:read` for findings, `analyses:read` for licenses, catalog reach for dependencies); totals, mixes, facets and deltas are computed only over what is kept, so a narrow grant never sees another team's counts. `?repo=` narrows further and never widens. The MCP and chat tools `security_findings` and `license_overview` call the same functions with the asker's principal (see [Public API catalog and MCP](#public-api-catalog-and-mcp)).

**Fleet cache** (`fleet-cache.ts`, `createFleetCache`): each fleet endpoint keeps its answer per endpoint key (with every parameter that changes it, the licenses policy entries and whether the caller may read them included) and set of visible repositories, valid while the set of newest analysis ids it was computed from stays the same; one entry per endpoint and visibility, at most 200 entries overall, least recently used dropped first, failed loads not kept, concurrent reads sharing one load. A new record, a changed grant or a changed policy is a new key, so answers are never stale; data that changes without a new record (tasks for `fixing`, the allowlist expiry against today) is joined after the cache. The cache lives in the process: each web replica keeps its own.

## Quality fleet tables

Quality › Bundles, CI, Assets, Reviews and Branches read stored `metrics` only, like the [Supply fleet tables](#supply-fleet-tables): record data is read for a sheet or a detail, and for a newest record stored before its metrics existed, never for a table row. Every endpoint narrows the same way (newest heads first, then `canSee` with `analyses:read`, totals over what is kept); Assets and Reviews also take `group` and `repo`, which narrow further and never widen. Every one except Reviews keeps its answers in its own `createFleetCache`, keyed on the newest analysis ids and the visible repositories. Coverage is described under [Coverage](#coverage).

- `GET /api/bundles` — `BundlesOverview` (`routes/bundles.ts`): a `BundlesRepoRow` for every readable repository with a `bundle` record, built from its newest main-line head (`latestHeadsWithMetrics`, so a newest head without metrics gets them computed from its data once) and the newest 20 heads of that line (`OVERVIEW_RECORDS` in `bundles.ts`, found among the newest 60 heads as `mainLineRecords`), so a run on another branch neither becomes the row nor joins the `series`. Per target: status, gzip, initial and delta of the newest measurement, `budget` and `verdict` from the current `budgets` option of `analyzers.bundle` (`bundleBudgetsFor` and `judgeTarget`, the rule the bundles health cell uses), `overBudget` and a `series` of the records read, oldest first; per repository the `failed` and `overBudget` counts and `records` read. Sorted by repository. The cache key holds the ids and update times of the `analyzers.bundle` entries, so a budget change is a new key.
- `GET /api/ci` — `CiOverview` (`routes/ci.ts`): a `CiRepoCard` for every readable repository whose newest main-line `ci-jobs` head (`latestHeadsWithMetrics`) saw a run in the last 30 days: pipelines, median and p90 pipeline time, success rate, week-over-week `change`, weekly medians, the problem-job count, `groups`, `status` (`CiStatus`), `flakyJobs` and `queueMedian`. Heads whose metrics predate `weeks` get them recomputed from their record's data (`withCurrentMetrics` in `fleet-metrics.ts`, stored fields kept). `releaseGate { pipeline, branch }` is joined after the cache, only on cards whose repository the caller may `releases:read` and only while releases are on for it: `pipeline` is the `gates.pipeline` of its resolved `releases` setting, `branch` the flow's target branch, else the card's `ref`. The `releases` entries are read only when a card qualifies.
- `GET /api/ci/jobs?repo=&limit=` — `CiJobsView`: the jobs of the repository's newest `ci-jobs` record (`ciJobTable` of [@holtkeeper/ci-jobs](../../../packages/ci-jobs/docs/README.md)): at most `limit` rows (default 50, capped at 200 as `CI_JOBS_MAX`; 400 like the Assets table's when not a positive integer), jobs with problems first, then the slowest; each row with `outcomes` of its final attempts (`success`, `failed`, `canceled`). `total` counts every job of the record and `outcomes` sums over all of them, rows left out included; `range` is the record's window and `ref` its branch option. 404 without a record in the current format. The parsed data of the newest 20 records is kept in memory, keyed on the newest record id.
- `GET /api/ci/jobs/fleet?sort=&limit=` — `CiFleetJobsView`: the jobs of the newest `ci-jobs` record of every repository the caller may read, each with its `repo`, ranked by `sort` (`rankFleetJobs`): `slowest` (default; slowest median first), `unreliable` (only jobs that failed or passed on retry, highest failure rate first) or `slower` (only jobs whose median grew, most first). At most `limit` rows (default 50, capped at `CI_JOBS_MAX`); `total` counts every job the ranking kept and `repos` the records read. The rows are cached per set of newest records and visible repositories (`createFleetCache`), so page views re-read nothing until a new record lands. A bad `sort` or `limit` answers 400.
- `GET /api/assets?group=&repo=&status=&kind=&problem=&format=&sort=&cursor=&limit=` — `AssetsOverview` (`assetsTable` and `assetsPage` in `assets.ts`): over the newest main-line `assets` head of every readable repository (`latestHeadsWithMetrics`: a newest head stored without metrics gets them computed from its data once), `repos` summarizes every repository matching `group` and `repo`, largest first, each with `moreRows` counting the file rows its metrics left out (they keep 50), which no filter or `total` sees, and `items` are the file rows the metrics keep (`AssetsMetrics.rows`) that match the filters: `status` `policy` (a problem above `info`), `saving` or `any`, `kind`, `problem` (a rule), `format`. `sort` is `severity` (default, then size), `saving` or `size`; ties go by repository and path. Pages hold `limit` rows (default 50, at most 200); `cursor` is the previous page's `nextCursor`, present while rows remain; `total` counts every matching row. Unknown values, and a `repo` that is not `forge:path`, answer 400 with the first problem (`readQuery` in `context.ts`, the shape `readBody` uses). The cache keeps the whole sorted table per filter set; pages are cut from it.
- `GET /api/reviews?repo=&group=&verdict=&since=&before=&limit=` — `ReviewList` (`listReviews` in `reviews.ts`): review runs newest first from `review` heads created at or after `since` (default 30 days ago) and before `before`, rows from the stored `ReviewMetrics` (records without readable metrics are left out): merge request, mode, verdict, posted findings in total and per severity, threads resolved, `model`, `durationMs` and `guideScopes` (absent or empty for records stored before them) and `costUsd`. `limit` defaults to 50, at most 200; heads are read in pages of `limit + 1` and at most 1000 per request (`REVIEWS_SCAN`), so filtered-out rows cannot make a request read without bound. `nextBefore` is set whenever older rows may follow, also when the scan stopped first; `totals` sum the rows returned. The first page (no `before`) also carries `window`: reviews, per-verdict counts, findings in total and per severity, resolved threads and cost over every row the query matches in its window (`windowTotals`, heads read in pages of 200 up to `REVIEWS_SCAN`; `partial` when the scan stopped there). A bad query, and a `repo` that is not `forge:path`, answers 400 like the Assets table's.
- `GET /api/reviews/:id` — `ReviewDetail` (`reviewDetail`): the run's row, summary, reviewed head, source and target branch, every finding (posted ones and the ones the forge rejected, with the error) and the tokens used. 404 when the record is not a review, its data does not parse or the caller may not read its repository, so an id never reveals one.
- `GET /api/branches` — `BranchesOverview` (`branchesOverview` in `branches.ts`): a `BranchesRepoRow` for the newest main-line `branches` head of every readable repository (`latestHeadsWithMetrics`): counts by reason, `delta` of each count against the main-line record before it (found among the repository's newest 10 heads), up to 50 authors with branches to clean up and the 20 oldest branches worth deleting, with `more` counting the rest. Most to clean up first.

## Stack

`GET /api/stack` (`routes/stack.ts`) — `StackOverview`: the newest `stack` record of every config group, one `StackGroupView` per group with a repository in the caller's catalog reach, limited to those repositories (each with its config groups, for folding other teams). Views are built by `stackGroupViews` in `stack.ts`, which the `stack` tools share. Tools carry every use judged at the record's `checkedAt` (`lag`, `support`, release line, end-of-life date); convention results of repositories the caller may read with `analyses:read` carry the id of the suggested fix, which `POST /api/analyses/:analysisId/changes` turns into a merge request, and its per-file diff. For other repositories `problems` is only a count of the differences and a read `error` is generic, since problems quote values from the files; the `stack` tools quote them only where the caller has `analyses:read` (internal agents without an asker: the task's team). `changes` compares with the group's newest record at least a week older: uses that newly reached or left an ended or ending line, convention differences that appeared or were fixed. Reads stored records only.

Each `StackTool` carries `cycles`, the product's release lines (`cycle`, `releaseDate`, `eol` as a date or a boolean, `lts`, newest `latest`) as the lifecycle source listed them when the record was made; absent when none is known. The UI draws version lines and support from them without another lookup.

## Knowledge

`/api/knowledge` exposes the knowledge base of [@holtkeeper/knowledge](../../../packages/knowledge/docs/README.md):

- `GET /api/knowledge?status=&kind=&topic=&package=&subject=&scope=&q=&repo=&limit=` — `status`/`kind` take comma lists; `q` searches (full text, best first, with `score`), otherwise newest first. Without `repo`, entries of readable scopes plus accepted `shared` entries within cross-team reach. Every entry carries `owner` (`scopeOwner`). `people` names the users among authors and editors.
- `GET /api/knowledge/:id` — `{ entry, history }`; readable like the list. `history` is empty when only the shared path grants the read (no `knowledge:read` on the scope), so earlier team-only revisions stay hidden.
- `POST /api/knowledge` — a person's entry (`source: human`, `status` defaults to `accepted`); validated with `validateEntry`, 400 on broken rules. Without `visibility` or `subject`, `sharingDefaults` applies: a decision or convention about one package is `shared` with that package as its subject.
- `PUT /api/knowledge/:id` — replaces the content and bumps the version; needs write on both the old and the new scope; `version` in the body gives 409 when the entry changed since.
- `POST /api/knowledge/:id/accept|reject|archive` — status changes; accepting an entry that `supersedes` another archives that one (when the caller may write it).
- `DELETE /api/knowledge/:id`.

- `GET /api/knowledge/counts` — `KnowledgeCounts`: per Knowledge space key (the Guide scope keys) the Guide sections with human rules or generated text, live notes (proposed and accepted) as the space's Notes table lists them (`all`: every note the caller may read, as `GET /api/knowledge` returns it; a group: notes naming it; a family: notes naming any member; a repository: notes covering it, inherited ones included, for every repository the stored group listings, families, notes and learnings know) and proposed learning candidates for it. Only spaces whose scope the caller may read (the readable scopes narrow the result, never widen it); a space with nothing may be missing.

Changes are logged as `knowledge.created`, `knowledge.updated`, `knowledge.accepted`, `knowledge.rejected`, `knowledge.archived`, `knowledge.removed`.

## Guide

`routes/guides.ts` serves the [Guide](../../../packages/guide/docs/README.md): team rules per scope and section, stored in `store.guides`, and families in `store.families`. A scope is `all`, `group:<config group>`, `family:<id>` or `repo:<forge>:<path>`; sections are `general`, `review`, `testing`, `testids`, `assets`, `commits`, `releases`.

- `GET /api/guide?scope=` — `GuideScopeView`: every section of the scope (empty ones with version 0), a label, `canEdit` and `people` (users who edited rules or accepted generated text or learnings).
- `GET /api/guide/section?scope=&section=` — `GuideSectionDetail`: the section, its previous human layers newest first, `canEdit` and `people` (users who made them).
- `PUT /api/guide/section?scope=&section=` — `{ rules, steering?, version? }` replaces the human layer (a changed `rules` or `steering` makes a revision); `version` gives 409 when it changed since. Logged as `guide.update` with field-level changes; repository scopes name the repository.
- `POST /api/guide/section/restore?scope=&section=&version=` — makes a previous human layer current again (a new revision), logged as `guide.restore`.
- `POST /api/guide/section/accept?scope=repo:…&section=` — `{ inputHash? }` accepts the generated text waiting for a person (`proposal`, or a first `generated` layer nobody accepted): it becomes the accepted `generated` layer with `acceptedBy`/`acceptedAt`. 409 when nothing waits or `inputHash` is not the waiting text; 400 for other scopes. Needs `knowledge:write` on the repository, logged as `guide.accept`.
- `POST /api/guide/section/reject` — `GuideSectionRejectInput { scope, section, inputHash }` rejects the generated text waiting for a person in a repository section (other scopes: 400). The rejection is remembered in `Store.kv` per section with `inputHash`, `generatedAt`, who and when (503 without `kv`); it names that generated version and leaves the stored text alone, so later version history can show it. The waiting text no longer shows, and the `guide` job does not propose text from the same inputs again; changed inputs propose anew. 409 when nothing waits, when `inputHash` is not the waiting text, or when concurrent rejections kept it from landing. Needs `knowledge:write` on the repository; logged as `guide.reject` with `inputHash`, `generatedAt` and `model`. Answers the section.
- `POST /api/guide/regenerate?repo=` — `{ sections?, prompt? }` queues a manual `guide` job ([@holtkeeper/guide-generator](../../../packages/guide-generator/docs/README.md)) with `force: true`, so it calls the model even when the evidence did not change; `prompt` is a one-off extra prompt stored with the result. Needs `knowledge:write` and `analyses:run` on the repository; 409 without the analyzer. Answers the job (201), logged as `guide.regenerate`.
- `GET /api/guide/chain?repo=&section=` — `GuideChainView`: per section (only `section` when given) the numbered layers in exactly the order the agent reads them: repository files (`repo-file`), repository rules, family, groups (several, in config order), all repositories, learnings, policies, generated text (with its `version`, `proposed` while nobody accepted it), notes; each with kind, scope key, source label, text, characters and whether the budget cut it; plus the budget (`total` 12000, `human` 8000, `generated` 4000 and what is used; with `section`, that of the whole prompt of the section's task, e.g. every section a review reads) and warnings. Needs `knowledge:read` on the repository. The MCP knowledge and rules tools return the layers of the same chain in the same order.
- `GET /api/guide/repo-files?repo=` — `GuideRepoFilesView`: the repository's own rules files (`REVIEW.md`, `AGENTS.md`, …) at the default branch head (`sha`, when the forge reports it), with path, blob sha, characters and text, in the order the chain reads them; cached by sha. Needs `knowledge:read` on the repository.
- `GET /api/guide/generated/history?scope=&section=` — `GuideGeneratedHistory`: every generated text the section stored (`store.guides.generatedHistory`), newest version first, each marked `rejected` (its `inputHash` was rejected) and `current` (`generated` or `proposal`) when the section holds it now; `people` names who accepted. Needs `knowledge:read` on the scope.
- `GET /api/guide/preview?repo=&task=&section=` — `GuidePreview`: the text `createGuideResolver` gives a task (`review`, `chat`, `release-notes`, `agent`) of the repository, with blocks, warnings (e.g. repository rules too long) and the character budget. The repository's rules files (`REVIEW.md`, `AGENTS.md`, ...) are read from the forge at the default branch head, as for `/api/guide/chain`, and come first as the `repo-file` block; when the forge cannot be read they are left out with a warning.
- `GET /api/families`, `POST /api/families`, `PUT /api/families/:id`, `DELETE /api/families/:id` — families (`{ name, members }`, members `forge:path`, at least two, each in at most one family: 409 otherwise). Deleting a family drops its Guide sections and returns learnings accepted into it to `proposed`. The list shows only members the caller may `repos:read` and leaves out families with none. Logged as `family.create`, `family.update`, `family.delete`.

### Review learnings

Replies to Holtkeeper's review comments (and rules MCP clients propose with `propose_rule_change`) become learning candidates (`learnings.ts`, [@holtkeeper/guide](../../../packages/guide/docs/README.md#review-learnings)). When a reply in one of its review threads arrives (webhook or polling), the event dispatcher queues the thread reply job and, in the background, runs `captureReplyLearning`: replies `looksLikeFeedback` rejects stop there with no forge read and no LLM call; otherwise the merge request's URL is read for the source link and `captureLearning` runs one fast-tier call on `ServerDeps.automaticAgentFor` (not interactive, so it respects the budget reserve; task kind `learning`, which mounts no toolsets). The note is claimed first, so the same reply never makes two calls. When a merge request is seen closed or merged and a `review` record of it is stored (Holtkeeper reviewed it; otherwise no forge request at all), `harvestReactions` reads 👍/👎 (`listNoteReactions`) on every inline comment Holtkeeper posted and stores the counts under the comment's finding category; forges without reactions are skipped. No LLM is involved.

`routes/learnings.ts`:

- `GET /api/learnings?repo=&status=` — `LearningList`: candidates of repositories the caller has `knowledge:read` on, newest first; `status` is a comma-separated list of `proposed`, `accepted`, `rejected`. Each carries `canDecide` (`knowledge:write` on its repository) and `scopes`, the scope keys of its repository the caller may edit (repository, family, groups, `all`); `people` names the users who proposed (`propose_rule_change`), decided or edited them.
- `POST /api/learnings/:id/accept` — `{ scope?, rule?, section? }` accepts the candidate (edited first when `rule` or `section` is given) into that scope's learnings, by default the scope its `suggestedScope` points at (the repository, its family, its first group; 400 when the repository has none). The scope must apply to the repository (400) and the caller needs `knowledge:write` on the repository plus edit rights on the scope (`settings:write` for `all`, groups and families); accepting again moves the rule. Logged as `learning.accept`.
- `PATCH /api/learnings/:id` — `{ rule?, section?, suggestedScope? }`; an accepted candidate's Guide entry follows. 409 when the rule equals another candidate of the repository. Logged as `learning.update`.
- `POST /api/learnings/:id/reject` — rejects it; an accepted one leaves the Guide (needs edit rights on that scope). Logged as `learning.reject`.
- `POST /api/learnings/accept` — `AcceptLearningsInput { ids, scope? }` accepts several candidates, one after another through the same path as a single accept (no new store call), each into `scope` or its suggested scope. `AcceptLearningsResult { accepted, failed[{ id, error }] }` in the order given; `ids` holds 1–200 ids, duplicates dropped; a failing candidate (unknown or unreadable: `learning candidate not found`, no rights, scope not allowed) never stops the rest. Every accepted candidate gets its own `learning.accept` audit event; the request itself is audited as `learnings.accept` with counts, which Home leaves out.

Every candidate in `LearningList` carries `sourceKind` (`review-reply`: one reply; `mcp`: a direct proposal without replies; `merged`: several discussions, or a proposal plus replies) and `confidence` 1–5, computed from the sources only: 1, plus 1 each for at least 2 distinct discussions, at least 2 distinct authors, at least 2 distinct repositories and at least 3 distinct authors (reply authors and the proposer), capped at 5.

Edit rights on a family scope are checked against the family the scope names (every current member), never the repository's current family; a family that no longer exists denies.

- `GET /api/learnings/reactions?repo=` — `ReactionTotalsList`: 👍/👎 per finding category for a repository (`knowledge:read`), or over all repositories for a global `knowledge:read` grant.
- `GET /api/families/suggestions` — `suggestFamilies` over the newest `usages` record of every repository (direct dependencies without the repository's own packages) and the runtimes and package managers of the newest `stack` records, leaving out repositories already in a family and dismissed suggestions; only suggestions whose members the caller may edit.
- `POST /api/families/suggestions/dismiss` — `FamilySuggestionDismissInput { members }`: hides the suggestion with that member set (`suggestionKey`: sorted, any order) for everyone, kept in `Store.kv` under `families:dismissed-suggestions` (503 without one); a later suggestion with other members shows again. Needs `settings:write` on every member; 204, logged as `family.suggestion_dismiss`.

## AI usage

Agent runs recorded by [@holtkeeper/ai-usage](../../../packages/ai-usage/docs/README.md):

- `GET /api/ai/usage?from=&to=&repo=&group=&model=&provider=&taskKind=&feature=&analyzer=&origin=&outcome=&groupBy=` — `AiUsageBuckets`: aggregate buckets plus ungrouped totals. `feature` (`reviews`, `tasks`, `chat`, `knowledge` or `releases`, see `featureTaskKinds` of @holtkeeper/ai-usage) narrows to that feature's task kinds; anything else answers 400. `/api/ai/runs` takes the same filters. `groupBy` is a comma list of `day,week,month,repo,group,model,provider,taskKind,analyzer,origin`; `from` defaults to 30 days ago.
- `GET /api/ai/runs?…&before=&limit=` — `AiRunList`, newest first; `next` is the `before` of the next page. Records carry `jobId` / `analysisId` for links. `people` names the users behind the page's interactive runs (`peopleOf`), only for callers with `users:read` in some grant; others get no names and the web shows a short id.
- `GET /api/ai/overview?period=week|month|30d&groups=&feature=&origin=&model=&taskKind=` — `AiUsageOverview` (default `week`). `feature`, `origin`, `model` and `taskKind` narrow the totals, top lists and forecast like `groups=`; budgets, `automaticStopsAt` and `caps` ignore them and always show the real figures. It holds: totals and automatic spend of the period so far (`current`) against the same elapsed span of the period before (`comparison`: Monday 00:00 to the same weekday and time last week, the same days of the previous UTC month, or the 30 days before; `periodSpans` of @holtkeeper/ai-usage), the top 5 repositories, models, task kinds and analyzers by cost, the status of every readable `llm.budget` entry plus the default budget for callers who read everything when no global entry exists (spend and automatic spend this week, `weeklyUsd`, `reserveUsd`, `warnPercent`, %, `forecastUsd`, `automaticStopsAt`, the week's range), cache hit ratio (cache read tokens over all input tokens), error rate, `automaticStopsAt` of the broadest budget (`broadestBudget`) and `forecast`: this budget week's `spendForecast` over everything the overview covers, whatever the period. A forecast is the week's spend so far plus the mean spend of the same remaining span over the last 4 full weeks (weeks before the first recorded usage are skipped; without any, the week's pace so far is extended), and `forecast.days` splits the rest of the week by local day, today first (`perDay`). `caps` are the read-only spend caps fixed in code: a write task's default and highest cap (`DEFAULT_TASK_BUDGET_USD`, `MAX_TASK_BUDGET_USD` of @holtkeeper/write-task), a chat reply's cap (`CHAT_REPLY_LIMITS`) and the mean cost of the period's chat replies (task kind `chat`, denied runs left out) within what the caller may read. Unknown periods and features answer 400.
- `GET /api/ai/week?week=YYYY-MM-DD&groups=` — `AiWeekBreakdown`: one budget week (`week` is its Monday, default the current week; anything else answers 400) with totals and spend by task kind, analyzer (runs without one share the empty key) and provider, most expensive first (`weekBreakdown`).

## Home

`GET /api/home` (`routes/home.ts`, rules in `home.ts`) answers `HomeView`, Home in one read. It reads only stored data, never a forge, and keeps each answer per principal and grants for 30 seconds.

- `attention` — Needs attention, most urgent first, then newest (not-analysed repositories after the other low items): jobs that failed in the last 24 hours grouped by analyzer and `errorSignature`, or by analyzer and repository for failures without one (the item id is `failureSnoozeId` of `snoozes.ts`: `job-failures:<analyzer>:<signature>` or `job-failures:<analyzer>:<forge:path>`); jobs an AI budget stopped in the last 24 hours, by reason; critical and high vulnerabilities of each repository's latest audit (with the change since the audit before); `audit.allowlist` entries the caller may write that expired (`allowlist`) or expire within 7 days (`allowlist-expiring`), one per entry with its Inbox item id (`allowlistNotices` of `inbox.ts`, shared with the Inbox); releases waiting on a person (from the release overview snapshot, `ReleaseService.snapshot`, which never refreshes it); proposed learned rules per repository and proposed knowledge entries the caller may decide; repositories whose newest analysis of an existing analyzer is older than 14 days; repositories the caller may see (jobs, audits, release cards, analyses, exact group paths) and read analyses of that have no record at all (`not-analysed`). Every item names its repositories with their groups, a sentence and a panel path to act on it, built with [@holtkeeper/web-paths](../../../packages/web-paths/docs/README.md): releases the caller may decide (`can.run` with a head), learnings, knowledge proposals and allowlist entries open their Inbox item (`/inbox?item=<InboxItem.id>&kind=`; learnings and knowledge the oldest proposal).
- `action` — the one action of each item: `retry` (`analyzer`; the client re-queues the analyzer on every repository of the item) only for repository jobs when the caller holds `analyses:run` on each of them and the analyzer can be queued through `POST /api/jobs`; `review` for releases, learnings and knowledge that open the Inbox; `renew` for allowlist entries; `open` for the rest, with the item's page.
- `snoozed` — items whose id the caller snoozed (`/api/me/snoozes`) and whose snooze has not run out are kept and marked `snoozed: true`. Snoozes are read on every request, outside the 30-second cache, so a snooze shows at once. Allowlist items share their id with the Inbox, so a snooze covers both.
- `changes` — What changed: one row per audit log event of the last 7 days the caller may see that succeeded, newest first, at most 40, for the high-signal actions only (versions, proposals, acceptances, dismissals, deploys, setting changes, allowlist renewals, knowledge edits, accepted learned rules, Guide edits, accepts and rejections, new repositories, credential changes, invitations, sign-ups, recoveries, issued sign-in links and rejected agent tasks (`task.reject`, linking the group on Ops › Tasks); sign-ins and personal preferences are left out). Each row has one deterministic sentence without the actor's name, built only from whitelisted fields (the action, the repository path and short tokens of `details`: release `version`, `tag` and `environment`, setting `key`, allowlist `advisory`; never free text or changed values), the page that shows it, the time and the actor (`people` resolves users).
- `spend` — with `ai:read`: this week's spend of the readable budget covering the most (`broadestBudget`: a global one, else the least specific scope, the fullest among equals), its limit, reserve, `warnPercent`, action, `forecastUsd` and `automaticStopsAt` from the same forecast `/api/ai/overview` uses (no linear projection), and spend by task kind over the caller's readable usage.

Repository health is not part of Home: the web reads the `cells` of `/api/repos` for Fleet health and the worst repositories. Scoping to the viewer's teams happens in the UI, so one answer serves every scope position.

## Inbox

`GET /api/inbox` (`routes/inbox.ts`, rules in `inbox.ts`) answers `InboxFeed`: every decision the caller may make, from six sources: proposed task groups, proposed knowledge notes, learning candidates, generated Guide text waiting for a person that nobody rejected (`GuideStore.list()` filtered by `pendingGenerated`), releases that need a person and are not dismissed (from the release overview snapshot, never a forge; a card whose release state could not be read has no head to decide on and is not an Inbox item), and `audit.allowlist` entries that expire within 7 days or have expired. The raw sources are shared by every caller and reused for 30 seconds; the permission filter (see [Permissions per endpoint](#permissions-per-endpoint)) and the split into sections run on every request, so one caller's answer never leaks into another's. `mine` holds what the caller may decide inside their home groups (and items above every team), `teams` the rest; a caller without home groups gets everything in `mine`. Each section is oldest first, snoozed items stay with `snoozed: true`, and `people` resolves `proposedBy`.

`GET /api/inbox/count` answers `InboxCount` (`mine`, `teams`, `total`) without snoozed items. It reads the same stored sources and the caller's snoozes only, never a forge or `releases.overview`, and answers with an `ETag` (`Cache-Control: private, no-cache`); a matching `If-None-Match` gets 304.

Decisions go through each kind's own endpoint, and only the caller's own permission counts:

- task groups: approve or cancel (see [Agent tasks](#agent-tasks)); notes and learnings: accept or reject (see [Knowledge](#knowledge) and [Review learnings](#review-learnings));
- generated Guide text: `POST /api/guide/section/accept` or `POST /api/guide/section/reject` (see [Guide](#guide));
- releases: Accept (`POST /api/releases/accept`, offered when `ReleaseCard.can.accept`) or `POST /api/releases/dismiss` (see [Managed configuration](#managed-configuration));
- allowlist entries: `POST /api/audits/allowlist/renew` — `AllowlistRenewInput { settingId, advisory, package?, expires, reason? }` moves the expiry of one entry of an `audit.allowlist` setting entry (found by `advisory` and `package`; absent matches an entry without one) to `expires` (`YYYY-MM-DD`, not in the past: 400) and replaces its reason when `reason` is given. The renewed entry follows the governing `audit.allowlistPolicy` (`setting-rules.ts`): an expiry more than `maxDays` from today or a blank reason when `requireReason` is on answers 400 with the rule it breaks. Needs `settings:write` on the entry's scope. There is no optimistic locking: the setting value is rewritten, last write wins, like any setting write. 404 for an unknown setting or entry, 409 when the stored allowlist does not validate. Audited as `allowlist.renew` with the `expires` and `reason` changes. Answers the `SettingView`.

**Snoozes** (`snoozes.ts`, `routes/snoozes.ts`) are personal marks kept in `Store.kv` under `snooze:<principal>` (at most 500, the ones ending soonest dropped first): `GET /api/me/snoozes` lists the caller's snoozes that have not run out (`SnoozeList`, soonest to end first), `POST /api/me/snoozes` with `{ id, until }` (`until` in the future, else 400) snoozes a Home attention item or an Inbox item, replacing an earlier snooze of the same id, and `DELETE /api/me/snoozes?id=` ends one. Both writes answer the new `SnoozeList`; 409 when concurrent writes kept the change from landing, 503 for a store without `kv`. Snoozes are not decisions and are not audited.

Inbox decisions are not available through MCP (see [Public API catalog and MCP](#public-api-catalog-and-mcp)).

## Jobs and webhooks

`startServer` always starts a scheduler and a worker (`src/jobs.ts`, configured by `jobs` of the config file, with defaults when it has none; see [@holtkeeper/jobs](../../../packages/jobs/docs/README.md)) and stops them with the server. Pass the analyzers jobs may run as `ServerOptions.analyzers` and an `agentFor(repo)` for analyzers that use an LLM. Job outcomes stay on the job records (`blocked` when an AI budget refused or stopped the run); they are not audited. Schedules that name an analyzer the server does not have or have invalid options are skipped and logged.

Analyzer options per scope come from the setting `analyzers.<kind>` (section `Analyzers`; the panel edits them in a settings sheet on the page that owns the analyzer); `analyzerSettings(analyzers)` returns the definitions, with the analyzer's `presets` as setting presets. A value is a partial options object, validated field by field and stored without defaults; it overrides schedule options and is overridden by a manual job's own options. Analyzers in `RUN_ONLY_ANALYZERS` (`guide`) get no such setting: their options are set per run by their own endpoint.

Keys in `retiredSettingKeys` of [@holtkeeper/settings](../../../packages/settings/docs/README.md#retired-keys) are dropped everywhere: `GET /api/settings` lists neither their definitions nor their stored entries, `GET /api/settings/resolve` leaves them out and `PUT /api/settings` refuses them as unknown, so old rows never fail validation.

### Settings resolver

`POST /api/settings/draft` (`PolicyDraftInput`) saves several setting changes at once for Settings › Policies: it validates every change like `PUT /api/settings` first and stores nothing unless all pass, then writes one `setting.draft` audit event. `POST /api/commit-conventions/check` (`analyses:read` on the repository) checks a message, a branch name or both against the repository's commit conventions. Both are described in [policies.md](policies.md).

`GET /api/settings/resolve?repo=forge:path` or `?group=<id>` answers `ResolvedSettings` for the hub's and the group page's Settings tab: `settings` (the winner per key with an entry), `cascade` (every covering entry per key) and `rows`, one `ResolvedSettingRow` per defined key in definition order, built with `effectiveSettings`. A row carries the definition's `label` and `section` (the web groups rows by it), the winning `value`, its `source` and, with an entry, the next broader source it `replaces` (with its value; the definition's `default` when nothing broader covers the focus) and `overrides` (how many broader entries it beats). `source.layer` is `repo` when one of the entry's path patterns matches the repository, `group` when one of its groups does (`source.groups` names them), `org` for an entry covering everything and `default` without an entry. `analyzers.<kind>` stays one row whose entry applies whole, never merged field by field. Retired keys, keys without a definition, secret definitions and `releases.notify` (instance-wide webhooks) get no row; a `global` key only ever shows `org` or `default`.

A group focus stands for a member no narrower entry names: only entries covering everything or matching the group count (a group intersection such as `web + payments` does not), and their path patterns are ignored. An unknown group is 404, neither parameter 400. Writing overrides goes through `PUT /api/settings` and is audited there.

At startup the server seeds the defaults of a fresh install (`seedDefaultSettings` from [@holtkeeper/settings](../../../packages/settings/docs/README.md#defaults-on-a-fresh-install)) against every setting it knows, plus `defaultPolling` from [@holtkeeper/updates](../../../packages/updates/docs/README.md#setting) so polling is on everywhere; `ServerOptions.defaultSettings` replaces the values, `false` turns seeding off. Before loading the panel config it also seeds the default triggers (`seedDefaults` from [@holtkeeper/managed-config](../../../packages/managed-config/docs/README.md#defaults)) for the analyzers it has, and no schedule (see [Freshness](#freshness)); first, once per store, it deletes the schedules earlier releases seeded (`retireSeededSchedules`); `ServerOptions.defaultConfig` replaces them, `false` turns this off. `GET /api/settings` returns each definition's `presets` and `people`: name and avatar of the users among the entries' `updatedBy`, like `/api/history`.

### Agent tasks

Code changes go through task groups (`tasks.ts`, routes in `routes/tasks.ts`, stored in [`AgentTaskStore`](../../../packages/store/docs/README.md#agent-tasks)): one source, one or more target repositories, one [write task](../../../packages/write-task/docs/README.md) per repository on the shared branch `holtkeeper/<group id>-<slug>`. A group starts `proposed`; a person approves or cancels it.

- `POST /api/task-groups` (`AgentTaskGroupInput { kind?, title, prompt?, plan?, patch?, repos, run?, source? }`, `createTaskGroup`) proposes; the caller must see every target (`repos:read`, or catalog reach of another team's repository under `access.crossTeam`), and proposing a `patch` needs `canRunTask` on every target too (403 `ForbiddenError` naming the repository), since the patch runs before any agent. `source` takes every type but `chat` (400): only the chat panel sets chat sources, so a request cannot point a group at another thread's card. 400 for unknown repositories, more than `maxRepos` (default 10) or neither prompt nor patch. With `run: true` it is approved at once. Answers 201 `AgentTaskGroupView` (the group without its patch, derived `status`, tasks with their branch and `can: { retry, cancel }`, summed `costUsd`, `hasPatch`, and `can: { approve, cancel }` for the caller).
- `POST /api/task-groups/:id/approve` (`approveTaskGroup`) queues one `write-task` job per proposed task, moving each task from `proposed` to `approved` atomically first (`AgentTaskStore.transition`), so a double click or two approvals at once queue each task once (`maxAttempts` 1, `actor` the approver, options `taskId` = the group id, `task` = the task id, the kind mapped to the write task kind, `group` when there are several targets). The approver becomes every task's requester. Refused with 409 while the global setting `tasks.write` has `enabled: false` (the default), for read-only repositories, once the group's tasks spent or hold `perGroupUsd`, or when this week's AI spend of task kind `write-task` plus the budgets of other approved, queued and running tasks plus the new budgets would pass `weeklyUsd` (default $40), and with 403 unless `canRunTask`: `tasks:run` on the repository plus `repos:read` there, or, for another team's repository, catalog reach and a `tasks:run` grant that covers it (team grants never do, so it must name the repository or its group explicitly). Each job's budget is `perRepoUsd` (default $1.50), lowered so the group stays within `perGroupUsd` (default $5): what its tasks spent and still hold counts, so retries and added repositories get only what is left. A click approves as trigger `manual` and an MCP `start_task` as `command`, both interactive work for the [budget](#ai-usage) that may use the reserve; groups created by automation with another trigger run as automatic work (`budgetClass: automatic`, jobs with trigger `schedule`).
- A `propagate` run whose checks fail in some repositories proposes one `propagate-fix` group for them (`proposePropagateFixes`, injected into the analyzer as its `FixProposer`): proposer `analyzer:propagate`, source `{ type: 'propagate', group }`, automatic budget, each task with its own prompt (failing output, release notes) and the bump as its patch, so the write task tries `git apply -3` before its agent. Nothing runs until a person approves it in Ops › Tasks. While `tasks.write` is off nothing is proposed, and the rollout opens its `needs-attention` drafts instead.
- `POST /api/task-groups/:id/cancel` (`cancelTaskGroup`) cancels every task that has not opened a merge request or ended, and its job; the proposer may cancel their own group, anyone else needs `tasks:run` on every target. Open merge requests stay.
- `POST /api/task-groups/:id/reject` (`rejectTaskGroup`) is the Inbox and Tasks reject: a cancel of a group whose status is still `proposed` (409 otherwise), with the cancel's permissions, audited as `task.reject` (target `task-group`, with `repo` when the group has one target), which Home's What changed lists. Proposed groups never expire on their own.
- `POST /api/task-groups/:id/retry` (`retryTaskGroup`) runs every `failed` or `cancelled` task of the group that ran once and has no open merge request again, as `POST /api/tasks/:id/retry` does for one: the same checks (`tasks.write`, `canRunTask` on each target, read-only, the group and weekly caps) for all of them at once, so a refusal retries none; 409 when nothing can run again. Audited as `task.retry` on the group.
- `GET /api/task-groups/needs-approval` (`TaskApprovalCount { count }`, `countGroupsAwaitingApproval`) counts the groups the caller sees (`canSeeGroup`) with a task still `proposed`, reading only proposed tasks and their groups, for the Tasks tab badge.
- `POST /api/task-groups/:id/requests` (`{ repo, approve }`, `decideRepoRequest`) decides a repository a running task asked for (`request_repository`): approving adds a task for it, approved and queued at once when the group already was (`tasks:run` there); rejecting needs the same or being the proposer.
- `POST /api/tasks/:id/retry` (`retryTask`) runs a `failed` or `cancelled` task again as a new job on the same branch for the caller, under the same checks as approving; a task whose merge request is still open, or one that never ran (cancelled or rejected before approval: retrying is no approval), is refused (409). `POST /api/tasks/:id/cancel` cancels that one task and its job (`cancelTaskGroup` with a task id): its proposer, or `tasks:run` on its repository.
- `GET /api/write-tasks` (`WriteTasksStatus`): the `tasks.write` switch and caps, and the write pool read from `write-task` jobs (queued and running counts, when the oldest queued one was queued, when a worker last started one; `writePoolStatus`). `spentUsd` (this week's write task spend) needs global `ai:read` or `settings:read`, `pool.workers` (ids of workers running write tasks now) global `settings:read`. Everyone gets `pool.busyWorkers` (how many workers run write tasks now) and `pool.totalWorkers`, the live workers in the `workers` registry key (absent without a KV store). The registry does not record pools, so the total counts workers of every pool and an idle write pool and a missing one still look the same here until a task waits.
- `GET /api/task-groups?source=&repo=&limit=` (`AgentTaskGroupList`, with `people`: names and avatars of proposers, approvers, cancellers, requesters and deciders) and `GET /api/task-groups/:id` (`AgentTaskGroupDetail`, the same with `people`, the group's `patch` in full and `taskPatches` for tasks with their own, so approvers see what runs), `GET /api/tasks/:id`: groups the caller proposed or approved, or with a target they may `repos:read` (other teams' catalog reach does not cover tasks). Reading one group, and listing groups (only those on the page with an open merge request), first refreshes their open merge requests from the forge (`refreshTaskGroup`, at most once a minute per merge request): `getMergeRequest` for the state and head commit, the branch's latest pipeline for CI, and `getMergeRequestDiff` whenever the head commit moved, for the diffstat; merged makes the task `done`, closed `cancelled`. Each `AgentTaskView` carries `ci` (the open merge request's CI, `none` without one) and `diffstat` (`{ files, additions, deletions, source }`: the merge request's when read, else the task's or group's patch counted by `diffstatOf`), and each group `can: { approve, cancel, retry, reject }`.
- Task progress: the write-task analyzer's `onStart` calls `taskStarted`, which refuses a job no approved task queued (no stored task, another repository or group, another job's task, or a task no longer approved or queued), so a `write-task` job from anywhere else never runs, and marks the task `running`. The job engine's `onFinished` (also for jobs stale recovery fails after their worker died) calls `taskJobFinished`, which ignores jobs the task no longer runs and stores `mr-open` with the merge request, `done` when there was nothing to change (or a dry run), `failed`/`cancelled` otherwise, with the transcript; the job's cost (its AI usage records, whatever the outcome) is added to what earlier runs spent. Groups from a chat thread get their card rewritten in place (`syncTaskCard`) and a system message linking each new merge request or naming the failure.
- Audit events: `task.propose`, `task.run`, `task.approve`, `task.reject`, `task.cancel`, `task.retry`, `task.add_repo`, `task.reject_repo` (target `task-group`).

The server replaces the registry's `write-task` analyzer with one whose policy (`writeTaskPolicy`) reads `tasks.write`, `repo.freeze`, the config's `dryRun`, `jobs.execution.mode` (`host` refuses: checks run repository scripts) and this week's write task spend against `weeklyUsd` (reached: a budget stop) when each task starts, so turning the switch off or marking a repository read-only stops tasks still in the queue. A worker serving the `write` pool does not start in `host` mode. Events, merge request policies and note commands never queue `write-task` jobs. It reads the repository's commit conventions with `commitConventionsReader` (the `commits.conventions` setting, push rules, commitlint, history) and hands the agent's commands the egress proxy variables of `jobs.execution.egress`. Agent runs go through the same wrapper as every job agent (`withServerDefaults`: Guide context, the weekly budget, the transcript in the artifact store, an AI usage record with task kind `write-task`). Only workers of the `write` pool run the jobs (`serve --pool write`); `/api/jobs/:id/why` cannot tell that a write task waits for such a worker.

### Freshness

Analyses stay current without schedules: every analyzer declares `refresh` ([@holtkeeper/analyzer](../../../packages/analyzer/docs/README.md#freshness)), and a leader duty (`startFreshness`, a sweep one minute after taking the lead, then every five minutes; only with a key-value store) queues what is stale. `decideFreshness` of [@holtkeeper/jobs](../../../packages/jobs/docs/README.md#freshness) decides each analyzer on each listed repository (and each group, for group analyzers); `sweepFreshness` adds:

- **Heads.** `freshness:head:<forge:path>` holds the default-branch head (`{ sha, at, checkedAt }`; a new sha restarts the 30-minute debounce). Push webhooks and polled pushes set it at once; each sweep also reads up to 25 heads not checked for `headPollMinutes` (oldest first, one `headCommit` request each, skipping saturated credentials). A head that cannot be read (empty or inaccessible repository) is noted in `freshness:head-miss:<forge:path>` and tried again only after four times `headPollMinutes`.
- **Applicability and setup.** Analyzers whose options do not validate with the target's `analyzers.<kind>` setting (`automaticJobBlocker`, the same rule triggers use through `automaticJobReady`, which also yields the no-tests-by-design reason) or whose `appliesTo` says no (cached per head in `freshness:applies:*`) are skipped. An uncached `appliesTo` is read only while picking jobs under the hourly caps, stopping once they are full or the credential is saturated, so the first sweep does not read every repository. `refresh.paths` compares the record's commit with the head (`compareCommits`, memoized in `freshness:paths:*`); no matching file means fresh.
- **Budget.** Analyzers that may call an LLM (`needs.agent`) skip records without a sha (the first sweep after an upgrade queues none of them) and wait while automatic work reached the weekly budget minus its reserve (`budgetGuard`, `interactive: false`).
- **Caps.** At most `maxJobsPerHour` freshness jobs (default 10) and `maxAiJobsPerHour` of LLM analyzers (default 2) are created in any hour, longest-stale first (no record, then the oldest); the rest wait. A job already queued or running for the analyzer and target is never doubled, and a freshness job that failed holds the next try back by the analyzer's interval.
- **Jobs** get trigger `freshness` and the decision's `reason` (`sha 1a2b3c4 != head 5d6e7f8`, `cadence 7d elapsed`, `no record yet`), shown by `why_job` and the job's Why.

Settings (section `Automation`): `freshness` (scoped, one entry per team = config group) `{ mode: 'on' | 'off' | 'slower', factor }`, default on, `slower` multiplies every interval and cadence by `factor` (default 3); `freshness.sweep` (global) `{ maxJobsPerHour, maxAiJobsPerHour, nightWindow: { from, to }, headPollMinutes }`, night window default 01:00–07:00 in the instance time zone. `freshnessStatus(deps, target)` evaluates one target without queuing or reading heads, for the `analysis_status` tool. Each sweep also keeps its decisions per analyzer and target in `freshness:summary` (one day); `freshnessSummary(deps, visible)` sums them per team (every repository, and each config group of each repository) for `GET /api/automation/freshness`, the Freshness cards of Ops › Automation, with the next sweep five minutes after the last.

### GitLab webhook

Point a GitLab project or group webhook at `https://<server>/api/webhooks/gitlab` with the secret token set to `jobs.webhookSecret`, and enable the events you use: "Tag push events", "Merge request events", "Comments". The token is compared in constant time; without `webhookSecret` the endpoint answers 404, a wrong token 401. The server finds the configured `gitlab` forge whose `url` prefixes the project's URL (or the only one). Events that queue nothing are acknowledged with `{ enqueued: [], ignored: <reason> }`; malformed payloads of handled events get 400.

**New repositories** (`new-repos.ts`) — when a group listing of polling (scheduled or by hand) finds repositories that no stored listing of any group had, `jobs.onNewRepo` queues its analyzers for them once, with trigger `new-repo` and the audit event `repo.discover`. Only repository analyzers that are not `exclusive` (do not push, commit or open merge requests) are queued: `analyzers` when set, else every such analyzer, minus `exclude` (the default trigger so also runs `guide` once), limited to `groups`, to analyzers whose `appliesTo` matches and to ones whose options are valid with the repository's `analyzers.<kind>` setting. A group that never listed counts all its repositories as new, so a new group or a fresh install analyzes everything once; a repository moving between groups does not. The default `new-repo` trigger (`{ on: 'newRepo' }`) is seeded into the panel; delete it there, or set `jobs.onNewRepo` in the file, to change that. Repositories known before the trigger existed get the same jobs by hand: `POST /api/triggers/new-repo/run`. `GET /api/jobs/analyzers` marks analyzers that change repositories with `exclusive: true`.

**Push Hook** — a push to a branch queues `jobs.onPush.analyzers` (repo-scope only) with `ref` = the pushed commit, `{ branch }` as options and trigger `push`, when the branch matches one of `onPush.branches` (`Bun.Glob`; `*` stops at `/`, `**` does not) and the repository one of `onPush.groups`, if given. Queued jobs of the same analyzer and branch for an older commit are canceled first, so a burst of pushes runs once for the newest. Deleted branches, tag refs and pushes by the forge's bot username are ignored. Polling reports branch pushes the same way (`pushes` of the `polling` setting). Unlike other events, pushes to read-only repositories still queue their analyzers. Tag, push and merge request triggers leave out analyzers the server does not have (a stored trigger may still name a removed one) and analyzers whose options stay invalid with the repository's `analyzers.<kind>` setting; they and merge request policies also leave out analyzers marked `defaultBranchOnly` (`guide`) whenever the job would carry a ref. The webhook itself is unchanged. The hook's `before`, `project.default_branch` and the paths of its commits (when it lists all of them; GitLab sends at most 20) go into the event.

**Default-branch pushes** also record the pushed commit as the repository's head for [freshness](#freshness) (`noteDefaultBranchPush`; the default branch from the event, else `getRepository`); they queue nothing by themselves. Webhooks Holtkeeper registers subscribe to every event GitLab has (`webhookEvents` of `@holtkeeper/forge`); deliveries no trigger cares about are answered with `ignored` and queue nothing, so a new trigger never needs a new registration.

**Tag Push Hook** — queues `jobs.onTag.analyzers` for the repository with `ref` = the tag and trigger `tag` (for monorepo package tags such as `@scope/name@1.2.3` the tagged commit's sha, so every package one commit releases makes one job), only when the repository is in one of `onTag.groups`, if given. Group-scope analyzers are queued once per matching group without a ref. Jobs already queued for the same analyzer, repository and ref are skipped. Deleted tags are ignored.

**Merge Request Hook** — queues `jobs.onMergeRequest.analyzers` with options `{ mergeRequest: <iid> }`, `ref` = the head commit (`last_commit.id`) and trigger `webhook` when the merge request is opened, reopened or updated with new commits (`oldrev` present) or out of draft; other updates (title, description, approvals) are ignored. `actions` narrows that to some of `open`, `update`, `reopen`; drafts are skipped unless `draft: true`; `groups` limits repositories. Labels added in the event (`changes.labels`) queue `jobs.onLabel[<label>]`, drafts included. Group-scope analyzers are not queued from merge request events. Closed and merged merge requests are ignored.

**Note Hook** on merge requests:

- `/holtkeeper <command> [args]` on any line goes to the chat router (`chatFor`, see [Chat](#chat)) with the merge request as the conversation. `jobs.commands[<command>]` queues its `analyzer` with `{ mergeRequest: <iid>, ...options }`, `ref` = the head commit and trigger `command`, so its agent runs count as interactive for the AI budget. Arguments `key=value` set options by name, `--flag` sets `flag: true`, the others fill the `args` option names in order, the last name taking the rest as a list (`lint: { analyzer: 'widget-lint', args: ['targets'] }` turns `/holtkeeper lint web api` into `targets: ['web', 'api']`); double quotes keep spaces. Options are validated against the analyzer before queueing; a command whose analyzer the server does not have (a leftover of a retired one) is not offered, and events never queue unknown analyzers. Anyone who can comment on the merge request can run these. The built-in `release`, `verify` and `help` are always there. Answers are a standalone note (not a resolvable thread), or a reply when the command was posted in a thread.
- A reply in a thread Holtkeeper started (first note by the forge's bot username or carrying its review marker, but not a chat note) queues `review` (or `jobs.commands.review.analyzer`) with `{ mergeRequest, replyTo: <discussion id> }` and trigger `command`, since a person asked, so it counts as interactive for the AI budget; the review analyzer answers that thread. This needs the forge's `listDiscussions`. The reply is also looked at for a lasting rule in the background ([Review learnings](#review-learnings)).
- A merge request seen closed or merged that Holtkeeper reviewed has the reactions on its review comments counted in the background ([Review learnings](#review-learnings)).

Events by the forge's bot username (`botUsername` of the panel forge, `jobs.botUsernames.<forge>` of the effective config) and notes carrying Holtkeeper's hidden markers (`<!-- holtkeeper:review ... -->`, `<!-- holtkeeper:chat -->`) are ignored, so the bot never answers itself. Jobs already queued or running for the same analyzer, repository, ref and options are skipped. Audit events: `job.command` and `chat.command` (built-in commands that ran), with the note's author as actor, and `mr_policy.<status>` for every policy outcome; queued jobs themselves are not audited.

**Agent replies** (`chatReplies`): one reply per thread at a time across processes (a trigger during a reply runs one more afterwards). A process first takes the thread's reply claim (`claimReply`, stale after 10 minutes, `STALE_REPLY_MS`) and waits for it while another process replies; it releases it when done. The agent comes from `ServerDeps.chatAgentFor(target, { actor, interactive: true, requester, subject })` (`subject` the thread's title), the settings agent in production, so every run is interactive work of the person who asked (it may use the budget reserve, and ai-usage records them as actor). `target` is the thread's repository, `chat:group/<name>` with that group, or `chat:team` with no groups for unscoped threads; the Guide, provider credential and toolsets follow it. The reply runs on tier `main`, `taskKind: 'chat'`, `maxTurns` 12, $0.40 (`CHAT_REPLY_LIMITS`), `capabilities: []` and no checkout; it mounts `knowledge` (search only, and only with the asker's `knowledge:read`), `libraries`, `catalog`, `rules`, `releases` (read-only) and `ops`, plus `propose_task` (`repos`, `title`, `summary` as the plan), which records up to three proposals; each becomes a task group (kind `chat`, source the thread, proposed by the asker, `createTaskGroup`) and a `task` card with the group id and its spend cap (`postTaskCard`), approved or cancelled from the card (see [Agent tasks](#agent-tasks)). A proposal the asker may not make (a repository they cannot see) leaves a cancelled card and a notice. The answer is stored with `costUsd`, `transcriptRef` and `toolTrace` (tool calls counted from the transcript). No agent, a weekly budget refusal, the per-reply cap or an error leave a system notice instead. The tools read only what both the thread's target and the asker may read (`requester`): catalog packages, usages and `test_ids` need the asker's `analyses:read`, audits `audits:read`, `repo_rules` and knowledge `knowledge:read`, release state `releases:read`, jobs `analyses:read` and budgets `ai:read`/`ai:admin` (the default budget only instance-wide). `release_status` never says who accepted a release.

**Thread titles** (`chat-titles.ts`, `chatTitles`): a thread created without a title is named from its first human message that is not a slash command, in the background after a post answers. Every ordinary post to a thread whose title is still pending starts a run (one per thread at a time in a process; slash commands start none), so a run lost to a restart is repaired by the next message. The message alone, anonymized like reply prompts and cut to 1,200 characters, goes between `<message>` tags as data (`<message>` tags inside it are removed) to a `fast` one-shot (`TITLE_SYSTEM`, one turn, $0.02, task kind `chat-summary` so it counts under Chat spend) as interactive work of the poster, recorded under the subject `Title of thread <first 8 characters of the id>`; the answer keeps its first line as plain text without quotes or a trailing period, at most 60 characters (`cleanTitle`, fenced code blocks skipped); the system prompt asks for the topic without people, participant labels in the answer are mapped back to the participants' names, and an answer that still holds an unknown label, `a teammate` or `[email]` is dropped. Without an agent, with the weekly budget used up, on an empty answer or any failure (logged, never posted) the title is the message's first line outside fenced code blocks, cut at a word boundary (`fallbackTitle`). It is stored with the `generatedTitle` patch, which applies only while `titlePending` is set; a rename with `PATCH` clears it first, so a person's title is never replaced.

**Prompt** (`chat-prompt.ts`): the system prompt (`CHAT_SYSTEM`) is fixed and the Guide of the target for task `chat` comes as context, so the prefix caches. The user prompt is the running summary, the conversation up to the agent's last reply and every message since, merged into one block. Humans appear only as `Participant A`, `Participant B`, … by first appearance in the thread (stable, stored as `participants`); the agent is `assistant`, Holtkeeper's own messages `system` (cards as title, subtitle and task summaries). `anonymize` replaces ids, emails, user names, names and their parts of every `users` account, every poster the thread remembers (`people`, so `header` principals without an account are covered once they posted) and the asker with labels (`a teammate` for people outside the thread) and any other email with `[email]`. A `header` person who never posted in the thread is unknown to the server, so their name in free text stays. Agent replies store the run's `transcriptRef` (the server defaults save every run's transcript to the artifacts) and the tool trace counted from it. Once the history after the summary passes ~20k estimated tokens (`SUMMARY_THRESHOLD_TOKENS`), a `fast` one-shot (`chat-summary`, $0.02) folds everything but the newest ~8k tokens into the summary (`planSummary`), so the summary is recomputed only after another threshold's worth of messages.

### Webhooks per forge

Each forge can have its own webhook: `POST https://<server>/api/webhooks/<forgeId>` with `X-Gitlab-Token` equal to `jobs.webhooks.<forgeId>.secret`. The forge is known from the URL, so no URL matching is needed. Forges get the secret from `POST /api/forges/:id/webhook` (below). `POST /api/webhooks/gitlab` with `jobs.webhookSecret` of the config file keeps working. URLs are built from `server.publicUrl` (e.g. `https://holtkeeper.example.com`), else from the origin of the request that asks for them.

**Auto-registration.** `POST /api/forges/:id/webhook { register?, targets? }` generates a new secret (32 random bytes, base64url, sealed in the forge document and returned once) and, with `register: true`, registers the hook through the forge's `ensureWebhook` for each target with every event of `webhookEvents`. Targets default to the forge's groups: the static prefix of every include glob as a GitLab group (`games/*` → group `games`), exact paths as projects. GitLab group hooks need Premium; on Free (404/403) the adapter registers one project hook per project of the group and the response's `notes` say so. Registration is idempotent by URL: an existing hook with the same URL is updated. Rotating (calling it again) re-registers on the hooks registered before, so GitLab gets the new secret at once; failures per target are in `errors` and do not undo the new secret. Removing the forge removes the hooks it registered.

**Keeping registrations current.** Each registered hook records its `events`. The leader runs `syncWebhooks` at start and every hour: forge webhooks of panel forges and repository webhooks of the repositories polling has listed whose recorded events differ from `webhookEvents` (or were registered before events were recorded) are registered again through `ensureWebhook` with the same URL and secret, so they start delivering new event kinds without a rotation. Failures are logged as `webhooks: ...` and retried on the next run.

The forge's token needs scope `api` and the **Maintainer** role (project hooks) or **Owner** role (group hooks) on the targets.

**Pipeline Hook** — for a pipeline of a merge request's head commit that ended `success` or `failed`, the merge request policies run again as an `update` event (the engine loads the latest pipeline fresh), so approvals and merges deferred while the pipeline ran happen now. Only `enqueue` intents queue jobs. Pipelines of other commits are ignored.

### Repository updates

Webhook deliveries are turned into `ForgeEvent`s (`routes/webhooks.ts`) and handled by `createEventDispatcher(deps)` (`events.ts`), which does everything described above. Polling (`updates.ts`) finds the same events and hands them to the same dispatcher, so a repository behaves the same whichever way it learns about a change; jobs queued from polling have trigger `poll`, and audit events from polling have actor `poll` and `via: 'system'`. A job already queued or running for the same analyzer, ref and options is not queued twice, so a change seen both ways runs once.

**Repository webhooks.** Each repository can have its own URL `https://<server>/api/webhooks/r/<token>`. The token (24 random bytes, base64url) is the secret: it is sealed with the vault in `store.kv` (`repo-hook:<forge>:<path>`) so the URL can be shown again, and found by its SHA-256 (`repo-hook-token:<hash>`). Deliveries about another project answer 400, unknown tokens 404; only GitLab payloads are understood for now. The hook keeps its last 50 deliveries, newest first (a ring under its own key `repo-hook-deliveries:<forge>:<path>`, so recording one never rewrites the token or the registered hooks; kept across rotation, deleted with the hook): forge event header, a one-line `summary` (`push to main, 3 commits`, `merge request !7 open`, `comment on !7`, `pipeline failed on !7`, `tag v1.2.0`), jobs queued or why it was ignored, the `error` of a rejected delivery (bad body, another project) and its duration. `createdBy` is the principal who issued the current URL.

**Polling.** A leader duty ticks every 15 s. Repositories are those of the config's groups (listed from the forge every 30 minutes or by hand; the result, what the include patterns matched before excludes (`matched`) and the last 20 attempts are kept in `poll-group:<group>`, and a failed listing keeps the previous list, or the group's exact include paths when there is none) plus exact repositories the `polling` setting names. For each with `polling` enabled ([@holtkeeper/updates](../../../packages/updates/docs/README.md)):

- The interval is the setting's, or `withWebhook` while any webhook URL reported about the repository in the last 24 hours (`webhook-seen:<forge>:<path>`); `withWebhook: 'off'` stops polling then.
- Repositories are grouped by limiter key (the forge's credential id, `forge:<id>` for a forge without one). Each key's polling budget is `pollShare` (default 0.2) of its `requestsPerMinute` from `limits.credentials` or the kind defaults; when the repositories of a key ask for more, all of them are slowed by the same factor (`stretch`). A never-polled repository starts at a stable point within its interval.
- Due repositories run one at a time per key, oldest first. A key is skipped while the limiter reports it saturated (cool-down after 429, queue, no free slot) or while the requests spent on it in the last minute would pass its budget; it is tried again next tick.
- State lives in `store.kv` (`poll:<forge>:<path>`: cursor, last poll, requests, events, error, next poll, effective interval, stretch and the last 20 attempts, each `scheduled` or `manual` with its result and duration). A lease (`poll-lock:<forge>:<path>`, 2 minutes) keeps two processes from polling one repository at once.

### Merge request policies

Merge request, note (`/holtkeeper <command>`, as a `command` event) and pipeline events first run the policies of the setting `mergeRequests.policies` (see [@holtkeeper/mr-policies](../../../packages/mr-policies/docs/README.md)) that cover the repository, through the repository's `GitForge`. Every outcome is logged as `mr_policy.<status>` (`done`, `skipped`, `deferred`, `failed`, `intent`, …) with the policy, action and detail; invalid settings entries as `mr_policy.invalid`. The configured analyzers are then queued minus the policies' `skipAnalyzers` (`*` skips all), plus their `enqueue` intents. Done actions are remembered per head commit in `store.kv` (`policy:<engine key>`, 90 days), so a redelivered event does not approve twice. `config.dryRun` evaluates without changing anything. Without policies nothing extra is loaded from the forge.

### Release assistant

Every forge event of a repository with releases on (`releases.enabled`, default off) except notes also goes to the release assistant (`src/releases.ts`, one per server, shared by routes and the event dispatcher), in the background: it rereads that repository's overview row once events stop for 30 s (`releaseRefreshDelayMs`), so bursts cost one read; a tag drops the cached tag list (`release:tags:<forge>:<path>`, otherwise kept 30 minutes; read in pages of 100 that double until the timeline page, the version or the `release_changes` range asked for is covered, at most 3200 tags; a version whose predecessor in the list is dated after it, such as a maintenance tag, does not count as covered); a push to the release flow's source branch rewrites the description of the open candidate merge request Holtkeeper opened; merging the candidate (source into target) records `merged` and, with `acceptance: merge`, accepts; adding `release-accepted` to the merged candidate accepts with `acceptance: label`. Versions are never created on their own. Release events are kept per repository in `store.kv` (`release:history:<forge>:<path>`, newest 100), audited as `release.<kind>` and sent to the `releases.notify` targets. Ranges between two version tags are read once with `listCommits` and kept for good under `release:range:<forge>:<path>:<from sha>:<to sha>`. Servers without `store.kv` keep this state in memory.

**Tracker issues** (`issues.ts`, optional): with a credential of kind `jira` ([@holtkeeper/issues-jira](../../../packages/issues-jira/docs/README.md); `url` the Jira site, options `{ authKind: 'basic', email }` for a Cloud API token or `{ authKind: 'bearer' }` for a Data Center personal access token, checked by `validateJiraCredentialOptions`) whose scope covers the repository (the most specific one wins), ticket keys of the repository view's plans (`ReleaseRepoView.issues`), of a version's tasks and of `release_changes` get the issue's title, status, category, type and page. Lookups go through `cachedTracker` in `Store.kv` (`issues:jira:<credential>:<key>`, one hour for open issues and unknown keys, a day for done ones), one batched search per range. Without such a credential, or when Jira fails (logged), pages and tools show plain keys; nothing is ever written to Jira and the credential never reaches agents. `ServerDeps.issueTracker` replaces the lookup in tests.

See the `/api/releases/*` endpoints under [Managed configuration](#managed-configuration) and [@holtkeeper/release](../../../packages/release/docs/README.md).

### Forge SSH keys

### Group titles

A group document may carry a `title` (trimmed, 1–60 characters; `PUT /api/config/groups/:id`, global `settings:write`, audited as `group.update`). It is display only: grants, settings scopes, home groups, guides, schedules and triggers keep naming the key, and stored data never holds the title. Text for people and agents names a titled group through `groupLabeler(config)` as `Title (key)`, so the key needed for a tool call or a setting is always there: the `ops` tools (jobs of a group, budget scopes, `fleet_health` rows), `security_findings` and `license_overview` rows, the `assets` policy source, knowledge scopes and the team named on shared entries, the team of `catalog`, `stack`, `who_uses` and `evaluate_dependency` results, write tasks' related repositories and exported chat threads. Each of those contexts takes an optional `groupLabel` (default the key). The repository overview's knowledge labels use the plain title (`groupTitle` of [@holtkeeper/core](../../../packages/core/docs/README.md#group-lists)). Tool inputs (`fleet_health`'s `group`) still take the key.

A forge can issue an SSH key on the account behind its token (`POST /api/forges/:id/ssh-key { usage?, expiresInDays?, identity? }`, global `settings:write`). The server generates an Ed25519 key, registers it as a user key (`usage` default `auth_and_signing`, expiry default 365 days), pins the forge host's SSH keys with `ssh-keyscan` (trust on first use; a failure is a note and git stays on HTTPS), reads the commit identity from `getCurrentUser` unless `identity` is given, and stores the key as an `ssh` credential with the token credential's scope. The forge document keeps only the credential id; the forge entry of `GET /api/config/forges` shows `sshKey` (public key, fingerprint, usage, expiry, identity, whether host keys are pinned), never the private key. Calling it again rotates the key in place (`rotateSshKey`: the new key is registered and stored before the old one is removed). Deleting the key or the forge removes the registration and the credential.

Jobs use the key through `gitKeyFor` (see [@holtkeeper/jobs](../../../packages/jobs/docs/README.md#context)): clone, fetch and push over SSH, signed commits for propagate. Running git over SSH and signing needs `ssh`, `ssh-keyscan` and `ssh-keygen` on the host (`openssh-client` in the worker image).

### Egress rules

`GET /api/egress/rules` serves `EgressRulesResponse` to an egress proxy (such as [docker/egress-proxy](../../../docker/egress-proxy/README.md)) that sends `Authorization: Bearer <server.egress.secret>`; without `server.egress` it answers 404, with a wrong secret 401, and no session or MCP token grants it. Every panel GitLab forge gives one rule unless its document has `packages: false` (the "Packages for jobs" switch, on by default): `GET`/`HEAD` to its package registries (`gitlabPackageRegistry`) get `Authorization: Bearer <token>` with its credential's current token, read with `reveal` on every request, so rotations reach the proxy on its next read. Forges whose credential cannot be read are left out and logged. Forges whose document also has `cachePackages: true` ("Cache packages", off by default, only with packages on) add a `cache` entry: a private cache rule (`{ kind: "packages", host, paths, private: true }`) for their package files (`gitlabPackageFiles`), so the proxy keeps what jobs download with the token; the response has no `cache` key when no forge caches.

Every `egress-secret` credential ("Proxy secret" in the panel) adds one replacement rule per host: the credential URL's host and its `options.hosts`. Its `options` (checked by `validateEgressSecretOptions` on create and update) are `placeholder` (16–128 of `A-Za-z0-9._~-`; the panel generates a UUID), optional `hosts` (`example.com` or `*.example.com`), `paths` (regular expressions), `methods` (default any, sent as `*`) and `in` (`headers`, `url`, `body`; default `headers`). The rule replaces the placeholder with the revealed secret; it is `insecure` (plain HTTP too) only when the credential URL is `http:`. Jobs are given the placeholder, e.g. `TURBO_TOKEN=<placeholder>` in the `toolchain` setting's `env`, and never see the secret; the placeholder is useless against any other host. Prefer `headers`: a server that stores what it receives in a URL or body could hand the real value back to a job. The response is `no-store`.

### Egress cache

`GET /api/egress/cache` returns `EgressCacheView` for the proxy in `server.egress.proxy`: `{ configured: false }` without one, `{ configured: true, error }` when it cannot be reached, refuses the secret or has caching off, otherwise what one replica reports (store, TTL per kind, size limits, counters since its start, cached URL patterns, totals and the 5000 most recently used entries). The server asks the proxy itself: `GET http://egress-cache.invalid/v1/cache` sent through it with `Authorization: Bearer <server.egress.secret>`, a reserved host the proxy answers instead of forwarding ([docker/egress-proxy](../../../docker/egress-proxy/README.md#download-cache)). `POST /api/egress/cache/delete` takes `DeleteEgressCacheInput` (`paths`, a `kind`, or `{}` for everything), returns `{ removed, bytes }` (502 when the proxy fails, 404 without a proxy) and logs `egress-cache.cleared`.

### Read-only repositories

The scoped setting `repo.freeze` (`{ reason, until? }`; everything, groups, repository patterns or paths) makes Holtkeeper a pure analytics tool for the repositories it covers. `readOnlyRepos` (`read-only.ts`) resolves it with `resolveRepoFreeze` of [@holtkeeper/settings](../../../packages/settings/docs/README.md#freezes): the most specific entry not past its `until` wins, so a freeze stops counting at `until` and an expired narrow entry lets a broader one apply again. The repository hub's `access` (`GET /api/repos/overview`) carries the freeze's `reason` and `until`.

- Every forge client of the effective config, file and panel forges alike, goes through `readOnlyDefinition` of [@holtkeeper/forge](../../../packages/forge/docs/README.md#read-only-repositories): comments, reviews, thread replies, labels, merges, branches, commits, tags, pipeline jobs, deploy keys and project webhooks of those repositories are refused with `ReadOnlyRepositoryError` before they are sent. The setting is read at each write, so a change applies at once.
- Merge request, note and pipeline events of those repositories are ignored (`ignored: 'the repository is read-only'`): no policies, reviews, commands or acknowledgements. Tag events still queue their analyzers.
- Job checkouts of those repositories get no `publisher`, so nothing is pushed over git.

Analyses, schedules and links between repositories (dependency inventory, stack conventions, internal packages) keep working. Jobs that would change such a repository, such as propagate or audit fixes, fail with the read-only error.

## Repository health

`repo-health.ts` classifies a repository from stored data only: the newest main-line record head per kind (`metrics`, never `data`), recent jobs, recent audit runs and the stored release cards. `readHealthSources` reads them once per request: one `settings.list()`, `latestHeadsWithMetrics`, the newest 500 jobs of the repositories whose analyses the caller may read, with `audits` the newest 500 audit runs and, when given, the release snapshot. `latestHeadsWithMetrics` (`analyses.ts`) takes the newest head per repository and kind, replaced by the newest head without a ref when it names one (`mainLineRecords`), so a run on a feature branch never becomes the repository's health. Heads stored without metrics get them computed from their data with default options: one `latest` read per kind that misses them (a `get` for a replaced head), kept in process per record id, failures included, so later requests read no data for the same records; history keeps what was stored. `repoHealth` then calls `settingCascades` once per repository for the options it is judged by: the coverage target is the `target` option of the most specific `analyzers.coverage` entry (`coverageTargetOf`, default 60), bundle budgets the `budgets` option of `analyzers.bundle` (target name or glob → maximum gzip bytes, judged with `budgetFor` and `budgetVerdict` from `@holtkeeper/bundles`; without an entry the verdicts stored with the record).

Each cell is `{ value, sub, tone }` with tone `ok`, `warn`, `bad`, `info` or `none` (nothing to judge). Every threshold lives in `repo-health.ts`, except the bundle budget rule (`@holtkeeper/bundles`). Sizes use the shared `formatBytes` of `@holtkeeper/report`.

| Cell           | Needs           | From                      | Rule                                                                                                                                                                                                                                                        |
| -------------- | --------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `security`     | `audits:read`   | `audit` metrics or run    | critical or high: bad; expired allowlist entries, medium, low or unrated: warn; none: ok. The newest audit run wins when it is newer than the `audit` record (runs ingested through `POST /api/audit-runs` store none)                                      |
| `dependencies` | `analyses:read` | `renovate` metrics        | a security update: bad; a major update or 10 or more outdated: warn; else ok. Without majors the sub says `minor only`, `patch only` or `minor or patch`                                                                                                    |
| `coverage`     | `analyses:read` | `coverage` metrics        | below the target: bad; down by 1 point or more since the record before: warn; else ok                                                                                                                                                                       |
| `bundles`      | `analyses:read` | `bundle` metrics          | a target over its budget: bad; a failed target, one from 90% of its budget or 10% growth: warn; else ok                                                                                                                                                     |
| `jobs`         | `analyses:read` | jobs of the last 24 hours | the latest run of an analyzer failed: bad; stopped by the AI budget: warn; running or queued: info; else ok                                                                                                                                                 |

A cell the caller may not read is left out, and `health` is computed over the cells that remain: `failing` with a bad one, `warnings` with a warn one, `not-analysed` when every cell is `none`, else `healthy`. `freshness` (`{ current, total }`: newest records, one per kind, younger than 14 days) and `lastAnalysedAt` need `analyses:read`.

`GET /api/repos` (`routes/repos.ts`) answers `RepoList`: every member of the configured groups as the poller's stored group listings name them (`listedRepos`: every group's listing read at once, plus exact include paths, also without a key-value store), never only audited repositories, that the caller may read (see [Permissions per endpoint](#permissions-per-endpoint)), sorted by `forge:path`. Each `RepoSummary` carries `health`, `cells`, `freshness`, `lastAnalysedAt`, `updates` (`repoUpdatesSummaries`, all repositories' keys read at once: `webhook` after a delivery in the last day, `polling` with its interval when the `polling` entry covering the repository is on, else `off`, plus the last poll and its error), `latestAudit` (the newest run of the same audit read health uses) and `configurable`. All reads are batched per request; no forge is called.

## Roles, health and metrics

`startServer(config, { roles, worker, drainTimeoutMs })` runs what `roles` asks for (`roles.ts`, default `['all']`): `web` serves the API, UI and webhooks; `worker` runs the job worker; `scheduler` runs schedules, credential rotation, artifact and audit retention, only while this process holds the leader lease (`leader.ts`: `kv.acquireLease` on `leader:scheduler`, 30 s TTL, renewed every 10 s; a failed renewal stops the duties). Processes without `web` serve only the operational endpoints. `worker: { concurrency?, claimDelayMs?, maxJobs?, pools? }` overrides `jobs.concurrency`, delays claims, picks the worker pools it serves (see `@holtkeeper/jobs`, default `['default']`; write tasks need a `write` worker) and makes the worker stop after `maxJobs` jobs; `RunningServer.exhausted` then resolves.

Every process answers `GET /healthz` (alive), `GET /readyz` (store query, Postgres migrations via `ready()`, artifact store `ping()`, not draining; 503 with a JSON body per check otherwise) and `GET /metrics` (Prometheus text: queue gauges, finished jobs and a duration histogram by analyzer, webhook deliveries by forge and status, AI runs/tokens/cost, limiter saturation per key, artifact store bytes; `metrics.ts`). They bypass authentication. `stop()` drains: readiness fails, the worker stops claiming and running jobs get `drainTimeoutMs` (30 s) before they are requeued, then the lease is released and the store closed.

With `limits: { distributed: true }` the limiter keeps its counters in the store's `kv` (`limiter-state.ts`, `storeLimiterState` from `@holtkeeper/limits`). See [docs/deployment.md](../../../docs/deployment.md) for Docker and Kubernetes.

## Limits

One `@holtkeeper/limits` limiter is shared by the server (`deps.limiter`): GitLab requests of forges count against their credential id (kind defaults, overridden by the everything-scope entry of the setting `limits.credentials`); the job worker's admission hook leaves jobs waiting while their forge key or, for analyzers that use an agent, their AI provider key (the credential id the global `llm.provider` names) is saturated. The agent factory gets the same limiter. Settings › Integrations reads its live usage from `GET /api/limits/usage` ([integrations.md](integrations.md#request-limits-usage)).

## Feeding audits

`POST /api/audit-runs` stores an audit report made elsewhere, as the caller (`audits:run` on the repository). Machine credentials (API tokens) for CI are not implemented yet; until then CI uploads work with `noAuth` or `headerAuth` behind a proxy that authenticates CI.

## Media

Responsive image variants and SVG optimization for files in repositories, behind a small `MediaEngine` interface (`src/media/engine.ts`). `src/media/adapter.ts` maps it to `@holtkeeper/media` (sharp, svgo), imported on first use; it probes the image (rejecting more than `maxPixels` from the header), plans and encodes variants (`formats`, `widths`, `quality`; `densities` give a texture-style `@Nx` ladder; preset `fast`/`default`/`max` sets encoder effort), optimizes SVGs with svgo's `safe` preset and renders snippets for every framework. Tests pass a fake engine as `ServerDeps.media`.

Merge request reviews use `createMediaReviewer({ publicUrl, cache, policyFor })` (`src/media/reviewer.ts`) as the review analyzer's `mediaReviewer`; `policyFor` reads the repository's `assets.policy` (see [Assets](#assets)). Files the policy ignores are skipped. Per changed raster image: a savings table (original against WebP/re-encoded, plus AVIF when `formats.raster` asks for it; typical transfer at 375/768/1440 CSS px at DPR 2) with a note when the merge request brings none of the siblings the policy asks for (`hero.webp`, `hero-640w.webp`) or the image is wider than 1280 px without sized variants (`-640w`, `-720`, `@2x` siblings), a line naming where the file breaks the policy (`policyNotes`: disallowed format, size above `warn`/`error`, larger than `maxDimension`), and a `<picture>` suggestion on added `<img>` usage lines when a format's saving clears `minSaving` (both its percent and its bytes, as in the analyzer). Added SVGs get a whole-file svgo suggestion when its saving clears `minSaving` and is at least 64 bytes (otherwise a summary line) and inline `<svg>`/`<path>` fragments whose lines the diff adds entirely get suggestions (svgo for static HTML/Vue/Svelte SVGs, path data only for JSX and SVGs with bindings), unless `formats.svg` is `keep`. Each image links to the assets area of the repository hub's Quality tab with the media dialog open on the merge request's head (`panelLink`: `webPaths.repo(repo, { tab: 'quality', section: 'assets', file, ref })` from `@holtkeeper/web-paths` on `publicUrl`, `/repos/<forge>/<path>?tab=quality&section=assets&file=…&ref=…`), labelled as a merge request offer under `mode: 'suggest-mr'`.

**Variant cache.** The reviewer, the media panel and background jobs (`context.cache`) share `artifactCache(artifacts)`: every encoded variant is stored as an artifact (tag `kind: cache`) under the ref `cache/media/v1/<source sha256>/<spec and encoder hash>`, so a re-push, a later review or the next scheduled `assets` analysis of an unchanged image reuses it instead of encoding again. With `server.artifacts.kind: 's3'` the cache lives in the bucket and is shared by every server and worker pod; storage sweeps remove it like other artifacts and a swept entry is simply encoded again.

Artifacts returned by analyzer runs in background jobs (e.g. the encoded variants of `assets`) are stored in the artifact store tagged `{ repo, kind, analysis }` (`persistArtifactsTo`); external uploads send them in `artifacts` of `POST /api/analyses`.

`POST /api/media/variants` — `MediaVariantsInput { repo: 'forge:path', file, ref?, formats?, widths?, densities?, quality?, preset? }`. Reads the original with `forge.readFileBytes` (SVG through `readFile`), runs the engine and stores each variant (or the optimized SVG) as an artifact tagged `{ repo, kind: 'media', source }`. Returns `MediaVariantsResult { original, variants: { id, format, width, height, quality, bytes, savingsPercent, path }[], svg?, snippets, savings, exists }`; `path` is the engine's suggestion or `<dir>/<name>-<width>w.<format>`, `savings` the smallest variant per format against the original, and `exists` says for every variant `path` whether a file is already there at `ref` (the default branch without one). `exists` is read from the forge on every request, cached results included: one `listFiles` per folder (up to 10,000 entries), a file read per path when the forge cannot list or the folder is larger.

- Limits (`MediaLimits`): originals up to 25 MB and 50 megapixels (the engine rejects bigger images before decoding them fully; 413), two images processed at once, eight more waiting, then 429. Engine failures are 422.
- Results are cached in memory by (SHA-256 of the original, options), 100 entries, and recomputed when one of their artifacts is gone.

`POST /api/media/apply` — `MediaApplyInput { repo, file, ref?, variants: id[], paths?: { [id]: path }, replaceOriginal?: id, snippet?: { file, range, oldText, newText }, mode, title? }`.

- `merge-request`: one `CodeChange` with a `write-binary` edit per variant (new files; a conflict when the path exists), one replacing `file` when `replaceOriginal` is given (guarded by the current file's SHA-256), and the snippet as a `replace` edit; opened with `openMergeRequest` against `ref` or the default branch. Returns `MediaApplyResult { applied, conflicts, mergeRequest? }` and logs `media.merge_request_opened`.
- `zip`: an `application/zip` download with the files at their paths and a `README.md` holding the snippet.

## Assets

`assets.ts` resolves the `assets.policy` setting ([@holtkeeper/assets](../../../packages/assets/docs/README.md#policy), registered as `assetsPolicySetting`, section Repositories, edited on the repository's Assets tab and in the Guide's Assets section) per repository: `assetsPolicyFor` returns the most specific entry, else `defaultAssetsPolicy`. Assets jobs get it as their `policy` option (`scopedAnalyzerOptions`); the `analyzers.assets` setting cannot set `policy` (`SETTING_OPTIONS` drops it from that setting's schema and form). The review's media reviewer and the `assets` tools read the same policy.

`GET /api/assets/repo?repo=forge:path` (`analyses:read` on the repository) — `RepoAssetsView`: the effective `policy` with `policyFrom` (id and scope of the winning entry; absent for the default), `trend` (total bytes and violations of the 12 newest records, oldest first) and, once the analyzer has run, the newest record's `analysisId`, `createdAt`, `ref`, `sha`, `checkedPolicy` (false for records made before the policy) and `summary` (`assetsSummary`). It reads stored records only; nothing runs on a page view. The fleet table over every repository, `GET /api/assets`, is described under [Quality fleet tables](#quality-fleet-tables).

## Coverage

`coverage.ts` turns stored `coverage` records into the data of Quality › Coverage; nothing runs on a page view. `GET /api/coverage` lists a `CoverageRepoCard` for every repository with a record the caller may read (`analyses:read`), from stored metrics only (`coverageCards`): the newest main-line head of each repository (`latestHeadsWithMetrics`) and the heads of its 12 newest main-line records; record data is read only for a newest record whose metrics predate `totals` (`withCurrentMetrics`). A card holds its groups, the newest record's `analysisId`, `createdAt`, `ref`, `sha`, `tools` and `totals` (`coverageTotals`: lines, branches, functions, files, files and lines without tests), `change` (points of line coverage since the record before), `trend` (line and branch shares of those records, oldest first) and `head`, the default-branch head freshness last saw (`readHead`), set only when it differs from the record's `sha`. Answers are kept in a fleet cache keyed on the newest analysis ids, the visible repositories and the freshness heads (see [Supply fleet tables](#supply-fleet-tables)).

`GET /api/coverage/repo?repo=forge:path` (`analyses:read` on the repository) — `RepoCoverageView`: the same `card` (absent until the analyzer ran) plus `changed` (`changedFilesCoverage`: line coverage of the files that are new or whose counts moved since the record before), `groups` (`coverageGroups`: per workspace package or top-level folder), `worst` (`worstFiles`: the 10 files with the most uncovered lines) and `changes` (`coverageChanges`: up to 20 files whose line coverage moved by 5 points or more since the record before), plus `job`, the summary of the job that produced the card's record (`jobSummary`, the same fields `GET /api/analyses/:id` gives), when the caller may read it.

## Repository page

`repo-page.ts` builds the repository page's data from stored records; nothing asks the forge or a model on a page view. It needs `analyses:read` on the repository.

`GET /api/repos/overview?repo=forge:path` — `RepoOverview`, what the repository hub's header and Overview show: the config `groups`, `health` and `cells` (the same as `GET /api/repos`, cells the caller may not read left out), `cards` (the Supply chain then Quality cards, each with tone, status in words, headline value and unit, up to two lines, optional segments and the record it describes; a card behind a permission the caller lacks is absent), `head` (the default-branch head freshness last saw, from `readHead`), `defaultBranch`, `analyses` (the newest record of every kind as `AnalysisSummary`, reviews left out and the `audit` record without `audits:read`, for the freshness table), `audit` (only with `audits:read`), `dependencies` (direct dependencies of the newest `depgraph` record), `stack`, `toolchain` (runtimes and package managers of the newest `stack` record), `reviews30d` (Holtkeeper's reviews of the last 30 days summed), `work` (jobs and failures since Monday 00:00 UTC, write tasks awaiting approval only with `repos:read`, AI spend only with `ai:read` or `ai:admin`), `knowledge` (Guide sections, notes, proposed learnings and inherited scopes; only with `knowledge:read`), `release` (stage, versions and the newest deploy; only with `releases:read` while releases are on) and `access` (read-only with reason and end, whether write tasks may open merge requests). It never carries the head commit's title.

## Storage

`GET /api/storage` returns `StorageOverview { providers: { id, label, bytes, count?, details, available, note?, clearable, error?, reportedBy? }[], totalBytes }` from `ServerDeps.storage` (`StorageProvider`s). `startServer` registers the artifact store (`artifactStorage`) and the database (`databaseStorage(server.databasePath, store.database)`: the Postgres database by domain, or the SQLite file plus `-wal`/`-shm`), plus `ServerOptions.storage`. `POST /api/storage/:id/clear { scope? }` calls the provider's `clear` (409 when it has none, 400 for a bad scope) and logs `storage.cleared`.

**Worker disks.** Git mirrors (`mirrorStorage(jobs.cacheDir)`) and the mise tool cache (`miseCacheStorage`) live where jobs run, so only processes with the `worker` duty register them, and they publish what they measure (`startStorageReports`, `storage-reports.ts`): every 5 minutes into the store's kv (`storage:reports`, one entry per worker named after its host, the pod name in Kubernetes; atomic with `compareAndSet`), removed when the worker stops and dropped after 15 minutes without an update (a killed pod). The overview shows reported areas instead of a local measurement of the same id: bytes and counts add up, `details` lists the workers and `reportedBy` how many reported. A worker writes a random id into `.holtkeeper-volume` in each area's directory, so workers sharing one volume (a ReadWriteMany mirror cache) are one `shared: a, b` line, counted once. Clearing a reported area appends a request to `storage:clears` and returns `{ requested }` (workers asked); every worker started before the request carries it out within 15 seconds (on a shared volume only the first worker by name) and reports again.

## Database

`GET /api/database` returns `DatabaseView` from `store.database` (the store's `DatabaseInspector`): `{ available: false, reason }` for the memory store or when inspection fails (missing rights, unreachable database), otherwise `{ overview, tables, indexes, domains, history, advice, migrations, resettable }`. `tables` carry their domain (`tableDomain`); `indexes` are marked `unused` (never scanned, not unique or primary, not a GIN or GiST search index, which only searches scan) and `duplicateOf` (same table and definition apart from the name; the smaller one counts as the original). `domains` sum tables per domain with `weekAgoBytes` from the newest snapshot at least seven days old. `advice` (`databaseAdvice`, warnings first) flags duplicate indexes, unused indexes of 1 MB or more, tables with 20% or more dead rows (at least 1000) not vacuumed for a day (autovacuum starts at 20% by default, so busy tables pass that share between runs), Postgres tables of 10 000 rows or more not analyzed in 30 days, large tables read mostly by sequential scans, 80% of `max_connections` in use, sessions idle in a transaction, a cache hit ratio under 95%, replicas not streaming or 16 MB / 30 s behind, SQLite files a quarter free, and missing statement statistics.

`GET /api/database/queries?sort=total|mean|calls&limit=` (at most 200) returns `DatabaseQueries`; `POST /api/database/queries/reset` clears them (409 without statement statistics, 400 when the database refuses) and logs `database.queries-reset`; `GET /api/database/sessions` returns `{ sessions }`. Both 404 for the memory store.

**History.** The leader records a snapshot (`startDatabaseSnapshots`) at start and every 6 hours into the kv key `database:history`: one point per UTC day (`day`, `bytes`, bytes per domain), the latest measurement of the day winning, 90 days kept.

`databaseStorage(path, inspector)` in Settings › System → Storage reports a Postgres database by its size, split by domain.

## Audit log

Every mutating request (`POST`, `PUT`, `PATCH`, `DELETE`) under `/api` and `/auth/<provider>/admin` is appended to `store.audit` once its response is ready, whatever the outcome: actor (or `anonymous`), `via` (`webhook` for `/api/webhooks/*`; `ui` when the browser sent `Sec-Fetch-Site`, else `api`), the route template and params, status, duration, client IP (`X-Forwarded-For`, `X-Real-IP`, else the socket) and user agent. 401 and 403 are `denied`, other 4xx/5xx `error`. The action and target are derived from the route (`PATCH /api/credentials/:id` → `credential.update` on `credential:<id>`, `POST /api/credentials/:id/rotate` → `credential.rotate`). `target.repo` is set only by the route itself or from a permission check of the request that allowed a repository (`authorize` with a repository target remembers it; with several, the one `?repo=` names); a `denied` event never names a repository, so nobody can plant events in the audit log of a repository they cannot act on. Reads are not audited, except `audit.export`.

Routes enrich their event with `c.set('audit', { action?, target?, changes?, details? })`. Credentials, settings and knowledge record field-level `changes` (`diffChanges(before, after)`: dotted paths, arrays compared whole); fields named like secrets (`secret`, `password`, `token`, `apiKey`, `authorization`, ...) and the values of secret settings are `«redacted»`, and a new credential secret is recorded only as changed. User changes made through the `users` provider (`PATCH /auth/users/admin/users/:id`) get `changes` from the stored user before and after.

Background code appends with `appendAudit(store, event)` from `src/audit.ts`:

```ts
appendAudit(store: Pick<Store, 'audit'>, event: Omit<AuditEventInput, 'at'> & { at?: Timestamp }): Promise<AuditEvent | undefined>

await appendAudit(deps.store, {
  actor: { id: 'gitlab:work:42', name: 'jane', provider: 'gitlab:work' },
  via: 'webhook', // or 'job' / 'system'
  action: 'mr.policy.label',
  target: { type: 'merge-request', id: '17', repo: 'work:games/app' },
  outcome: 'ok',
  details: { label: 'needs-review' },
})
```

It never throws (failures are logged), so auditing never breaks the job or request it describes. The store's audit log is mandatory; it is the only record of who did what (there is no separate activity log).

Besides the request middleware, these write events on their own: seeding defaults (`setting.seed`, `config.seed`, `via: 'system'`), scheduled credential rotations (`credential.rotate`), AI budgets the first time they are exceeded in a week (`ai.budget_exceeded`), agent knowledge proposals (`knowledge.propose`, `knowledge.accept`, `knowledge.evidence`), release events (`release.<kind>`, `via: 'job'` or `webhook`), merge request policy outcomes and commands from merge request notes (`mr_policy.*`, `job.command`, `chat.command`, `via: 'webhook'`), repositories found by polling (`repo.discover`), the results of background runs started by hand (`schedule.run_result`, `trigger.run_result`, `analysis.backfill_result`), sign-ins and own passkey changes through the `users` provider, and `users` CLI commands. Job outcomes are not audited; they stay on the job records.

Inbox decisions log `guide.reject` (details `inputHash`, `generatedAt`, `model`), `release.dismiss` (target the repository, details `sha`) and `allowlist.renew` (target the setting entry, `changes` of `expires` and `reason`, details `key`, `advisory`, `package`). `POST /api/settings/draft` writes one `setting.draft` event for all its changes (details `keys`, `saved`, `removed`; change fields are prefixed `<key>#<id>.`). Snoozes are personal marks, not decisions, and are not audited.

| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/history`                         | `HistoryList` `{ events, nextCursor?, people }`, newest first; `cursor`, `limit` (≤ 500) and the filters below            |
| `GET /api/history/scope`                   | `HistoryScope` `{ repos: { repo, groups }[], instance }`: repositories with events the caller may see                     |

Filters: `actor`, `action` (prefix), `targetType`, `targetId`, `repo` (`forge:path`), `repos` (comma list of `forge:path`), `outcome`, `via`, `from`, `to`. The audit log is permission filtered: with global `audit:read` every event is listed; otherwise the caller needs `repos:read` somewhere and sees only events whose `target.repo` it can `repos:read` (`repos` narrows within those), never instance-level events such as settings, users or credentials. The summary follows the same rule: without a global `audit:read` it counts only readable repositories. The leader checks the chain at most once a day and records `audit.verify` as System; see [audit-log.md](audit-log.md). `people` holds the name and avatar of every user among the page's actors. Retention: `startServer(config, { auditRetentionDays })` sweeps daily, default 365 days, `0` keeps everything.

## Avatars

`GET /api/avatars/<seed>.svg?size=` (16–512, default 128) renders the [DiceBear](https://www.dicebear.com) **Voxel Bot** style locally with `@dicebear/core` from the definition in `@dicebear/styles` — no request leaves the server. The style is by DiceBear and licensed [CC0 1.0](https://creativecommons.org/publicdomain/zero/1.0/). Responses are `Cache-Control: public, max-age=31536000, immutable` with a content ETag (`If-None-Match` → 304) and a CSP that forbids scripts; recent renders are cached in memory.

The seed is the principal id (users: the user id). `GET /api/me` and `UserView` carry `avatarUrl` (`/api/avatars/<id>.svg`). `users` accounts may reroll with `PUT /api/me/avatar { seed }` (`null` goes back to the id); other providers answer 409.

## Preferences

`routes/preferences.ts` keeps each principal's own UI preferences in `Store.kv` under `prefs:<principal id>`. `GET /api/me/preferences` answers `UserPreferences { homeGroups, homeGroupsFromGrants }`: `homeGroups` (`GroupMatch[]`) are the groups the _My teams_ scope shows, the group entries of the principal's grants (`defaultHomeGroups`) until it picks its own. `PUT /api/me/preferences { homeGroups }` stores them deduplicated (at most 100; `null` goes back to the grants) and is audited as `user.preferences`; without `Store.kv` it answers 503 and `GET` the defaults. Home groups are a UI default, never a permission.
