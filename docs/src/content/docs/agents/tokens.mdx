An MCP token is a personal access token: it acts as the person who created it, cut down to reading. It never reaches further than its owner. Besides reading, it can only make proposals that people review (knowledge entries and Guide rules) and report exposed secrets. It cannot start tasks, run release steps or approve anything.

## What a token can see

A token carries its owner's grants, limited to these permissions:

| Permission       | What the agent can read with it                                                |
| ---------------- | ------------------------------------------------------------------------------ |
| `repos:read`     | Repositories, their health and analysis freshness.                             |
| `analyses:read`  | Analysis records: public API, usages, stack, coverage, assets, test ids, jobs. |
| `audits:read`    | Vulnerability findings from audits.                                            |
| `knowledge:read` | The knowledge base and the Guide.                                              |
| `releases:read`  | Release rules, status and changes.                                             |

So a developer of the storefront team gets an agent that sees the storefront's repositories, and other teams' repositories only as far as the **Reach** setting (`access.crossTeam`) lets everyone read their catalog. An admin's token reads everything, but still cannot write anything a read-only token cannot.

Whatever your grants, a token never gets `settings:write`, `credentials:*`, `users:*` or AI administration, and it cannot create or revoke tokens.

:::note
With passkey sign-in (`users` accounts) a token follows your **current** grants: when an admin narrows your access, your agents see less at once. Disabling your account or signing out everywhere revokes all your tokens. With other sign-in providers a token keeps the grants you had when you created it.
:::

## What a token can propose

Two tools write, and both only leave a proposal for people to review:

| Tool                  | What it leaves                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| `propose_knowledge`   | A knowledge entry for one repository, waiting in **Knowledge › Notes**.                               |
| `propose_rule_change` | One rule for a Guide section, waiting in **Knowledge › Learnings** unless the team auto-accepts them. |

See [Rules and knowledge](/agents/rules-and-knowledge/).

Everything else that changes something stays with people:

- **Tasks** start from Chat task cards, <Ui>Roll out</Ui> in **Supply chain › Libraries**, **Ops › Tasks** and `POST /api/task-groups`. An agent can follow a task's merge request with the read-only `review_status` on the task's branch; see [Changing code through tasks](/agents/tasks/).
- **Release steps** run from the [Releases](/guide/releases/overview/) screen and from confirmations in Chat.

## Report exposed secrets

Each token also has a **Report exposed secrets** choice, set on its row under **Account › Connect agents**:

| Choice                  | The agent                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| Under my name (default) | Gets `report_secret_exposure`; reports carry your name.                                    |
| Anonymously             | Gets `report_secret_exposure`; reports store nothing about you, only the day they arrived. |
| Off                     | Does not get the tool.                                                                     |

Agents call the tool on their own when a secret of the organization shows up in a session, masked, so administrators rotate it. Only you see the choice, administrators can neither read nor set it, and changing it is not audited. Anonymous calls are left out of the usage below. The choice links to the license's Use Condition: reporting is voluntary and never grounds for sanctions. See [Secret reports](/guide/supply-chain/secret-reports/).

## Scopes

The **New token** dialog has no switches: every new token reads and proposes. Tokens created earlier with the **Release steps** (`release`) or **Run tasks** (`tasks`) scope keep working, as read tokens: no MCP tool uses those scopes anymore, and the token list shows them as **Read**.

## Expiry and status

Tokens live 30 days, 90 days (the default), a year, or never expire. The table shows each token's state:

| Status       | Meaning                                       |
| ------------ | --------------------------------------------- |
| Active       | Used at least once and not about to expire.   |
| Expires soon | Expires within 14 days. Create its successor. |
| Expired      | Stopped working; agents get `401`.            |
| Never used   | Created but no call yet.                      |

**Last used** is updated at most once an hour, so it can lag a little behind a busy agent.

## Revoke a token

Press the trash icon on the token's row and confirm.

A revoked token stops working at once. Revoke a token when a machine is lost, a colleague leaves a shared agent behind, or you no longer recognize its calls. Creating and revoking tokens are logged as `mcp.token.created` and `mcp.token.revoked` in the audit log.

## Usage

Every tool call except anonymous secret reports is recorded with the tool, what it was about (a package or a repository), the client and the token.

- **Account › Connect agents** shows **Calls, 7 days** per token and, under **My usage**, your own calls over 7, 30 or 90 days with your most used tools, packages and clients.
- **Ops › AI spend** shows everyone's MCP usage to people who may see people (`users:read`); see [AI spend](/guide/ops/ai-spend/).

## Good practice

- One token per machine or agent, named after it. A leak then costs one revocation.
- Keep tokens out of repositories: no `.mcp.json` with a secret in version control.
- Give CI agents short-lived tokens and rotate them; give people's laptops 90 days.
- Revoke tokens nobody uses anymore instead of waiting for them to expire.
