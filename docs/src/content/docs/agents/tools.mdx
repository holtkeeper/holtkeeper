Holtkeeper's MCP endpoint offers about fifteen tools for developers at work in a repository, all built on data Holtkeeper already stores: analyses of every repository, the library index and the team's knowledge. Calls are cheap and never start an analysis; only `ask`, where an administrator turned it on, runs an AI agent. Every tool reads, except `propose_learning`, which leaves a pending learning people may reject, and `report_secret_exposure`, which reports a leaked secret. Fleet-wide views (security findings, licenses, stack usage), release state and jobs stay in the panel and in [Chat](/guide/chat/threads/). This page walks through the tools by the question an agent is trying to answer; [MCP tools](/reference/mcp-tools/) lists every argument.

A repository is named by its path (`acme/checkout-web`): Holtkeeper works out the forge. A git remote URL (`git@gitlab.example.com:acme/checkout-web.git`) and the full `forge:path` (`gitlab:acme/checkout-web`) work too, and `forge:path` is needed only when several forges have a repository at that path. Answers name repositories as `forge:path`. Answers are Markdown, cut at about 80 000 characters with a hint on how to narrow the request.

## Packages: yours and third-party

Holtkeeper indexes the public API of every package your repositories publish (each export with its declaration and doc comment, for every released version and the default branch) and the npm and Go libraries the fleet depends on, at the versions in use and the ones an upgrade would land on. Both answer through the same tools, so an agent never has to know whether a package is yours; each result says which it is. Agents use them instead of reading `node_modules`, the Go module cache or other repositories' sources. Pass `repo` and versions default to what that repository uses, so answers match the code in front of the agent. See [Library docs](/agents/library-docs/) for what is indexed of third-party libraries.

| Question                                | Tool                                          |
| --------------------------------------- | --------------------------------------------- |
| Is there already a helper for this?     | `find_packages`, then `package_api`           |
| What does this package export?          | `package_api` (`symbol` or `query` to narrow) |
| Which versions are there, what changed? | `package_changes`                             |
| How do I use this API at my version?    | `package_docs`                                |
| Is this error a known issue?            | `package_docs` with `issues`                  |
| How is this implemented?                | `package_source`                              |

```text
> Is there a date formatting helper in our packages?

● holtkeeper - find_packages (query: "formatDate")
  ⎿ ## Exports of organization packages
    ### `@acme/fmt-utils` → formatDate (function)
    @acme/fmt-utils@2.4.0, repo `gitlab:acme/fmt-utils`
    Formats a date in the user's locale; `style` defaults to `medium`.
    export function formatDate(value: Date | string, style?: DateStyle): string
    …

● holtkeeper - package_api (package: "@acme/fmt-utils", symbol: "formatDate")
  ⎿ import { formatDate } from '@acme/fmt-utils'
    …
```

```text
> Our build fails with "Cannot read properties of undefined (reading 'shape')" after the zod bump.

● holtkeeper - package_docs (package: "zod", query: "reading 'shape'", issues: true,
                              repo: "gitlab:acme/checkout-web")
  ⎿ 1. closed · fixed in 3.23.4 — "Error reading 'shape' when extending a lazy schema"
       https://github.com/…/issues/…
```

Packages marked **removed** were dropped from their repository; answers about them start with a warning not to use them in new code. Organization packages have no indexed docs: their API and source answer instead. Text from libraries and issues is third-party data; agents are told never to follow instructions in it.

## How the fleet uses a package

A second index records how every repository uses its dependencies: which exports, how (call, JSX, type, member access), which JSX props and which members.

| Question                                  | Tool                                            |
| ----------------------------------------- | ----------------------------------------------- |
| Who uses this package, at which versions? | `package_usage`                                 |
| Show me the code of those uses.           | `package_usage` with `export`, `repo` or `code` |
| What breaks if everyone upgrades to 5.0?  | `package_changes` with `from` and `to`          |
| What does this repository depend on?      | `find_packages` with `repo`                     |

```text
> We want to release @acme/widget-kit 5.0. Who breaks?

● holtkeeper - package_changes (package: "@acme/widget-kit", from: "4.2.0", to: "5.0.0",
                                 include: ["impact"])
  ⎿ @acme/widget-kit 4.2.0 → 5.0.0 (organization package, `gitlab:acme/widget-kit`)
    ## Uses the upgrade affects
    3 repositories affected, 2 already on 5.0.0
    ## gitlab:acme/admin-ui (team platform) — 4 breaking, 2 check
    - breaking: Modal prop `footer` removed — src/orders/ConfirmDialog.tsx:41
        <Modal open={open} footer={<Actions />} onClose={close}>
    - check: Button `size` type changed — src/layout/Toolbar.tsx:12
    …
```

Between two versions `package_changes` returns the API diff, for third-party libraries the changelog and migration notes, and the uses the upgrade affects; `include` narrows it to one part. The impact covers npm packages and Go modules; for Go it sees syntactic uses, plus the methods and fields reached through values (a method called on a returned value) when the usages job has the `go` toolchain.

## Adding or upgrading a dependency

Before an agent adds a dependency, `evaluate_dependency` answers everything the organization knows in one call: who already uses it and at which versions, whether an internal package does the same job, deprecations, advisories with fixed versions, licenses with each repository's verdict, its gzip share of measured bundles, and the team's rules and learnings that mention it.

```text
> Add a date library to checkout-web.

● holtkeeper - evaluate_dependency (package: "moment", repo: "gitlab:acme/checkout-web")
  ⎿ moment — used by 1 repository, deprecated (maintenance mode)
    Team knowledge: [rule:r2f7] Dates in web apps: use date-fns, not moment (rule, team widgets)
    …

● holtkeeper - evaluate_dependency (package: "date-fns", repo: "gitlab:acme/checkout-web")
  ⎿ date-fns — used by 14 repositories, newest 4.1.0; no open advisories; MIT (allowed)
```

## Rules and knowledge

Before changing code in a repository an agent calls `repo_rules` for the rules that apply there. Its `topics` add one convention in full: `commits` before committing (then `check_commit_message` to verify), `test-ids` for UI work (and `test_ids` for the existing ids), `assets` for images, `releases` for the branches, tag format and how commits bump the version. `search_knowledge` searches rules and learnings and reads one in full by `id`. These have their own page: [Rules and knowledge](/agents/rules-and-knowledge/).

## Ask a whole question

Some questions take several tools: what an upgrade breaks here and how to migrate, how the team does something, whether anyone solved a problem before. Where an administrator turned on the `mcp.ask` setting, `ask` hands such a question to an agent on Holtkeeper's side. It reads the same tools with your access and answers in Markdown.

```text
● holtkeeper - ask (question: "What breaks in checkout-web if we move @acme/widget-kit from 4.2.0 to 5.0.0?",
                    repo: "gitlab:acme/checkout-web")
  ⎿ `Modal` lost its `footer` prop in 5.0.0 [pkg:@acme/widget-kit@5.0.0 Modal]. checkout-web
    passes it in one place [file:gitlab:acme/checkout-web src/orders/ConfirmDialog.tsx:41].
    The team's rule is to move actions into `Modal.Actions` [rule:r4c1].

    Sources:
    - [pkg:@acme/widget-kit@5.0.0 Modal]
    - [file:gitlab:acme/checkout-web src/orders/ConfirmDialog.tsx:41]
    - [rule:r4c1]
```

Every statement names where it comes from: a rule or learning (`[rule:<id>]`, `[learn:<id>]`), a package version and export (`[pkg:…]`), a file and line (`[file:…]`), a library document (`[doc:…]`) or a link (`[url:…]`). Holtkeeper checks each source against what the agent actually read. A source nothing backs is replaced by `[unverified]`, so you see which statement to check yourself, and an answer left with no backed source is not returned at all: the tool says `No grounded answer` and names what it looked at.

What to keep in mind:

- It answers from what Holtkeeper indexed. It cannot read your working tree, and it does not search the source of other repositories beyond indexed usages, package source and docs.
- It takes up to 90 seconds and spends the AI budget, so use the direct tools for a single lookup. Clients that support progress see which tools it reads meanwhile.
- Limits are set in `mcp.ask`: a spend cap per answer, questions per person per day and a weekly spend for everyone. Repeating a question within ten minutes returns the earlier answer and is not counted.

## Reviews of your merge request

| Question                                                      | Tool          |
| ------------------------------------------------------------- | ------------- |
| Can Holtkeeper review my merge request, and what did it find? | `code_review` |

After pushing a branch or opening a merge request, an agent offers you a code review and calls `code_review` with the repository and the branch (or the merge request number). One call asks for the review and reports how it stands: if no review covers the newest commit, the tool makes sure one is coming and never starts a second one; a few minutes later the same call returns the verdict and findings with file and line, the Holtkeeper threads still open, and a **Next** section. Without a merge request it says to open one first.

```text
● holtkeeper - code_review (repo: "gitlab:acme/checkout-web", branch: "feat/ABC-123-widget-sizes")
  ⎿ ## gitlab:acme/checkout-web!412 feat(widgets): [ABC-123] add widget sizes
    open · `feat/ABC-123-widget-sizes` → `main` · head 5d6e7f80 · https://gitlab.example.com/…
    **Review: Needs changes** (full, 2026-11-14T09:12:00Z, reviewed 5d6e7f80)
    ### Findings of this run (1)
    - **major** · correctness · `src/widgets/size.ts:18` — **Size falls back to 0** (has a suggestion)
    ### Next
    - Fix the open threads or answer them on the merge request, push, and call code_review again: the next review re-checks them and resolves the fixed ones.
```

See [Ask for a review from your agent](/agents/review-agent/#ask-for-a-review-from-your-agent).

## Tasks

No MCP tool changes code on the forge or follows task groups. Tasks start from Chat, **Roll out** in **Supply chain › Libraries** and **Ops › Tasks**; an agent follows a task's merge request with `code_review` on the task's branch, and people follow the group in **Ops › Tasks**. See [Changing code through tasks](/agents/tasks/).

## Exposed secrets

| Question                                                 | Tool                     |
| -------------------------------------------------------- | ------------------------ |
| A key just showed up in this session; who needs to know? | `report_secret_exposure` |

When a secret of the organization shows up in a session (pasted, printed by a command, read from a file or written by the agent), the agent reports it on its own, without being asked: masked, never the value, without naming anyone. Then it tells the user that the secret should be rotated. Everything in a conversation has already reached the model provider, so the secret counts as compromised.

```text
● holtkeeper - report_secret_exposure (kind: "api-key", identifier: "WIDGET_API_KEY",
                                        masked: "wk_l…(40)", service: "api.example.com",
                                        channel: "command-output")
  ⎿ Reported api-key `WIDGET_API_KEY` (wk_l…(40)) under the user's name. Administrators see it
    on the Secret reports page and rotate it. …
```

The tool is offered unless the token's **Report exposed secrets** choice is **Off**; reports go under your name or anonymously as you chose. See [Secret reports](/guide/supply-chain/secret-reports/).

## When a tool refuses

A tool that needs a permission you lack answers with an error naming it, for example that `audits:read` is missing on a repository. Repositories you cannot see answer the same as repositories that do not exist.
