An agent on your laptop edits the repository in front of it. When a change has to land in other repositories too, or should run on Holtkeeper's workers with the repository's own checks, it becomes a **task**: a task group with one draft merge request per repository on a shared branch. Holtkeeper never merges.

Agents connected over MCP cannot start tasks. The MCP endpoint has no tool that queues code changes, approves a task group or asks for a review; people start tasks in the panel and in Chat. An agent can still help you write the plan you hand over, and follow a task's merge request with `review_status`.

## Where tasks start

| Where                            | How                                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| [Chat](/guide/chat/threads/)     | Ask for a change; Holtkeeper answers with a task card you approve or reject.                                        |
| **Supply chain › Libraries**     | <Ui>Roll out</Ui> an upgrade of a library across the repositories that use it.                                      |
| [Ops › Tasks](/guide/ops/tasks/) | <Ui>New task in Chat</Ui>, and <Ui>Approve</Ui> for groups that wait, such as fixes Holtkeeper's analyzers propose. |
| `POST /api/task-groups`          | Scripts calling the web API with a signed-in session that has `tasks:run`. MCP tokens cannot call it.               |

Whichever way a group starts, the same checks apply before it runs:

- A person with `tasks:run` on every target repository approves it. For another team's repository, that grant must name the repository explicitly; your own team's grant never covers it.
- Write tasks are switched on (**Agents may change code** in **Ops › Tasks**, the `tasks.write` setting, off until an admin turns it on).
- No target repository is read-only (`repo.freeze`).
- This week's write task spend stays under the weekly cap (default $40), and the group under its own cap (default $5). Each repository's task gets at most $1.50 by default, lowered so the group stays within its cap.

## What happens after approval

1. A write worker checks out each repository, makes a branch `holtkeeper/<task id>-<slug>`, lets an agent work with the repository's checks (for JavaScript: install, type check, lint, format, tests; for Go: `gofmt -l` on the changed files, `go vet`, `go test`, and `make lint` or `golangci-lint run`) and commits.
2. A draft merge request opens per repository. Failing checks keep it a draft and list the failing output in the description.
3. People review and merge on the forge. The [review agent](/agents/review-agent/) reviews the merge request when the repository's merge request triggers say so, or when someone presses <Ui>Review a merge request</Ui> on **Quality › Reviews**.

## Hand a change over from your agent

When your agent finds that a change belongs in many repositories, let it do the research over MCP and write the plan, then start the task yourself in Chat.

```text
> Rename the `variant` prop of Badge to `tone` in every app that uses it.

● holtkeeper - package_usage (package: "@acme/widget-kit")
  ⎿ Badge with prop `variant`: gitlab:acme/checkout-web (9), gitlab:acme/admin-ui (14)

● holtkeeper - commit_conventions (repo: "gitlab:acme/checkout-web")
  ⎿ Conventional Commits; types: feat, fix, refactor, …

● Holtkeeper's MCP tools cannot start tasks. Paste this into Holtkeeper Chat to
  propose one:

  Title: refactor: rename Badge variant to tone
  Repositories: gitlab:acme/checkout-web, gitlab:acme/admin-ui
  Plan: In every use of Badge from @acme/widget-kit, replace the `variant` prop
  with `tone` (same values). Do not touch other components.
```

Write the plan so the worker agent can follow it without your conversation: it sees the repository, its Guide and the checks, not your chat.

:::tip
Ask the agent to call `commit_conventions` for each repository and to check the title with `check_commit_message`. The commit message is chosen from the title and the worker agent's suggestions, and the first candidate the repository's conventions accept wins.
:::

## Follow it

There is no MCP tool for task groups. People follow a group in **Ops › Tasks**: each repository's task, merge request, CI and spend. The task's sheet shows the shared branch, `holtkeeper/<task id>-<slug>`.

With that branch, your agent follows a task's merge request like any other: `review_status` reads Holtkeeper's review of it, the open threads and what to fix next. It can also check out the branch and continue the work locally.

```text
● holtkeeper - review_status (repo: "gitlab:acme/checkout-web",
                              branch: "holtkeeper/g5k2qd-refactor-rename-badge-variant-to-tone")
  ⎿ ## gitlab:acme/checkout-web!412 refactor: rename Badge variant to tone
    open, draft · `holtkeeper/g5k2qd-refactor-rename-badge-variant-to-tone` → `main` · …
    **Review:** none yet
    ### Next
    - No review yet: draft merge requests are not reviewed automatically; comment `/holtkeeper review` on the merge request to ask for one.
```

See [Follow a review from your agent](/agents/review-agent/#follow-a-review-from-your-agent).

## What a task never does

- Merge. Merge requests stay drafts until a person decides.
- Start itself. Every group is started or approved by a person; no MCP tool starts, approves or reviews one.
- Read secrets. The worker agent gets the repository and the network through the egress proxy, never credentials; it may run only the detected checks, `gofmt -w` when the checks include `gofmt`, and `git status`, `git diff` and `git log`.
