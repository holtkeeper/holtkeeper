See and change what runs when — schedules, event triggers, merge request policies and freshness — as a list or as a map of every rule per team.

Four kinds of rules queue analyzer runs:

| Rule                 | Fires when                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------- |
| Schedule             | Its cron expression or interval comes due, inside the time windows you allow.               |
| Event trigger        | A push, a tag, a merge request, a label or a newly found repository arrives from the forge. |
| Merge request policy | A merge request event matches its conditions; it can also approve, merge, label or comment. |
| Freshness            | A stored analysis is older than the code or its cadence. Built in, tuned per team.          |

## Read the list

The list is the default view. The toolbar narrows it:

- **Scope switch.** _My teams_ keeps rules that cover every repository or sit in one of your home groups; a picked group keeps rules that cover every repository or sit in that group.
- **Text filter.** Matches a rule's name, id or analyzer.
- **Rule kind.** **Triggers**, **Schedules** (the default), **MR policies** and **Freshness** (with its count of stale analyses), each with its count.
- **Filters.** **Team** everywhere; on Schedules also **Status** and **Problems only**.

**Schedules** opens with a strip: how many schedules are on and paused, the next run, the jobs schedules queued this budget week, and the automatic AI spend of the week with its forecast (the same figures as [AI spend](/guide/ops/ai-spend/)), then the failing, blocked, partly failed and healthy counts. The table shows each schedule's cadence in words with its time zone, teams, analyzers (an **AI** tag marks ones that call a model), the last 14 runs as ticks, health, the last and next run, an on/off switch and <Ui>Run now</Ui>. Other teams' schedules fold into one row.

**Triggers** and **MR policies** list one row per rule with what fires it (or its conditions), its status, teams and actions. A row opens the rule's form in a sheet with **Rule** and **Activity** tabs.

### Schedule health

| Health        | Means                                                                  |
| ------------- | ---------------------------------------------------------------------- |
| Healthy       | The newest finished run succeeded.                                     |
| Partly failed | Some of its jobs failed and some succeeded.                            |
| Failing       | Jobs failed and none succeeded; the tag counts how many runs in a row. |
| Blocked       | The AI budget stopped its jobs.                                        |
| No runs yet   | It never finished a run.                                               |
| Paused        | It is switched off.                                                    |

Runs that queued nothing, or whose jobs were all cancelled, count as skipped and do not change the health.

## Add a schedule

1. Click <Ui>New rule</Ui> and pick the **Schedule** tab.
2. Name it and give it a cadence: a cron expression (`0 3 * * 1-5`) or an interval (`1h`, `2d`), and its time zone.
3. Pick the analyzers, and the groups and repositories it covers. Without groups it covers every top-level group.
4. Optionally limit when it may run, add jitter or spread its jobs.
5. Save. The sheet shows the next five runs, so check them before you leave.

How the time controls behave:

- **Windows.** With allowed windows a run must fall inside one of them; denied windows, skipped nights, weekends and holidays always win. A window whose end is before its start runs past midnight (`Fri 22:00–02:00` covers Saturday 01:00).
- **Moved runs.** A cron run that lands in a denied minute moves to the next allowed minute. Several runs that collapse onto one minute run once, so an hourly schedule with nights skipped runs once at 07:00, then hourly.
- **Intervals** start at the first allowed minute of each allowed stretch of a day and repeat while allowed: `1h` inside 09:00–18:00 runs at 09:00, 10:00, …, 17:00.
- **Jitter** delays each run by a stable random amount, the same in the preview and in real runs.
- **Spread** spaces the repository jobs of one run evenly over the allowed stretch, so 40 repositories do not hit the forge at once.
- **Time zones.** Times stay local across daylight saving changes: a 03:00 run stays at 03:00.

:::tip

<Ui>Run now</Ui> starts a schedule at once, even a paused one, with you recorded as the person who
ran it. It needs `analyses:run`. :::

## Add an event trigger

<Ui>New rule</Ui> › **Event trigger** queues analyzers when the forge reports something:

| Event          | Queues its analyzers when…                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| Push           | a branch matching one of the rule's globs gets new commits. A burst of pushes runs once, for the newest commit. |
| Tag            | a tag is pushed, on the tagged commit.                                                                          |
| Merge request  | a merge request is opened, reopened, gets new commits or leaves draft. Title or description edits do not count. |
| Label          | a given label is added to a merge request, drafts included.                                                     |
| New repository | a repository appears in a group for the first time. A built-in rule runs every read-only analyzer once on it.   |

Each trigger can be limited to some groups. Pushes by Holtkeeper's own bot user, deleted branches and deleted tags never fire.

## Add a merge request policy

A policy is an **If / Then** rule on merge request events. Conditions are all optional and must all hold; actions run in order.

      </Rows>
    </Stack>
  </Split>
</Screen>

| Conditions                                                                                                                                                                                                                   | Actions                                                                                                                                                      |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| event, source and target branch, author (or whether it is a bot), labels present or just added, title pattern, draft state, a `/holtkeeper` command, changed paths, diff size, pipeline state; combine with all, any and not | approve, merge, add or remove labels, comment, close, mark draft or ready, assign reviewers, queue an analyzer, call a webhook; skip analyzers for the event |

- Policies from narrower scopes run first; a policy marked **stop** ends evaluation.
- Approve, merge and comment happen once per head commit, so a redelivered event never approves twice. An approve waits while the pipeline runs and is skipped when it is not green.
- Holtkeeper never approves its own merge requests unless the policy explicitly allows it.
- A repository can switch off or replace a group policy by giving its own entry the same id.

:::note
When [merge request reviews are off](/guide/settings/policies/#merge-request-reviews) for a repository, policy comments and labels are skipped and approvals go out without their summary. Everything else runs as usual.
:::

## Tune freshness

Freshness keeps analyses current without schedules: every analyzer says when its record goes stale (the code changed, or a cadence passed), and a sweep every five minutes queues what is stale. **Freshness** in the list shows tiles for stale, waiting and fresh analyses and the next sweep, then each team:

1. Find the team.
2. Pick **On**, **Slower** (every interval and cadence multiplied by a factor from 2 to 10) or **Off**.
3. To go back to the shared setting, click <Ui>Use the every-repository setting</Ui>.

Pick a team to see which analyzers refresh for it and how. The footer names the sweeper's night window and hourly caps, with a link to [Settings › System](/guide/settings/system/#background-work) to change them.

:::caution
Analyzers that call a model refresh only after they have a record of a commit, wait while automatic work has used the weekly budget minus its reserve, and run at most two an hour by default. Heavy analyzers (coverage, bundles, assets) wait for the night window.
:::

## The map

**Map** draws the same rules on one canvas for one team at a time: that team's rules together with those covering every repository, linked to the events that fire them and the analyzers and actions they lead to.

- The team segments count each team's rules.
- Narrow the canvas by kind (**Triggers**, **Schedules**, **Policies**, **Built in**), with **Calls AI only**, or with text that matches titles, chips and linked events or actions.
- A rule node shows an **AI** tag, _Off_, or a status badge: a failing, partly failed or budget-blocked schedule, or stale freshness.
- Click a node to edit it in the drawer, whose footer (<Ui>Remove</Ui>, <Ui>Discard</Ui>, <Ui>Save rule</Ui>) stays pinned. A schedule also has **Health** and **Activity** tabs and <Ui>Open in the schedules list</Ui>.

<Ui>Show on Automation</Ui> on a run in [Ops › Runs](/guide/ops/runs/) opens the map with a notice
explaining why the job ran and the path that could have queued it highlighted, on the job's team.

## Who can do what

Seeing Automation needs `settings:read` over everything. Saving rules, switching schedules and changing freshness need `settings:write`; <Ui>Run now</Ui> needs `analyses:run`. <Ui>Configure</Ui> opens [Settings › Analyzers](/guide/settings/analyzers/), where every analyzer's state is read from these rules.
