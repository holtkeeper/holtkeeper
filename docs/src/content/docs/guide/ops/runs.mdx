## Find a run

The page lists the runs of every repository you can read. Three ways to narrow it:

- **Scope switch.** _My teams_ keeps the repositories of your home groups, a picked group keeps that group's, and the widest setting shows everything you may read. A repository picked in the **Repository** filter wins over the scope.
- **Segments.** **All**, **Failures** (failed runs) and **Queue** (queued runs), each with its count. Failures and Queue fix the status, so switching to them drops the **Status** filter.
- **Filters and search.** **Status** (in All only), **Analyzer**, **Repository** and **Trigger** pick one value each. Press <Kbd>/</Kbd> to search by run id prefix, repository or group, analyzer kind or label. The search covers every run you may read, not only the loaded pages, and the footer counts the matches.

A link from Automation adds a **schedule** chip, and a recurring failure adds a **failure signature** chip; remove either with its ×. Filters live in the URL, so <Ui>⋯</Ui> › <Ui>Copy link</Ui> shares the same view.

## What the table shows

| Column           | Meaning                                                                                                     |
| ---------------- | ----------------------------------------------------------------------------------------------------------- |
| Status           | Queued, running, finished, failed, cancelled, or blocked by the AI budget.                                  |
| Analyzer         | The analyzer, with a line under it (see below).                                                             |
| Repository · ref | Where it ran: a branch, a tag or a merge request head.                                                      |
| Trigger          | The schedule name, the person who started it, or the event (push, tag, webhook, freshness, new repository). |
| Duration         | From start to finish.                                                                                       |
| Tries            | Attempts out of the most allowed; amber after a retry.                                                      |
| Cost             | What the run's AI agents spent; `—` when it called no model.                                                |
| Started          | When it started, or _waiting 2 min 10 s_ and _due in 5 minutes_ for a queued run.                           |

The line under the analyzer says what matters most about the run: why a queued run still waits (its first reason, or that it waits for a free worker with N runs ahead), _Stopped by the AI budget_ for a blocked run, the failure signature or first error line of a failed run, and the last failed attempt of a run that was retried. The footer counts the shown runs and loads older pages.

- **Workers** shows each live worker with how many runs it is busy with and its newest heartbeat. You see it only with `analyses:read` over everything; an empty list means no worker announced itself recently.

:::tip
A long queue with no busy workers means no worker is running. Runs that sit in the Failures segment as _blocked by budget_ were stopped by the weekly AI budget; see [AI spend](/guide/ops/ai-spend/).
:::

## Start a run by hand

1. Click <Ui>Run analyzer</Ui> in the header.
2. Pick the analyzer and where it should run.
3. Start it. The run joins the queue like any other, with you as its trigger.

<Ui>Run analyzer</Ui>, <Ui>Run again</Ui> and <Ui>Cancel run</Ui> need `analyses:run`.
<Ui>Configure</Ui> (with `settings:read`) opens [Settings › Analyzers](/guide/settings/analyzers/),
on the filtered analyzer's sheet when the **Analyzer** filter is set.

## Deal with recurring failures

Under the table, in All and Failures, **Recurring failures** groups failed runs by analyzer and error signature over 24 hours, 7 days or 30 days.

- Click a row to switch to Failures filtered to that analyzer and signature.
- Click the id to open the latest run with it.
- <Ui>All failures</Ui> switches to the Failures segment.

:::note
A failure that hits many repositories at once usually has one cause outside them: an expired token, a registry outage, or a tool missing on the workers. Open one run, read its log, then use <Ui>Runs with the same failure</Ui> to see how far it spread.
:::

## Why a run ran

<Ui>Show on Automation</Ui> in a run's Steps tab opens the [automation
map](/guide/ops/automation/#the-map) with the path that could have queued the run highlighted: the
schedule, trigger, policy or freshness rule behind it. Coding agents ask the same question over MCP
with `why_job` and `job_log` ([MCP tools](/reference/mcp-tools/)).
