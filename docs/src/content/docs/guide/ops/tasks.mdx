Approve, follow and retry agent tasks that change code in one or many repositories, each ending in a draft merge request, and decide whether agents may write code at all.

A **task** is one request ("bump `@acme/widget-kit` to 6.0 and fix the breaking calls"). It becomes one task per repository, and each opens a draft merge request. Tasks come from Chat, from coding agents over MCP and from Holtkeeper itself (fixes and upgrades).

## Let agents change code

Agents write code only while the instance-wide switch **Agents may change code** is on. The block above the list shows it with an _On_ / _Off_ tag, who changed it last and when, and a link to the [Audit log](/guide/settings/audit-log/).

To turn it on:

1. Click the switch. A confirmation names the risks.
2. Read them: repository scripts run on write workers without a sandbox and can read the worker's environment and other checkouts; merge requests go out under the bot with the forge token; a wrong change can reach many repositories at once; tasks spend from the weekly AI budget.
3. Confirm. Turning it off saves at once and holds queued tasks.

The switch needs `settings:write` over everything.

:::caution
Keep the switch off until checks run in an isolated sidecar. A task that runs the repository's own install and test scripts can do anything those scripts can do on the worker.
:::

Next to the switch:

- **Write pool**: its state (_Turned off_, _Idle_, _Working_, or _No write worker_ when a task waited over five minutes with nothing running), busy against live workers, queued and running counts, the oldest wait and the last start.
- **This week's write spend** against the weekly cap, linking to [AI spend](/guide/ops/ai-spend/).
- **Caps**: per repository, per task, repositories per task and weekly. <Ui>Edit caps</Ui> opens the editor for them.

## Approve a task

Groups with a task still proposed sit in **Needs approval**; nothing runs until someone approves. The **Tasks** tab shows how many wait for you as a badge, and the same groups appear in the [Inbox](/guide/home/inbox/) (_Also in Inbox_ on the section header).

1. Open the group and read its **Plan**: the plan or request, the expected diff per file and the repositories with their spend caps.
2. Click <Ui>Approve</Ui>. The confirmation names the spend cap.
3. Confirm. The tasks queue on the write workers and move to **Running**.

<Ui>Reject</Ui> asks first, then cancels the proposal. Both buttons show only to people who may
decide: `tasks:run` on every repository of the group. Approval cannot be confirmed while **Agents
may change code** is off.

## Follow and fix tasks

Groups move through sections as their tasks go:

| Section        | A group is here when…                                                                              | Row action                                 |
| -------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Needs approval | a task is still proposed.                                                                          | <Ui>Approve</Ui>, <Ui>Reject</Ui>          |
| Running        | tasks are approved, queued or running; the caption counts repositories on workers and queued ones. | <Ui>Cancel</Ui> (asks first)               |
| Opened MR      | merge requests are open and nothing failed; the caption counts drafts.                             | opens the first merge request on the forge |
| Failed         | a task failed and none still works, even with other merge requests open.                           | <Ui>Retry</Ui>                             |
| Ended          | everything is done or cancelled.                                                                   | —                                          |

**Progress** reads _0 of 5_ before anything starts, _2 of 2_ once every repository has a merge request, else a mix such as _1 MR · 1 running · 1 queued_. **CI** shows the most pressing pipeline state among the group's merge requests (failed, running, pending, canceled, passed, no pipeline) and how many share it when they differ: _Failed · 1 of 3_. **Spend** shows the cap as _≤ $10.00_ while waiting for approval.

<Ui>Retry</Ui> queues every failed or cancelled task of the group again without asking, since the
group was approved before.

### Narrow the list

The scope switch keeps groups that touch your home groups' repositories (_My teams_) or one picked group's. The text filter (<Kbd>/</Kbd>) matches the title, a repository, a merge request like `!12` or the start of an id. **Open**, **Ended** and **All** switch the view; **Kind**, **Source**, **Repository** and **Proposed by** offer the values of the groups in scope.

## Start a task

<Ui>New task in Chat</Ui> opens [Chat](/guide/chat/threads/), where you describe the change and
Holtkeeper proposes the task. Coding agents start tasks with the `start_task` MCP tool and poll
`task_status` ([Agent tasks](/agents/tasks/)). <Ui>Configure</Ui> opens [Settings ›
AI](/guide/settings/ai/).

:::note
Every task spends from the same weekly AI budget as reviews and chat. Its own caps stop it earlier: by default $1.50 per repository and $5 per task, both changed with <Ui>Edit caps</Ui>.
:::
