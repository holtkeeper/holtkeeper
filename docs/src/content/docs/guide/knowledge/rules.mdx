Write the rules every agent run follows, for all repositories, for teams or for repository patterns, see the rules files your repositories already carry, and check the exact block a review or task gets.

Reviews, replies in review threads, agent tasks, chat, release notes and coding agents over MCP all read the same rules. They come from three places, strongest first: **rules** people write here, the repository's own **rules files**, and **learnings** Holtkeeper picked up from review replies (see [Learnings](/guide/knowledge/learnings/)). Your [policies](/guide/settings/policies/) are added as plain facts.

The design follows the conventions of `AGENTS.md`, GitHub Copilot instructions and Cursor rules: Markdown rules, scoped by paths, with the same activation modes. A team that already keeps those files gets them read as they are.

## Repository rules files

Holtkeeper reads these files from the repository: from the review's checkout, or from the default branch for chat, release notes and the effective prompt. They are read-only here; edit them in the repository.

| File                                          | Applies                                                                                            |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `REVIEW.md`, `AGENTS.md`, `CLAUDE.md` (root)  | Always.                                                                                            |
| `.github/copilot-instructions.md`             | Always.                                                                                            |
| `CONTRIBUTING.md`                             | Always.                                                                                            |
| `AGENTS.md`, `CLAUDE.md` in a folder          | To files under that folder.                                                                        |
| `.github/instructions/*.instructions.md`      | `applyTo` globs; `excludeAgent: code-review` keeps it out of reviews, `coding-agent` out of tasks. |
| `.cursor/rules/*.mdc`, `.continue/rules/*.md` | `alwaysApply`, `globs`, or only a `description` (offered on request).                              |
| `.claude/rules/*.md`                          | `paths` globs, otherwise always.                                                                   |
| `.windsurf/rules/*.md`                        | `trigger`: `always_on`, `glob`, `model_decision` (on request); `manual` is skipped.                |

Files under `node_modules`, `vendor`, `dist` and `build` are ignored. Root files share at most 4,800 characters; a longer one is cut at a line break with a pointer to the file. `REVIEW.md` keeps its `## Paths` and `## Ignore` sections for reviews, see [Reviews](/guide/quality/reviews/).

```md title=".github/instructions/routes.instructions.md"
---
applyTo: 'src/routes/**'
---

- Every new route needs a contract test in `test/contract/`.
- Return errors through `problem()`, never a bare `Response`.
```

:::tip
Rules that hold for one repository belong in its own files, where they are versioned with the code. Use panel rules for what spans repositories: the whole organization, a team, or alike repositories such as `acme/*/web`.
:::

| Field       | Meaning                                                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rule        | Markdown. Write short imperative lines an agent can follow, and say why when it is not obvious.                                                               |
| Scope       | _All repositories_, one or more _teams_ (a team is its set of repositories, see [Teams](/guide/repos/teams/)), or _repository patterns_ such as `acme/*/web`. |
| Files       | Optional path globs. The rule applies only when the task touches a matching file.                                                                             |
| Agents      | Optional. Limit the rule to **Review**, **Agent task**, **Chat** or **Release notes**; empty means all of them.                                               |
| Description | Optional. A rule with only a description is not injected: agents see it listed and read it when it fits the task. **Always apply** keeps it injected.         |

So a rule reaches a prompt in one of three ways, as in Cursor: **always**, **when a touched file matches**, or **on request** by its description.

:::caution
Saving checks the version you started from. If someone saved the rule in the meantime, your save is refused; reload, merge and save again.
:::

**History** lists earlier versions with who saved them, each with <Ui>Restore</Ui>.

## Policies

Some facts are settings, not prose, and reach agents as plain lines next to the rules: a repository with **no tests by design**, the test id convention and the [asset policy](/guide/quality/assets/) (reviews and tasks), and commit conventions (release notes, tasks and chat). Edit them in [Settings › Policies](/guide/settings/policies/).

1. Pick the repository, the run (**Review**, **Agent task**, **Chat** or **Release notes**) and, optionally, the touched files.
2. Read **Blocks**, **Full text** (the block as sent) or **Warnings** (what was cut and why).

Blocks come in this order:

1. Panel rules that always apply, broadest first: all repositories, teams, repository patterns.
2. Root rules files.
3. File-scoped panel rules, then nested and file-scoped rules files, that match the touched files. Without touched files, all of them, each titled with the paths it covers.
4. Policies.
5. **Learned rules**, under their own heading, best ranked first. Agents follow them unless a rule above says otherwise.

Everything shares **12,000 characters**. Rules files get at most 4,800 together and are cut with a pointer; learned rules get at most 3,000 and are dropped whole, lowest ranked first. Each block shows its size and **cut** when the budget shortened it. Rules offered on request are listed separately under the blocks.

Agents cite what they followed: `[rule:<id>]` for a rule, `[learn:<id>]` for a learning. A review comment that cites a learning counts as a use of it.

<Ui>Copy text</Ui> copies the block as sent.

## In a repository or team

The repository hub's **Knowledge** tab shows the repository's effective prompt and the rules and learnings that apply to it. The team page's **Knowledge** tab lists the rules scoped to the team.
