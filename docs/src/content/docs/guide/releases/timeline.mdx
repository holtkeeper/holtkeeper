## Pick a repository

The title holds a repository switch over the repositories on the [overview](/guide/releases/overview/). Opened without one, the page shows the first repository that needs action. Search with <Kbd>/</Kbd> to narrow the versions table by tag, version, commit or task key.

- <Ui>Configure</Ui> opens the repository's [flow setup](/guide/releases/flow-setup/); you need
  `settings:write` there.
- <Ui>⋯</Ui> has <Ui>Read the forge again</Ui> and <Ui>Open repository</Ui>.

Above the next release you may see a notice: a dry run (steps change nothing), a read-only repository, or releases turned off with <Ui>Set up its flow</Ui>. Then come the stage tag, in the same words as the overview, the flow in one line (mode, target branch, an example tag) and links to the current release merge request, compare view, tag and pipeline.

## Prepare the next version

The next release card shows the pending step: the version when the target branch has unreleased changes, the release merge request when the source branch is ahead, with a switch when both wait.

### Version

The bump row shows current → next version, the bump, the number of commits and how long the version has waited, then the reasons from the commit messages. Bumps follow Conventional Commits: a breaking change bumps the major (the minor while the major is 0), `feat` the minor, anything else the patch.

<Ui>Change version</Ui> picks a patch, minor or major bump, or a custom version.

- **Changes** are grouped by type; left-out ones are counted. <Ui>Edit entries</Ui> includes, leaves out or renames entries, and shows the result at once.
- **Tasks** lists the tracker keys named by the commits (`ABC-123`) with their status when a tracker is connected.
- **What changed** holds the notes: a digest of the changelog by default. <Ui>Write with AI</Ui> drafts them, you can edit them, or go back to the digest.

:::tip
The audience, language and tone of AI notes come from the **Releases** section of the repository's [Guide](/guide/knowledge/guide/), not from a setting here.
:::

### Gates

The checklist lists every gate with a pass or fail mark and how much it matters:

| Severity | Effect                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| blocks   | A failing one refuses the step unless someone overrides it in the confirmation. Nothing to release and a taken version can never be overridden. |
| warns    | Shown, never refuses. The changelog gate warns when some entries are not Conventional Commits.                                                  |
| info     | For your information, such as a branch without a pipeline.                                                                                      |

A failing acceptance gate says how to accept in this flow.

## Accept and create the version

When the flow asks for an acceptance, the version waits until someone accepts the current head of the target branch. An acceptance holds for that head only; new changes need a new one.

1. Review the changes, tasks, notes and gates.
2. Choose <Ui>Accept v8.3.0</Ui>. It appears only while the version waits for acceptance and you have `releases:run`. **Accepted by** now shows your name, where and when; <Ui>Withdraw</Ui> takes it back.
3. Choose the step's button: <Ui>Create v8.3.0</Ui>, <Ui>Open release MR</Ui> or <Ui>Update !231</Ui>.
4. Read the confirmation. It lists what will happen, previews the text, offers AI notes for a release merge request and asks you to override any failing gate that blocks.

The step's button stays off while a gate nobody may override fails or the version waits for acceptance; the reason is written beside the buttons. Other ways to accept, set in the flow: a `release-accepted` label on the merged release merge request, the merge itself, or a CI job calling the API.

A card shows the latest version's deploy status there, the version that runs now, the job, its order (right after the tag or after another environment, and whether it asks first) and the newest attempt with its link and duration. With `releases:run` it offers <Ui>Deploy</Ui>, <Ui>Retry</Ui> or <Ui>Deploy again</Ui>.

Environments that ask first, environments still waiting for an earlier one, retries and repeats go through a confirmation that takes a reason. The reason is kept on the attempt and in the history. Deploying before an earlier environment succeeded needs an explicit override.

:::note
Deploys run the manual jobs of the tag pipeline, and only when a person starts them. Holtkeeper follows a deploy for up to 12 hours.
:::
