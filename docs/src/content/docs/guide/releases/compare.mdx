Pick any two versions of a repository, or a version and the target branch, and see what changed between them: the tasks, the grouped changelog, the npm and Go dependency changes, the public API of the repository's own packages and, on request, an AI description and an AI breaking-change check. Use it to answer _will something break if we upgrade from A to B_, for example before upgrading an environment that runs an old version.

## Pick the two ends

Open **Compare** from the Releases tabs, <Ui>Compare versions</Ui> on the [timeline](/guide/releases/timeline/) or in a version's sheet (from the previous version to that one). The title holds the same repository switch as the timeline.

- <Ui>From (older)</Ui> lists every version tag, newest first; prereleases are marked.
- <Ui>To (newer)</Ui> lists the target branch, captioned _target branch — unreleased_, then the same
  tags. With the target branch the page shows what waits for the next version.
- The swap button exchanges the ends. A warning appears when <Ui>From</Ui> is newer than <Ui>To</Ui>.

Without a choice the page compares the latest stable version with the stable version before it. Picking another <Ui>To</Ui> moves <Ui>From</Ui> to the version before it (the latest version for the target branch); picking <Ui>From</Ui> keeps <Ui>To</Ui>. The two ends are always in the address, so a copied link shows the same range later.

Anyone who can read the repository's releases sees a running or finished description in **What changed**. <Ui>Describe changes</Ui> needs `releases:run` on the repository and an AI agent configured for it. A finished description is shown as it is, with no button to run it again; between two versions it is kept, so opening the comparison later costs nothing. When the range ends at the target branch and new commits land while a description runs, the page keeps showing that description for an hour. Descriptions and breaking-change checks are written in the **language** option of [AI reviews](/guide/quality/reviews/), English when none is set; code, versions and package names stay as they are. After you change that language, a kept description or check in the old language is not reused.

When dependencies cannot be read, for example because the forge cannot compare the two ends, a muted line says why. A lockfile that could not be read at one end shows as a warning above its root, and the rest of the comparison still appears.

## Check what could break

The <Ui>Breaking-change check</Ui> card answers whether an installation running <Ui>From</Ui> can move to <Ui>To</Ui> safely. Press <Ui>Check what could break</Ui>: Holtkeeper splits the changed files into up to eight areas, and one AI agent per area reads its diff together with the public API and dependency changes, looking for removed or changed APIs, configuration, data and migration changes, behavior changes and infrastructure changes. A last step merges the findings and writes a verdict.

- The check runs as a background job and takes a few minutes; the card shows its progress and links to the run. It costs AI budget, so it never runs on its own.
- The verdict is <Ui>Safe to upgrade</Ui>, <Ui>Review before upgrading</Ui> or <Ui>Breaks</Ui>. Findings are grouped by severity, each with the files involved, what it affects and how to check it.
- A finished check is kept for those two commits and shown to everyone who opens the same range. <Ui>Run again</Ui> starts a fresh one; after a failed first run the button stays <Ui>Check what could break</Ui>. A target branch that got new commits is a new range.
- An area whose agent gave no usable answer is listed as not checked, and the verdict is then at least <Ui>Review before upgrading</Ui>. <Ui>Breaks</Ui> always comes with at least one breaking finding.
- Each check has a spend limit; an agent that reaches its share answers with what it found so far.
- Lockfiles, generated, vendored and binary files are left out; the card says how many files no agent read.

The button needs `releases:run` on the repository and an AI agent configured for it.

## Public API and dependency details

<Ui>Public API</Ui> compares the stored public API snapshots of the repository's own packages at
both ends. A package whose exports lost something is marked <Ui>breaking</Ui>; a red <Ui>bumped</Ui>
tag means the version number moved less than the changes call for. Open a package for the full diff
and the uses in other repositories it touches.

Snapshots exist only for releases the public API analyzer has seen. When one end has none, nothing is compared: the section says <Ui>Cannot compare</Ui> and names the packages. With `analyses:run`, <Ui>Snapshot</Ui> queues snapshots of exactly the missing versions. The section shows each one as it waits and runs, and the comparison once they finish, with no reload needed. A failed snapshot shows its error, and the button retries it even while another version is still being snapshotted. When the target branch is the end without a snapshot, the section shows its default-branch run while it waits or runs. When nothing is recorded yet and the button is <Ui>Analyze past releases</Ui>, the section lists the snapshot jobs that backfill queues as they appear. Progress shows only to people who can read the repository's analyses. Without access to the repository's API catalog the section shows an error instead.

In <Ui>Dependencies</Ui>, <Ui>What changed</Ui> on an updated or added package shows what changed in it between the two versions: its API diff, for third-party packages the release notes and migration notes, and the uses in this repository the upgrade affects.
