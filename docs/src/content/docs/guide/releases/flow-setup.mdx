## Open the setup

Open **Releases › Flow setup**, or <Ui>Configure</Ui> on a repository's timeline, or <Ui>Set up releases</Ui> on the overview. Without a repository the page shows a picker of the repositories you may configure. The CI page's **Release gates** and the repository hub's **Releases** tab link here too.

Nothing is tagged or deployed from this page; it only edits the repository's `releases` setting.

| You see          | When                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------- |
| A wizard         | The repository has no `releases` setting yet: three steps, **Flow**, **Versions**, **Environments**. |
| One editing page | It is configured: **Releases on**, Flow, Versions and changelog, and Environments on one page.       |
| Read-only lines  | You do not have `settings:write` on the repository: the effective flow, nothing to edit.             |

## Start from the suggestion

The wizard reads the repository from the forge as soon as it opens: merge requests, tags, labels, `CHANGELOG.md`, commit messages, pipelines and protected branches. A notice names the suggested mode and why.

1. Read the suggestion and, below it, **What we read**.
2. Choose <Ui>Use it and turn releases on</Ui> to apply the suggestions, turn releases on and save in one go, or <Ui>Review the suggestions first</Ui> to only fill the draft and walk through the steps.
3. A field the checks refuse opens its step instead of saving.

On a configured repository, detection runs only when you ask with <Ui>Read the forge</Ui> (or <Ui>⋯</Ui> › <Ui>Read the forge again</Ui>); the button is then <Ui>Use the suggestions</Ui>.

| Mode          | How the repository releases                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Merge request | A release merge request brings the source branch (default `development`) into the target. The version is created on the target afterwards. |
| Trunk         | Work lands on the target directly; versions are tagged on it.                                                                              |
| External      | Another tool, such as changesets or release-please, releases the repository. Versions and deploys are shown; steps are off.                |

Acceptance says what the version waits for, so you can tie it to your own QA or sign-off:

| Acceptance | The version waits for                                             |
| ---------- | ----------------------------------------------------------------- |
| None       | Nothing; the version can be created at once. The default.         |
| Manual     | A person in the panel, or a CI job calling the API.               |
| Label      | The `release-accepted` label on the merged release merge request. |
| Merge      | The release merge request being merged.                           |

A person can accept in every mode.

## Versions and changelog

<Screen title="Releases › Flow setup › Versions">
  <Fields>
    <Field label="Scheme" value="Semantic (1.4.2)" />
    <Field label="Tag format" value="v{version}" mono />
    <Field label="Release candidates first" toggle={false} value="1.3.0-rc.1, rc.2, …" />
    <Field label="Prepend to CHANGELOG.md" toggle={true} value="On the target branch" />
    <Field label="Leave out commit types" value="ci, chore" mono />
    <Field label="Tracker URL" value="https://tracker.example.com/browse/{id}" mono />
  </Fields>
</Screen>

- **Scheme**: semantic versions, or calendar versions as `YYYY.MM.MICRO`.
- **Tag format** wraps the version and must contain `{version}`; the default is `v{version}`.
- **Release candidates** tag `1.3.0-rc.1`, `rc.2` and so on before the version.
- **CHANGELOG.md**: each version's notes are committed on top of the file.
- **Leave out commit types**: entries of these types are left out of the changelog.
- **Tracker URL** turns keys like `ABC-123` into links; `{id}` stands for the key.

The bump, the changelog grouping and the texts of merge requests, tags and releases are fixed. The style of AI notes is a rule in the **Releases** section of the [Guide](/guide/knowledge/guide/).

## Environments

Each environment has a name, a job (a glob over the tag pipeline's manual jobs), the environment it deploys after, and whether it asks for confirmation first.

1. Choose <Ui>+ Environment</Ui>. New environments are named `staging`, then `production`, then `environment-N`, and deploy after the last one.
2. Set the job and, if needed, change **After** and **Asks first**.
3. Rename freely: environments deployed after it follow the new name. Removing one clears the **After** of the ones that followed it.

The step also shows the release webhooks read-only: their scope and last change, never their URLs. <Ui>Manage in Settings</Ui> opens [Settings › Integrations](/guide/settings/integrations/).

## Save

- In the wizard, <Ui>Back</Ui> and <Ui>Continue</Ui> move between steps; the last step has <Ui>Save the flow</Ui> and **Turn releases on when I finish** (on by default). After saving, the repository's [timeline](/guide/releases/timeline/) opens.
- On a configured repository, <Ui>Save</Ui> in the header is enabled once the draft differs; <Ui>⋯</Ui> › <Ui>Start over</Ui> discards the draft.

The draft stays in the page until you save. Saving writes the repository's own `releases` entry, or creates one scoped to just this repository.

:::caution
Save refuses a missing source branch, a target equal to the source, a tag format without `{version}`, and empty or duplicate environment names. The page jumps to the first step with an error, marked **fix**.
:::
