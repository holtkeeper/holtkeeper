## What the table shows

One row per library that a repository you can read depends on, from the newest dependency and usage records. Opening the page reads stored records only: no registry, forge or model is called.

| Column          | Meaning                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Library         | Name, ecosystem (npm or Go) and an `internal` tag for packages one of your own repositories publishes.                        |
| Versions in use | The exact versions repositories resolve, drawn as a bar tinted by how many majors each is behind.                             |
| Repos           | How many repositories use it.                                                                                                 |
| Latest          | The registry's newest release; for an internal package, the version in its own repository.                                    |
| Behind          | Breaking releases behind latest: majors, and minors while the version is below 1.0.                                           |
| Advisories      | Open vulnerability advisories from the latest audits, with the worst severity. See [Security](/guide/supply-chain/security/). |
| Update MRs      | Open update merge requests for the library.                                                                                   |

The segments above the table narrow it: **Third-party**, **Behind a major**, **Advisories**, **Update MRs** and **Internal**, plus an ecosystem switch; each carries its count. Every column sorts, and the filters, sort and open row live in the URL, so a link shows the same view.

Under _My teams_ the versions and the behind figures are recomputed for your teams' repositories; other teams fold into one row at the end. <Ui>⋯</Ui> › <Ui>Export CSV</Ui> downloads the rows on screen.

:::note
Advisories show only for repositories you may read audits of (`audits:read`), and team decisions only with `knowledge:read`. Everything else follows your catalog reach.
:::

## Inspect a library

Click a row, or move with <Kbd>J</Kbd> / <Kbd>K</Kbd> and press <Kbd>↵</Kbd>. The side sheet shows the version mix in its header and four tabs.

| Tab      | What it shows                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overview | Latest, ecosystem, license, links and description; team decisions; versions in use; advisories; licenses with their verdicts; bundle shares; indexed versions; update merge requests. |
| Upgrade  | The badge counts repositories not on the target yet. Pick from and to versions and see the affected uses or API changes, and the changelog.                                           |
| Used by  | The badge counts repositories using it. Who uses it, on which version, and which exports, props and members.                                                                          |
| Docs     | A search over the library's indexed documentation.                                                                                                                                    |

The header's quiet actions: <Ui>Plan upgrade</Ui> opens the Upgrade tab (needs `tasks:run`), <Ui>Copy as prompt</Ui> copies an upgrade prompt naming the target version and the repositories behind it, ready to paste into a coding agent. Internal packages also have <Ui>⋯</Ui> › <Ui>Public API</Ui>. <Ui>Open as page</Ui> opens the full library page.

## Check what an upgrade breaks

1. Open the library and go to **Upgrade**.
2. Pick **From** (default: the oldest version in use) and **To** (default: latest).
3. Read the affected uses. Each is one of three levels:

<Screen title="Supply chain › Libraries › some-lib › Upgrade">
  <Toolbar title="Upgrade">
    <Tag mono>From 4.2.0</Tag>
    <Tag mono>To 5.1.0</Tag>
    <Button>Copy as prompt</Button>
  </Toolbar>
  <Scroll>

| Level                             | Export        | Change                     | Repositories                         | Uses |
| --------------------------------- | ------------- | -------------------------- | ------------------------------------ | ---- |
| <Tag tone="bad">Breaking</Tag>    | `createStore` | removed                    | `acme/checkout-web`, `acme/admin-ui` | 14   |
| <Tag tone="bad">Breaking</Tag>    | `Widget`      | changed · lost prop `size` | `acme/admin-ui`                      | 3    |
| <Tag tone="warn">Check</Tag>      | `Widget`      | changed                    | `acme/checkout-web`                  | 21   |
| <Tag tone="info">Deprecated</Tag> | `fooUtil`     | deprecated                 | `acme/docs-site`                     | 2    |

  </Scroll>
</Screen>

| Level      | When                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------- |
| Breaking   | The export was removed, or a use touches a member or prop the new declaration no longer has. |
| Check      | The declaration changed, but the use does not touch anything that disappeared.               |
| Deprecated | The export is newly marked deprecated.                                                       |

Repositories already on the target version are left out. Use-level impact covers npm packages whose code a `usages` analysis has read; for other libraries the tab shows the API changes and the changelog instead, and says why a part is missing.

:::caution
Impact reads uses Holtkeeper found in code. Uses through local wrappers, re-exporting barrels or values typed as `any` can stay invisible, so treat an empty list as "nothing found", not as a guarantee.
:::

## Roll out a version

With `tasks:run`, the library page's primary <Ui>Roll out 5.0.0</Ui> upgrades every repository in scope that is below the target.

<Screen title="Supply chain › Libraries › @acme/widget-kit › Roll out">
  <Stack>
    <Toolbar title="Roll out @acme/widget-kit 5.0.0" />
    <Rows>
      <Row title="acme/checkout-web" sub="4.3.2 → 5.0.0" />
      <Row title="acme/docs-site" sub="4.3.2 → 5.0.0" />
      <Row title="acme/storefront" sub="4.1.0 → 5.0.0" />
      <Row title="acme/partner-portal" sub="4.3.2 → 5.0.0" />
    </Rows>
    <Fields columns={1}>
      <Field label="Spend cap" value={'$2.00 per repository'} hint="From the write task settings" />
    </Fields>
    <Toolbar>
      <Button ghost>Cancel</Button>
      <Button primary>Roll out</Button>
    </Toolbar>
  </Stack>
</Screen>

1. Open the library page and choose <Ui>Roll out</Ui> with the version.
2. Check the list of repositories and the spend cap.
3. Confirm. Holtkeeper starts one upgrade task group: one draft merge request per repository, written by an agent.

The dialog says so when write tasks are off or when more repositories are in scope than one rollout allows. Follow the tasks in [Ops › Tasks](/guide/ops/tasks/) or your [Inbox](/guide/home/inbox/).

:::tip
Narrow the scope first (the scope switch or **Group**) to roll a version out team by team.
:::

## Third-party documentation

The **Docs** tab and the API of third-party libraries come from the library index, which keeps a few versions of every npm package and Go module your repositories use: the ones in use and the ones an upgrade would land on. Agents read the same index over MCP. Setup and coverage are in [Library docs for agents](/agents/library-docs/); the index's state is in [Settings › System](/guide/settings/system/).
