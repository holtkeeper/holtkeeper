## What the table shows

One row per repository with pipelines in the last 30 days, from its newest CI record. The analyzer reads finished jobs from the forge once a day and keeps their history, so later runs only fetch what is new.

| Column     | Meaning                                                                                  |
| ---------- | ---------------------------------------------------------------------------------------- |
| Repository | Opens the repository hub at Quality › CI; its groups and branch sit under the name.      |
| Status     | **Failing**, **Flaky**, **Slower**, **Healthy** or **Idle** (no pipeline in the window). |
| Median     | Median pipeline time of passing pipelines on the default branch.                         |
| Change     | How the median moved. `↑ 12% slower` reads as bad; changes under 5% stay neutral.        |
| Trend      | A sparkline of the last 8 weekly medians.                                                |
| p90        | The pipeline time 9 in 10 passing pipelines stay under.                                  |
| Success    | Share of pipelines that passed.                                                          |
| Flaky      | Jobs that passed only on retry.                                                          |
| Queue      | Median time jobs waited for a runner.                                                    |
| Pipelines  | Pipelines in the window, and the age of the last one.                                    |

**Status** filters by state and **Problems only** hides healthy and idle repositories. The scope switch (_My teams_ folds other teams' rows into one row with their failing, flaky and healthy counts) and the header search narrow by team, path or group. Headers re-sort, and filters live in the URL.

:::note
Pipeline time is how long any job of the pipeline was running, retries included. Idle gaps, such as a manual job started days later, do not count, so it can differ from the forge's own pipeline duration.
:::

## How jobs are judged

| Problem | When                                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Failing | The job fails in 10% or more of its runs, with at least two failures. Jobs allowed to fail never count.                                     |
| Slower  | The median of the last two weeks is at least 20% and 15 seconds above the rest of the window, with at least five passing runs on each side. |
| Flaky   | The job passed only on retry in two or more pipelines.                                                                                      |

A repository is **Failing** when a job keeps failing, else **Flaky**, else **Slower**, else **Healthy**. For slower jobs Holtkeeper finds the day the slowdown started and links the first run of that day, so you can see which commit did it.

| Tab         | What it shows                                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overview    | Job duration by stage (one bar per job in run order, median solid over p90, with problem tags), up to five problem jobs with a reason and a link to the run, the pipeline numbers, and pipeline time per week as a chart. |
| Jobs        | Every job with median, p90, change, failure rate, passes on retry, runs, problem tags and a link to the last run.                                                                                                         |
| Problems    | The problem list, then jobs flagged with other problems.                                                                                                                                                                  |
| Reliability | Jobs that failed or passed only on retry, worst failure rate first.                                                                                                                                                       |

Problem reasons read like "fails in 23% of runs", "+40% since 12 Oct (1m 40s → 2m 20s)" or "passed only on retry in 3 pipelines".

<Ui>Re-read pipelines</Ui> runs the CI analyzer for the repository at once (it needs
`analyses:run`). <Ui>Release gates</Ui> appears when the repository's releases wait on CI and opens
[Releases › Flow setup](/guide/releases/flow-setup/); the release-gate fact in Overview needs
`releases:read`. <Ui>⋯</Ui> › <Ui>Open repository</Ui> goes to the hub, and <Ui>Open as page</Ui> to
the [analysis record](/guide/quality/analysis-record/).

:::tip
A sheet that says the record is in an older format offers <Ui>Run now</Ui>. One run brings it up to date.
:::

## Change what the analyzer reads

The analyzer's options are the `analyzers.ci-jobs` setting in **Settings › Analyzers**, per scope like every analyzer. They set the window length, a single branch or tag to read instead of every ref, how many recent days are compared with the rest, and the change in percent and seconds that marks a job slower.

```json title="analyzers.ci-jobs · one group"
{
  "branch": "main",
  "changePercent": 25,
  "minChangeSeconds": 30
}
```
