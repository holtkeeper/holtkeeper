Whoever signs in, and however they sign in, ends up with a set of **grants**. A grant is a list of actions on a scope: _read and run analyses on team `widgets`_, _change settings on `acme/round/**`_, or _everything on every repository_. Some grants come from the person's own access, the rest from the teams they belong to. Every request is checked against them, in the panel, over MCP and in chat, so a person or an agent sees exactly the repositories their grants cover and nothing else. Lists never show what you cannot read, and a page you may not open names the permission you are missing.

## Actions

| Action                                      | Allows                                                          |
| ------------------------------------------- | --------------------------------------------------------------- |
| `repos:read`                                | See repositories and their health.                              |
| `analyses:read`, `analyses:run`             | Read analysis results and runs; run analyzers.                  |
| `audits:read`, `audits:run`                 | Read and run security audits.                                   |
| `releases:read`, `releases:run`             | See release state; run release steps.                           |
| `tasks:run`                                 | Approve agent tasks that push branches and open merge requests. |
| `knowledge:read`, `knowledge:write`         | Read and edit the Guide, notes and learnings.                   |
| `settings:read`, `settings:write`           | Read and change settings in the scope.                          |
| `credentials:read`, `credentials:write`     | See and manage credentials such as forge tokens.                |
| `ai:read`, `ai:admin`                       | See AI spend; manage AI usage.                                  |
| `users:read`, `users:invite`, `users:write` | See people, invite them, change their access.                   |
| `audit:read`                                | Read the whole audit log (only meaningful on everything).       |

`*` allows every action. The full list with what each screen needs is in [Permissions](/reference/permissions/).

Some objects belong to the whole instance rather than to repositories: forges, Automation, Settings › System. They need the action on a grant over **everything**, so a maintainer of `widgets` edits the settings of the team's repositories but not the forges, and cannot change which repositories the team owns.

## Team membership

Being in a team gives access to its repositories with no grant to hand out:

| Role in the team | On the repositories the team owns                                                                                                                                 |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Maintainer       | Everything (`*`), and may edit the team's title and members.                                                                                                      |
| Member           | Read repositories, analyses, audits, releases and settings; run analyzers, audits and releases; approve tasks; read and write knowledge; see AI spend and people. |

Both read the repositories the team **consumes**: the repository, its analyses, releases and knowledge. Membership applies at the next request after a team changes. A team's **Owns**, **Exclude** and **Consumes** patterns decide what its members reach, so only someone with `settings:write` over everything changes them. See [Teams](/guide/repos/teams/).

## Role presets

Settings › People & access offers four presets. Each is one grant on one scope you pick, except Admin, which always covers everything.

| Role       | On its scope                                                                       |
| ---------- | ---------------------------------------------------------------------------------- |
| Viewer     | Reads health, analyses, audits, releases, knowledge and settings.                  |
| Developer  | Viewer, plus runs analyzers and audits, approves agent tasks and writes knowledge. |
| Maintainer | Developer, plus runs release steps and edits settings.                             |
| Admin      | Everything on every repository: people, credentials, AI budget and integrations.   |

Personal grants add to what membership gives: use them for administrators and exceptions. Grants that match no preset show as **Custom**. A person can hold several, for example Maintainer on `acme/kit/**` and Viewer on everything.

## Delegation

People hand out access only within what they hold. Inviting someone needs `users:invite` over the scope, and the new grants must fit inside the inviter's own: an admin of `acme/**` can make someone admin of `acme/round/**` or of `acme/*/web`, but not of `tools/**` or of everything. A maintainer of `widgets` can invite someone onto the team's repositories, never beyond them. Nobody changes their own grants. Changing a person's grants or disabling them takes effect on their next request.

## Home teams are not permissions

Your **home teams** (Account › My teams) only decide what the **My teams** switch shows on list pages. They start as the teams you are a member of and the teams your grants name, and you can change them freely; they never widen or narrow access. Membership on Repos › Teams is what gives access.

## Other teams' catalog

**Reach** is one instance-wide level that decides how much of other teams' low-sensitivity catalog everyone reads: package inventories, public APIs, stack and usage counts. Off keeps people to their own teams; the middle level opens the catalog without code; the default also opens usage snippets. It never covers findings, audits, runs, releases or review output.

## How people sign in

Sign-in is set in the config file, and the permission model is the same for each:

| Sign-in  | Who                                                                                 |
| -------- | ----------------------------------------------------------------------------------- |
| Password | One `root` admin behind a password. The quickstart default.                         |
| Users    | Personal accounts with passkeys, optional single sign-on (OIDC), invites and roles. |
| Header   | Users and grants from a reverse proxy's headers.                                    |
| None     | No sign-in, one root user. For local trials only.                                   |
