Every Holtkeeper process, whatever its role, answers three endpoints without authentication: a liveness probe, a readiness probe and Prometheus metrics. Inside the panel, **Settings › System** runs the same checks on demand and adds storage, the database and the worker reports.

## Probes

| Endpoint       | Answers 200 when                                                                                                              | Use it for                              |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `GET /healthz` | The process answers.                                                                                                          | Liveness, startup, Docker `HEALTHCHECK` |
| `GET /readyz`  | The store answers a query (Postgres: migrations applied), the artifact store answers a ping, and the process is not draining. | Readiness, load balancers               |

`/readyz` answers 503 with a JSON body per check when one fails, so the body tells you which dependency is down.

```sh title="Terminal"
curl -s https://holtkeeper.example.com/readyz
```

The Helm chart wires startup and liveness probes to `/healthz` and readiness to `/readyz`; the image's own health check calls `/healthz`.

:::caution
`/metrics` needs no authentication and is served on the web Service too. If the host is public, block the path at the ingress.
:::

## Metrics

`GET /metrics` serves Prometheus text format. The ones to watch first:

| Metric                                            | Type      | Tells you                                             |
| ------------------------------------------------- | --------- | ----------------------------------------------------- |
| `holtkeeper_jobs_queued`                          | gauge     | Queued jobs due now; the scaling signal for KEDA.     |
| `holtkeeper_jobs{status="queued"\|"running"}`     | gauge     | Queue and running jobs.                               |
| `holtkeeper_jobs_finished_total{analyzer,status}` | counter   | Finished jobs by analyzer and outcome.                |
| `holtkeeper_job_duration_seconds{analyzer}`       | histogram | How long jobs take.                                   |
| `holtkeeper_webhook_events_total{forge,status}`   | counter   | Webhook deliveries from GitLab.                       |
| `holtkeeper_ai_cost_usd_total{provider,model}`    | counter   | AI spend; tokens and runs have their own counters.    |
| `holtkeeper_limiter_saturated{key}`               | gauge     | A forge or AI token at its rate or concurrency limit. |
| `holtkeeper_artifact_store_bytes`                 | gauge     | Artifact store size, listed at most every 5 minutes.  |
| `holtkeeper_draining`                             | gauge     | The process is shutting down.                         |

Store-backed series (queue, AI usage) are reported only by processes with the web role, each with the same value: aggregate them with `max`, not `sum`. The chart's `metrics.serviceMonitor.enabled` adds a ServiceMonitor for the Prometheus Operator. The full list is in the [deployment reference](/self-host/reference/deployment/#health-readiness-metrics-shutdown).

## Shutdown

On `SIGTERM` a process fails readiness at once, stops claiming jobs and gives running jobs the drain timeout (`--drain-timeout`, default `30s`; the chart's workers use `120s`) to finish. Jobs still running are then requeued and run again on another worker; the interrupted attempt counts. Give the container a grace period longer than the drain timeout — Compose uses 60 s, the chart's workers 150 s.
