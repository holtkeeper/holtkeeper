Access in Holtkeeper is a list of **grants**. Each grant pairs a scope (everything, some teams, or path patterns) with a list of actions; `*` allows every action. A check asks whether a person may do one action on one repository, on an object owned by a scope (a credential, a setting), or on the whole system, which needs a grant scoped to everything. Team members get grants on their team's repositories from membership: maintainers `*`, members the read and run actions, and every member the read actions on what the team consumes. See [Permissions and scopes](/start/concepts/permissions/) for how scopes match.

## Actions

| Action              | Lets a person                                                                                                                                                                                                  |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `repos:read`        | Read repositories: the fleet, health, a repository's hub.                                                                                                                                                      |
| `analyses:read`     | Read analyses: public API, usages, coverage, bundles, assets, CI, reviews, jobs.                                                                                                                               |
| `analyses:run`      | Run analyzers: **Measure now**, **Run analyzer…**, **Review a merge request**.                                                                                                                                 |
| `audits:read`       | Read security audits and their findings.                                                                                                                                                                       |
| `audits:run`        | Run security audits and fixes.                                                                                                                                                                                 |
| `catalog:read`      | Read other teams' catalog: packages, versions, public API, stack, usage counts and shared notes. Implied by `analyses:read` on the same scope; never covers findings, audits, jobs, releases, reviews or code. |
| `releases:read`     | Read release plans, status and timelines.                                                                                                                                                                      |
| `releases:run`      | Run release steps: propose, accept, version, deploy.                                                                                                                                                           |
| `tasks:run`         | Approve agent tasks that push a branch and open a merge request. For another team's repository the grant must cover that repository itself; your own team's grant never reaches it.                            |
| `settings:read`     | Read settings and the effective config.                                                                                                                                                                        |
| `settings:write`    | Change settings in scope.                                                                                                                                                                                      |
| `credentials:read`  | See credentials. On a grant scoped to everything, also see [secret reports](/guide/supply-chain/secret-reports/).                                                                                              |
| `credentials:write` | Add, rotate or delete credentials. On a grant scoped to everything, also change the status and notes of secret reports.                                                                                        |
| `knowledge:read`    | Read rules and learnings.                                                                                                                                                                                      |
| `knowledge:write`   | Write rules and learnings, approve or reject learnings.                                                                                                                                                        |
| `ai:read`           | See AI spend.                                                                                                                                                                                                  |
| `ai:admin`          | Manage AI spend: the budget and the provider. Includes `ai:read`.                                                                                                                                              |
| `users:read`        | See people.                                                                                                                                                                                                    |
| `users:invite`      | Invite people, with grants no wider than their own.                                                                                                                                                            |
| `users:write`       | Change people and their access.                                                                                                                                                                                |
| `audit:read`        | Read the whole audit log. Only checked on a grant scoped to everything.                                                                                                                                        |

Without `audit:read`, the audit log still lists events about repositories you can read.

## Roles

**Settings › People** hands out four presets. Each applies to one scope, except Admin, which always covers every repository. Grants that match no preset show as **Custom**; no grants at all as **No access**.

| Role       | Actions                                                                                          | Summary                                     |
| ---------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------- |
| Viewer     | `repos:read`, `analyses:read`, `audits:read`, `releases:read`, `knowledge:read`, `settings:read` | Read only.                                  |
| Developer  | Viewer, plus `analyses:run`, `audits:run`, `tasks:run`, `knowledge:write`                        | Run analyzers, start agent tasks.           |
| Maintainer | Developer, plus `releases:run`, `settings:write`                                                 | Run release steps, edit settings in scope.  |
| Admin      | `*` on everything                                                                                | Org-wide, including people and credentials. |

| Run analyzers and audits                      |        |     ✓     |     ✓      |   ✓   |

| See release plans and timelines               |   ✓    |     ✓     |     ✓      |   ✓   |

| Read knowledge                                |   ✓    |     ✓     |     ✓      |   ✓   |

AI, people, credentials and audit-log actions are not part of any narrower preset; give them with a custom grant.

## Delegation

A person may hand grants to someone else only with `users:invite` over each scope and only within their own grants. An admin of `acme/round/**` can invite an admin of `acme/round/**` or of `acme/round/web`, but never of `acme/**`, another folder or everything. A maintainer of team `widgets` can invite onto the team's repositories, never beyond them.

## MCP tokens

A token acts as its owner, cut down to `repos:read`, `analyses:read`, `audits:read`, `knowledge:read` and `releases:read`. Besides reading, it can only propose learnings, which people may reject before they activate (`propose_learning`), and ask for a review of a merge request, at most one per commit (`code_review`). It never runs release steps or tasks, whatever its owner may do. Its tools check the owner's grants per repository: package tools catalog reach, knowledge and `repo_rules` `knowledge:read`, its `releases` topic `releases:read`, and its `commits` and `assets` topics, `check_commit_message`, `test_ids`, `repo_assets` and `code_review` `analyses:read`. `ask` reads through the same tools with the same grants.

A token may also report exposed secrets with `report_secret_exposure`, unless its owner set **Report exposed secrets** to **Off**. The report needs no permission beyond reading: a report naming a repository is accepted only when the owner may read it (`repos:read`). Only the owner sees and changes that choice; it is not audited. Reading and handling reports needs `credentials:read` and `credentials:write` on everything, which a token never gets.

The API still accepts the `release` and `tasks` scopes on tokens created earlier, but no MCP tool uses them: such tokens work as read tokens.

See [Tokens and scopes](/agents/tokens/).

## Refusals

A refused request answers `403` with the missing action and, for a repository, its `forge:path`. It never names teams, and a repository you cannot see gets the same answer as one that does not exist. MCP tools answer the same as an error result. The panel hides buttons you lack the permission for and shows a card naming it on pages you cannot open.
