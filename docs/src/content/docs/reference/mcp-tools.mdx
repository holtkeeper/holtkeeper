The MCP endpoint (`POST /mcp`) serves the tools below, in this order. Every tool reads stored data only, unless marked **writes**. Arguments marked `?` are optional; repositories are always `forge:path` (`gitlab:acme/checkout-web`). Only `propose_knowledge` and `propose_rule_change` write, and both leave a proposal for people to review, plus `report_secret_exposure`, which files a [secret report](/guide/supply-chain/secret-reports/); no tool starts tasks, runs release steps or approves anything. Fleet-wide tools (security findings, licenses, stack usage), release state and job tools are not served over MCP; people find them in the panel and in [Chat](/guide/chat/threads/). Which tools a client sees depends on its owner's access; **Account › Connect agents › Tool reference** shows the live list with every argument's description.

For a walkthrough with example calls, see [What agents can ask](/agents/tools/).

## Packages and usage (catalog)

The public API of the organization's packages and how every repository uses its dependencies. `version` is a version, a tag, `latest` (newest release, the default) or `head` (default branch). `repo` picks one of several repositories with a package of the same name; for third-party packages, the repository whose version is the default. `ecosystem` is `npm` or `Go` (default: Go for a name with a `/` and no `@scope`, else npm).

| Tool                  | Description                                                                                                              | Arguments                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `list_packages`       | Indexed packages (newest version of each) with repository, description, entry points and recorded versions.              | `query?` (substring of name, description or repository)                                  |
| `get_package_api`     | The public API of one package version: every entry point with every export, its doc comment and declaration.             | `package`, `version?`, `subpath?`, `docs?` (default true), `repo?`, `ecosystem?`         |
| `search_symbols`      | Finds exports by name (exact, prefix, substring) or doc comment text across the newest version of every package.         | `query`, `package?`, `kind?`, `limit?` (1–50, default 20)                                |
| `get_symbol`          | One export in full: doc comment, declaration, source location and the import statement to use.                           | `package`, `name` (`default` for the default export), `version?`, `subpath?`, `repo?`    |
| `list_versions`       | Recorded versions, newest first, with tag, date, export count and how the API changed from the version before.           | `package`, `repo?`, `ecosystem?`                                                         |
| `diff_versions`       | Removed, changed, deprecated and added exports between two versions, and whether the bump matches semver.                | `package`, `from?`, `to?`, `repo?`, `ecosystem?`                                         |
| `package_usage`       | Who uses a package: versions per repository, every export used, how, JSX props passed and members read.                  | `package`                                                                                |
| `find_usages`         | The code of the uses: file, line and snippet, grouped by repository.                                                     | `package`, `export?`, `member?`, `prop?`, `kind?`, `repo?`, `limit?` (1–100, default 30) |
| `upgrade_impact`      | What an upgrade breaks: the API diff joined with the uses, as `breaking`, `check` or `deprecated`, with the code.        | `package`, `from?`, `to?`, `repo?`, `ecosystem?`                                         |
| `repo_packages`       | The packages one repository imports, with versions, ranges and uses; without `repo`, the repositories with a record.     | `repo?`                                                                                  |
| `evaluate_dependency` | Everything known about a dependency before adding or upgrading it: users, advisories, licenses, bundle share, knowledge. | `package`, `ecosystem?`, `version?`, `repo?`                                             |
| `who_uses`            | Which teams and repositories use a library, internal package or stack tool, at which versions and how far behind.        | `subject` (`npm:date-fns`, `Go:example.com/kit`, `tool:node` or a bare name)             |

Enumerations: `search_symbols` `kind` is `function`, `class`, `interface`, `type`, `variable`, `enum`, `namespace` or `reexport`. `find_usages` `kind` is `call`, `new`, `jsx`, `member`, `type`, `extends`, `reexport`, `reference` or `import`. Go packages of the organization's repositories are named by their full import path (`example.com/kit/log`); the catalog answers for them first, then the library index. `package_usage` takes a Go module path (all its packages) or a package import path, and `upgrade_impact` covers Go too, from syntactic uses and, when the usages job has the `go` toolchain, the methods and fields reached through values (`typed: true` sites).

## Knowledge

| Tool                | Description                                                                                      | Arguments                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `search_knowledge`  | Searches accepted knowledge entries, best match first; without `query`, every applicable entry.  | `query?`, `repo?`, `kind?`, `package?`, `subject?`, `topic?`, `limit?` (1–30, default 10) |
| `get_knowledge`     | One entry in full: body, status, scope, packages, topics, evidence and the entry it supersedes.  | `id` (or its citation `[kb:<id>]`)                                                        |
| `propose_knowledge` | **Writes.** Proposes an entry for one repository; it waits for review, duplicates are not added. | `title`, `body`, `repo`, `kind?`, `topics?`, `packages?`, `evidence?`                     |

`kind` is `decision`, `convention`, `migration`, `quirk` or `howto`. A package in `packages` is `{ ecosystem, name, from?, to? }` with semver ranges; evidence is `{ label, url }`.

| Tool                   | Description                                                                                                            | Arguments                                                               |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `repo_rules`           | The repository's Guide: team rules from every scope, learned rules, policies, generated text, then knowledge notes.    | `repo`, `task?`, `section?`, `only?`                                    |
| `propose_rule_change`  | **Writes.** Proposes one imperative rule for a Guide section; people review it under Knowledge › Learnings.            | `repo`, `section`, `rule`, `reason`, `scope?`                           |
| `test_ids`             | The test id convention and existing test ids per component.                                                            | `repo`, `path?` (file, folder or component name), `limit?` (default 20) |
| `suggest_test_ids`     | Interactive elements of one component file without a test id, each with a suggested id. Deterministic.                 | `repo`, `file`, `content` (the file's current text)                     |
| `commit_conventions`   | How commit messages and branch names should look: template, rules with their source, real examples, team notes.        | `repo`, `commits?` (history to learn from, default 100)                 |
| `check_commit_message` | Checks a commit message or merge request title and a branch name; errors break enforced rules, warnings history.       | `repo`, `message?`, `branch?`                                           |
| `release_rules`        | How a repository releases, in plain language: branches, flow, tag format, bump rules, acceptance, gates, environments. | `repo`                                                                  |

`release_rules` needs `releases:read` on the repository. `task` is `agent` (default), `review`, `chat` or `release-notes`. `section` and `only` are `general`, `review`, `testing`, `testids`, `assets`, `commits` or `releases`. `propose_rule_change` `scope` is `repo` (default), `family`, `path` (the repository's folder), `team` (its first owner team), or an exact scope such as `path:<forge>:<folder>`, `team:<key>`, `family:<id>` or `repo:<forge:path>`.

## Third-party libraries

`package` is the library (`zod`, `github.com/spf13/cobra`); a Go module path with its `/vN` suffix or a package path inside the module finds the module, and `ecosystem` defaults to Go for such paths, else npm. `version` defaults to the version `repo` uses, else the newest indexed one. Go modules carry their package docs, and `library_source` reads the module zip. Offered when the instance indexes library docs.

| Tool                    | Description                                                                                                          | Arguments                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `library_versions`      | Indexed versions with roles (used, latest, patch, minor, major, first), dates, deprecations, docs sources and users. | `package`, `ecosystem?`, `repo?`                                                    |
| `search_library_docs`   | Full-text search over shipped docs, repository docs at the version tag and release notes.                            | `query`, `package?`, `ecosystem?`, `version?`, `limit?` (1–30, default 10), `repo?` |
| `read_library_doc`      | One document by path, or one section by heading; without `path`, the list of documents.                              | `package`, `ecosystem?`, `version?`, `path?`, `heading?`, `repo?`                   |
| `library_changes`       | Changelog sections and release notes in (`from`, `to`], with migration guides for every major crossed.               | `package`, `ecosystem?`, `from`, `to`                                               |
| `search_library_issues` | Known issues and answered discussions matching an error message or symptom, with state, fix version and link.        | `package`, `ecosystem?`, `query`, `version?`, `limit?` (1–20, default 5), `repo?`   |
| `library_source`        | A file listing or one file with line numbers; the snapshot is made on first request.                                 | `package`, `ecosystem?`, `version?`, `path?`, `start?`, `end?`, `repo?`             |

## Reviews

| Tool            | Description                                                                                                                                                 | Arguments                                                   |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `review_status` | Holtkeeper's review of a merge request: verdict and summary of the newest run, findings with file and line, open threads, earlier runs and what to do next. | `repo`, `branch?` (source branch), `mergeRequest?` (number) |

Pass `branch` or `mergeRequest`; one of them is required. With `branch`, the tool takes the branch's open merge request, else its newest one. The answer ends with a **Next** section: what to fix, whether a review is queued or running, why none will start by itself, or "Nothing left to fix." It needs `analyses:read` on the repository. See [Follow a review from your agent](/agents/review-agent/#follow-a-review-from-your-agent).

## Security

Offered unless the token's owner set **Report exposed secrets** to **Off** or the instance runs with `server.secretReports: false`. Its description asks agents to call it on their own as soon as a secret shows up, masked and without naming anyone, and then to tell the user the secret needs rotating.

| Tool                     | Description                                                                                                                                  | Arguments                                                                                        |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `report_secret_exposure` | **Writes.** Reports a secret of the organization that got exposed in the session, under the owner's name or anonymously as the token is set. | `kind`, `identifier`, `masked`, `channel`, `service?`, `repo?`, `fingerprint?`, `circumstances?` |

`kind` is `api-key`, `token`, `password`, `private-key`, `certificate`, `connection-string`, `webhook-url` or `other`; `channel` (where it showed up) is `chat`, `command-output`, `file-read`, `commit`, `log`, `issue-or-merge-request` or `other`. `identifier` is the variable, key or setting that holds the secret (`WIDGET_API_KEY`, `unknown` when it has none), never the value. `masked` is at most the first 4 characters, `…` and the length (`wk_l…(40)`), never more than a quarter of the value and nothing of a password (`…(12)`). `fingerprint` is the first 16 hex characters of the SHA-256 of the exact value, not for passwords. `service` is the host or name the secret opens; `repo` is `forge:path`; one of them is required. `circumstances` describes how it happened in up to three sentences without people's names.

The tool refuses, and stores nothing for, text fields that look like a secret value, masks that show too much and malformed fingerprints, without repeating what was sent. The server refuses reports that are not about the organization: `repo` must be a fleet repository the token may read, or `service` must match `security.secretReports › services` or a forge host. A repeat of an open report is counted on it instead of filed again. Anonymous calls are not recorded in usage statistics.

## Errors

A tool that needs a permission you lack answers with an error result whose text names it, with the missing action and repository as structured content. Other failures start with `Failed:`. Answers longer than about 80 000 characters are cut with a hint to narrow the request (`subpath`, `docs: false`, or `search_symbols` and `get_symbol` for single names).
